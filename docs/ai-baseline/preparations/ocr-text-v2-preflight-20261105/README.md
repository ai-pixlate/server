# OCR Text v2 확대 사전 점검 — 34장 / 112개 섹션 후보

점검일 2026-11-05. **사전 점검만 수행한 후보 목록이며 신규 정답·동결본·평가 결과가 아니다.** OCR Text v1과 12개 부분 평가를 보존한 커밋은 `b3ff928025b28a536acf5618ea4225a178243513`이다. 사전 점검 보고서·색인·점검 스크립트는 사용자 요청에 따라 별도 커밋으로 보존한다.

## 1. 결론과 수량

기존 로컬 `pipeline/out/ocr_input/v1/`에 GS-01~03 원본 34장을 연속으로 덮는 **112개 고정 섹션**이 있다. 2026-09-23에 분할 5차 결과를 고정한 개발용 OCR 입력이며, v1.0.1이 34장을 모두 성공 처리해 만든 분할 집합은 아니다. 전체 비교용 **OCR Text v2 입력 후보로 재사용하는 방안**이며 아직 채택·동결하지 않았다.

## 2. 이미지·원본·누락 점검

- 원본 34개: gs-v1 manifest의 파일 해시·해상도 일치.
- 섹션 PNG 112개: 모두 존재, provenance 해시 일치, split.json의 크기 일치. 폭 800/830/1000px, 높이 201~3,470px.
- 섹션 top_offset이 0부터 원본 끝까지 빠짐/겹침 없이 이어짐을 확인했고, 디코딩한 섹션 픽셀은 공식 원본의 해당 crop과 112/112 일치했다. **정답 줄 bbox 검증은 아니다.** 이미지를 새로 저장하거나 재분할하지 않았다.
- provenance가 가리키는 origin/split·debug·run 파일 해시도 확인했다. 파일 누락·해시/크기/픽셀 불일치 0건.
- 섹션 이미지 합계 63,951,611바이트(약 61.0MiB). 입력은 로컬 전용 Git 제외 경로다. GitHub에 공유 완료된 것으로 표시하지 않는다. v2를 만들 때 입력 아카이브/보관 위치와 해시를 함께 관리해야 한다.
- 전체 경로·SHA-256·해상도·원본 연결·기존 정답 대응·출력 후보는 [inventory.json](inventory.json)의 sources/sections에 있다. 아래 목록과 같은 112개다.

## 3. 정답 재사용과 추가 검수량

- **재사용 가능:** OCR Text v1의 12개·369줄. text·ID·lines 순서·승인 근거·이미지 해시를 v2에서 추적한다. 기존 v1은 수정하지 않는다. L008 빈 정답 결정도 이 항목에 한해 승계한다.
- **새로 작성할 범위:** 100개 섹션. 추적된 OCR 줄 정답은 기존 12개뿐이며, 서비스 평가용 reference_unit은 핵심 정보/정책 기준이므로 전체 전사 정답으로 대체할 수 없다.
- 과거 100개 섹션 OCR 파일과 입력 이미지가 모두 존재·일치한다. 이 출력은 **정답이 아니고 v1.0.1 출력도 아니다**: 커밋 `e3a50b2c623b3cec0fef38af8fd0de6d75867bb5`, GPU 실행. 실제 서비스 버전 비교에 그대로 섞지 않는다.
- 과거 출력의 작업량 참고치는 **1,815개 검출 영역·25,460자(원문 문자열 길이 합)**다. 검출 영역은 정답 줄이 아니며 분리·병합·중복·누락·빈 출력이 있어 실제 전사량의 하한/상한도 아니다. 원본 전체의 누락 확인이 별도로 필요하다. 모델 출력을 정답으로 복사하지 않는다.
- 검수 속도 실측 자료가 없으므로 완료 소요시간을 확정할 수 없다. 예산 시나리오로만 1,815개 참고 영역당 30초/60초이면 약 15.1시간/30.3시간이며, 신규 전사·누락 영역 발견·수정·최종 확인 시간은 추가다. 이 속도는 관측값이 아니므로 일정 약속에 사용하지 않는다. 우선 5~10개 섹션에서 사람의 전사/검수 시간을 기록한 뒤 나머지를 산정하는 것을 권장한다(이번에는 실시하지 않음).

## 4. OCR v4·도구 호환성

- v4는 섹션별 문자열 비교이므로 112개로 확장 가능하다. N/S/D/I와 문자 가중 집계, 공백·NFC·순서 규칙, 0분모/실패 상태를 그대로 적용한다. 제품/실측 코드나 H01~H05·OP01~OP07을 바꿀 필요가 없다.
- `tools/baseline/ocr.py`는 섹션 수를 하드코딩하지 않는다. freeze의 expected_sections/expected_lines는 승인 자료에서 받으므로 v2의 전사 완료 후 실제 개수로 설정할 수 있다. v1 동결 경로에 추가하거나 덮어쓰지 않는다.
- 기존 `truth.py` 웹 검수 도구는 SAMPLES 12개와 v3의 bbox 검수에 묶여 있다. 100개 추가 텍스트 검수에는 목록/저장 경로를 외부 입력으로 받는 별도 v2 작업 공간 연결 또는 텍스트 전용 검수 방식이 필요하다. 이번에 구현하거나 새 정답 파일을 만들지 않았다.
- 입력 준비 도구는 같은 보존 형식의 회차에 재사용 가능하지만 매 버전 보정 후 반환 경계와 입력 해시를 다시 확인해야 한다. 섹션 키 이름만으로 연결하지 않는다.
- 텍스트 연결 순서는 v1에서 승인한 lines[] 원칙을 유지하고, 신규 전사의 읽기 순서도 검수한다. 다단·표·제품 라벨·판독 불가/잘림 항목의 기준은 전사·채점 전에 결정한다. L008의 빈 정답 처리를 새 판독 불가 항목에 자동 확대하지 않는다.
- 112개 모두 높이 4,000px 이하여서 타일 OCR·긴 이미지 성능을 대표하지 못한다. 전체 34장을 덮는 고정 crop OCR 평가와 서비스 전체 파이프라인 품질은 구분한다.

## 5. 출력 재사용·추가 실행 및 비용

최초 회차의 계측은 v1.0.1 `ocr.run()` 최종 반환을 순서대로 보존한다. 67개는 원본 DB ID→분할 이벤트→해당 섹션 위치/크기→DB image_key→객체 바이트 해시로 입력 동일성을 확인했다. 3개 보완 출력은 기존 검증을 재사용한다. 결과의 품질은 이번에 평가하지 않았다.

추가 **42개 섹션**: GS-01 2개, GS-02 4개는 고정 crop과 최초 분할이 달라 대응 출력이 없다. GS-03 36개는 상품 분석 실패에 따른 미도달 또는 입력 바이트/시도 연결 미확인이다. 예전 GS-03 후보를 좌표만으로 재사용하지 않는다. 후보 목록은 inventory.json에 남겼으며 더 많은 원시 증거를 확보하면 재사용 수가 달라질 수 있다.

현재 조건으로는 v1.0.1 고정 환경에서 42개에 로컬 OCR 1회씩 추가 실행해야 한다. 모두 4,000px 이하이므로 정상 경로 엔진 호출은 42회이며, 실패 시 임의 재시도 없이 기록한다. Gemini·번역·LaMa·상품 전체 재실행은 필요하지 않다. **외부 API 비용 USD 0**(로컬 CPU 모델만 사용 조건), 전력·장비 비용은 미산정이다.

관측된 재사용 67개 CPU 실행시간은 중앙 16.42초, 25~75백분위 약 8.64~26.02초다. 동일 시간 분포를 가정한 42개 계획치는 약 11.5분, 참고 구간 약 6.0~18.2분이며 초기화·검증·저장·실패 처리는 별도다. 통계적 예측 구간이나 보장 시간이 아니다. 옛 GPU 100개 실행시간을 Windows CPU 예상에 사용하지 않는다.

2·3차 통합은 같은 112개 이미지 바이트와 v2 동결 정답을 사용해 각 제품 SHA에서 새 출력으로 평가할 수 있다. 재분할을 매번 수행하면 입력이 바뀌므로 고정 OCR 비교가 아니다. 후속 버전은 원칙적으로 112개 출력이 필요하고, 해당 버전의 동일 입력·출처가 증명된 출력만 재사용한다. API/장비 비용과 소요시간은 그 실행 환경에 따라 다시 확인한다.

## 6. 다음 단계 — 별도 승인 필요

1. 기존 고정 입력 112개를 v2의 공식 OCR 비교 입력으로 채택할지 확정하고 공유·백업 위치를 정한다.
2. OCR Text v2 전용 작업 공간/검수 방식을 마련한다. v1 12개는 참조·추적하고 새 100개를 전사·전수 검수한다. 새 판독 불가/표/읽기 순서 결정과 출력 노출 이력을 남긴다.
3. 사용자 검수 승인 후 v2를 별도 버전으로 동결한다. v1의 동결·과거 측정 결과는 유지한다.
4. v1.0.1 추가 42개 실행 범위와 실패 처리, 전체 112개 채점을 별도로 승인받은 뒤 진행한다. 출력 준비와 정답 작성은 분리하며 OCR 출력을 정답으로 삼지 않는다.
5. 같은 입력·v2 기준으로 2·3차 통합을 비교한다. 기존 12개 부분 결과와 112개 전체 결과를 동일 분모 성능 비교로 표시하지 않는다.

이번 점검에서 전사·검수·동결·추가 OCR·CER 재계산·모델 API 호출을 수행하지 않았다. 사전 점검 산출물의 보존 커밋은 평가셋 채택이나 추가 실행 승인을 의미하지 않는다.
