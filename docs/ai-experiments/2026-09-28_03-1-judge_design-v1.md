## 0. 범위와 원칙

- 범위: `analyze()` 이후, 섹션 확인(사용자 개입 1) 이전의 두 단계. ③-1 AI 섹션 판정 → `content_findings`, ③-1' 정책 적용 → `section_verdict` 후보 + 섹션 버킷 권고. [계약 1.1, 1.3]
- MVP 판정 데이터는 **사전 2종**(규제사전 16행 · 현지부적합 8행)이다. 사이트별 게시 정책은 MVP 이후(`open-questions.md` 4절, 구 #2). **이것이 판정 항목 범위(#4-2)를 확정한 것은 아니다** — 이번 설계가 지원하는 항목 범위는 [D3-1]의 승인 대상이다.
- 두 단계는 책임 · 입력 · 출력 · 재실행 조건을 분리한다(1절). ③-1은 사전 항목의 해당 여부 · 근거만 내고 **어떤 정책값(판정값 · 허용 · 규제 분류)도 읽지 않는다.** 포함 · 제외 계산과 정책값에 따른 예외 처리는 전부 ③-1'의 결정적 로직이 한다. [계약 1.3] [`pipeline.md` 6절]
- 구현 소유자는 둘 다 AI 서버(`open-questions.md` 5절 #6). DB · API 계약은 BE 소유이므로 저장 형식에 닿는 결정은 전부 `[BE 합의]`로 표시한다.
- 부분 부적합은 섹션 전체 제외(5절 #8). 제외로 판정된 경우에만 적용한다.

### 2.2 ③-1a 검출 규칙 — `[설명서 §2 · 잠정]` · `open-questions.md` #42 [D1]

**전제의 불일치** — 설명서 §2는 "어절 시작과 일치 + 조사 · 어미 허용, 2어절 이상은 공백을 지우고 비교"라 적고, 현지부적합 `02_판정규칙`은 "리터럴 · 공백 제거 비교"라 적으며 `원`의 오탐 문맥으로 `연구원` · `인원` · `원료` · `원하시는`을 든다. `연구원`이 후보가 되려면 어절 시작 일치가 아니라 부분 문자열 비교여야 하므로 두 서술은 같은 엔진을 뜻하지 않는다. `kr_freq`(LC-06 63/66)도 부분 문자열 기준으로 재집계했다고 적혀 있다(설명서 §3 "리터럴 기준 재집계 · `원` 추가(16→63)"). 어느 쪽이 데이터 담당의 엔진인지 [원문 확인] · 데이터 담당 확인.

**비교 기준** — 오탐 감소가 아니라 **실제 제외 대상의 미탐**을 먼저 본다. [D3-2] 안 A에서는 매칭이 없으면 AI를 부르지 않으므로 검출 미탐은 곧 "검사 완료 · 포함 권고"가 된다.

**정규화(공통)** — 블록 `source_ko`와 패턴 모두: NFKC → 줄바꿈(`\n`) · 공백 제거 → 소문자(영문 패턴 `GIFT` · `G마켓` 때문). 정규화 문자열의 각 문자가 원문 `source_ko`의 몇 번째 문자에서 왔는지 **오프셋 대응표**를 함께 만든다(2.5절 근거 객체가 원문 구간을 잘라내는 데 쓴다. NFKC로 문자 수가 바뀌는 경우는 대응표가 원문 쪽 구간으로 흡수한다).

| 안 | 규칙 | `10,000원` | `3만원` | `5천원` | `원료` | `연구원` | `인원` | `원하시는` |
|---|---|---|---|---|---|---|---|---|
| **추천 B** 공백 제거 부분 문자열 | 정규화 텍스트에 정규화 패턴이 부분 문자열로 있으면 매칭. 모든 패턴 종류(한글 · 다어절 · 숫자 · 기호 · 영문)에 같은 규칙 | ✓ | ✓(`만원` · `원`) | ✓ | ✓(오탐, AI가 거름) | ✓(오탐) | ✓(오탐) | ✓(오탐) |
| A 어절 시작 접두 일치 | 어떤 어절이 패턴으로 시작하면 매칭(조사 · 어미 허용). 다어절 · 숫자 · 기호 · 영문은 B와 같음 | **✗ 미탐** | **✗ 미탐** | **✗ 미탐** | ✓ | ✗ | ✗ | ✓ |
| A' 접두 + 숫자 뒤 허용 | A에 "앞 문자가 숫자 · 숫자 구두점이면 허용"을 더함 | ✓ | ✓(`만원`) | **✗ 미탐**(`천`이 한글) | ✓ | ✗ | ✗ | ✓ |

- 추천 B 이유: (1) **위 표의 가격 예제에서** 미탐이 0이다. A · A'는 정상 가격 표기를 놓치고, 놓친 것은 AI 호출 없이 포함 권고가 된다. 이 "미탐 0"은 제시한 예제에 한한 성질이며, OCR 오류(`원`이 `윈`으로 읽힘) · 블록 분리(`10,000` | `원`) · 사전에 없는 표현(`₩` · `KRW`)의 미탐은 매칭 규칙과 별개로 실측에서 센다. (2) 데이터 담당이 패턴을 "넓게 잡고 오탐은 AI가 거른다"고 설계했다. `kr_freq`가 같은 부분 문자열 엔진으로 집계됐는지는 확인 요청 대상이며(11절), 확인되면 실측 수치와 비교할 수 있다. (3) 규칙이 하나라 오프셋 대응이 단순하다. 비용: 오탐이 AI 호출을 늘린다(LC-06 신호가 상품 63/66) — 실측에서 호출 수와 비용을 재고, 줄여야 하면 A'를 **패턴별 옵션**(예: 특정 항목만 접두 일치)으로 실험한다. 규칙을 바꾸는 판단은 위 예제표의 미탐 0을 유지하는 범위에서만.
- **블록 경계**: 매칭은 블록 안에서만. 블록을 넘는 매칭은 v1 없음(#42).
- **결과 단위**: 원시 매칭 = (사전 항목 ID, 패턴, `block_key`, 정규화 구간, **원문 구간** `raw_span{start,end}`, 원문 텍스트). 같은 항목 · 같은 블록에서 여러 번 매칭되면 각각 보존한다.
- **하지 않는 것**: 억제 · 겹침 처리 · 규제 분류 필터 · `allowed` 제외. 전부 ③-1'(3.2절)에서 한다. 검출은 사전의 정책 필드를 읽지 않는다.

### 2.3 ③-1b 판정 항목 범위와 호출 범위 [D3-1] [D3-2] [D3-3] · `open-questions.md` #5 · #4-2

| 안 | 내용 | 호출 수(섹션 100개 기준) |
|---|---|---|
**D3-1 지원 항목 범위 — 실측 전에 승인 필요(A · B 공통).** 이 설계가 판정하는 항목은 현지부적합 LC-01~08(LLM 맥락 판정)과 규제사전 16행(규칙 매칭만)이다. 기존 #4-2 항목(비포·애프터 · 시술 비유 · 타사 비교 · 외부 플랫폼 표시)은 v1 미지원이며, 이는 사이트별 게시 정책 제외(구 #2)와 별개의 결정이다. 어느 호출 방식을 택하든 이 범위 승인 없이는 입력 · 응답 검증 · finding 조립을 구현할 수 없다.

**D3-2 실측에 쓸 호출 방식 — 실측 전에 결정.** LLM이 판정하는 항목은 어느 안에서도 **LC 8개뿐**이다. 규제 16행은 규칙 결과만 쓰고 LLM에 보내지 않는다(C 제외). 안의 차이는 "어느 섹션에서 LLM을 부르는가"다.

| 안 | LLM 호출 섹션 | LLM에 보내는 항목 | 호출 수(섹션 100개 기준) |
|---|---|---|---|
| A 매칭 한정 호출 | 현지부적합 매칭이 1개 이상인 섹션 | 매칭된 LC 항목만 | 매칭 있는 섹션 수(실측 전 미상) |
| **B 전 섹션 호출** | 모든 섹션(텍스트 없는 섹션 포함) | LC 8개 전체(매칭 여부는 참고 표시) | 100회 |
| C | A + 규제 매칭 섹션 | LC + 매칭된 RG | A보다 많음 |

추천 = 실측 1회는 **B**. 이유: 계약 1.2 "텍스트가 없는 섹션도 이미지 기반 판정 대상"과 맞고, "매칭 없는 섹션에는 판단할 것이 없다"는 전제가 확인되지 않았으며(OCR이 놓친 텍스트를 이미지에서 볼 수 있다), B로 돌려야 매칭 없는 섹션의 관찰값이 생긴다. C는 설명서가 규제 문맥 판단을 N4 영어 단계(F-TRN-03)에 두므로 v1 범위로 끌어오지 않는다.

**D3-3 운영 호출 방식 — 실측 뒤 결정.** 실측에서 "매칭 없는 섹션에서 LLM이 `present`를 낸 건"을 먼저 **관찰값으로 집계**하고, 육안 검수로 실제 부적합 여부와 원인(OCR 미검출 / 사전 패턴 부족 / 블록 분리 / LLM 오탐)을 분류한 뒤 그 분류 결과로 판단한다. 관찰값 자체를 OCR 미검출 수로 읽지 않는다. A로 바꾸려면 아래를 각각 승인해야 한다(하나라도 없으면 A는 구현하지 않는다):

1. OCR 미검출로 생기는 판정 공백(패턴이 이미지에는 있으나 OCR 텍스트에 없는 경우)을 수용할지 — 육안 검수 분류의 "OCR 미검출 · 실제 부적합" 건수로 판단.
2. "매칭 없음 · AI 미검사"를 `content_findings: {findings: []}`(검사 완료)로 표시해도 되는 범위 — 2.5절의 누락 정의와 연결.
3. 계약 1.2 · 1.3의 이미지 판정 규칙을 어떻게 개정할지 — `open-questions.md` 3절 B(상위 문서 수정)에 등재.

B를 유지하면 1~3은 필요 없고 비용이 기준이 된다. D3-1(항목 범위)은 어느 쪽이든 필요하다.

### 2.4 ③-1b 입력 구성 [D4] [D5]

- **섹션 이미지 동봉** [D4]: 추천 = 동봉. 크기는 **폭 기준** `judge.image_width_px = 768`(잠정) — ①과 같은 근거(긴 띠에서 긴 변 기준 축소는 글자 판독이 불가). 세로가 아주 긴 섹션(②의 4,000px 초과 유형)은 v1에서 창 분할 없이 그대로 보내고 실측에서 판독 가능 여부를 본다. 대안: 긴 변 기준 1024(④ 라벨 판정 기준값) — 짧은 섹션에는 유리하나 긴 섹션에서 글자가 사라진다. 이미지를 동봉해도 근거 출처는 AI가 실제로 쓴 것을 보고한다(2.5절).
- **앞뒤 섹션 텍스트** [D5]: 추천 = 같은 원본 이미지 안의 앞 1 · 뒤 1 섹션의 블록 텍스트를 "참고 문맥"으로 동봉하되 근거 블록으로는 지정하지 못하게 한다(근거는 현재 섹션 블록만, #48). 원본 이미지 경계는 넘지 않는다. 이유: PoC `sec_adj`가 앞뒤 텍스트 동봉 조건이었고, 현지부적합 예시("1+1기획"은 구성명 / 행사 문구)는 이웃 섹션이 갈라 준다. 대안: 문맥 없음(비교 실험 기준선).
- **사전 맥락 2열**: 판정 대상 항목마다 `제외하는 맥락` · `제외하지 않는 맥락` · 항목명을 그대로 전달한다. 안내문(셀러 문장) · `kr_freq` · 판정값은 보내지 않는다(판정 근거가 아니며 정책값이다).
- **판정 항목과 매칭 정보**: 보내는 항목은 LC 8개(안 B) 또는 매칭된 LC 항목(안 A)이며 규제 항목은 보내지 않는다. 현지부적합 매칭이 있으면 매칭된 블록 · 패턴을 항목별 "후보 표시"로 함께 보낸다(안 B에서는 참고, 안 A에서는 호출 근거). 응답 검증은 보낸 LC 항목 집합을 기준으로 한다(2.6절).
- **휴리스틱 역할 · 규제 매칭**: 보내지 않는다(v1 기준선).

### 2.5 ③-1 출력 — `JudgeResult` = `content_findings` [계약 4.1] + 근거 객체

  "section_key": "sec_12_03",
  "status": "ok",
  "content_findings": {
    "schema_version": "1",
    "findings": [

       "evidence_block_ids": ["blk_003", "blk_004"], "evidence_source": "text",

       "evidence_block_ids": ["blk_007"], "evidence_source": "text",

- `content_type` 값 [D6] · `open-questions.md` #4-1: **추천 A = 사전 항목 ID(`LC-xx` · `RG-xxx`)**. 이유: 사전 `id`는 변경 금지 규칙이 있는 안정 식별자이고(규제사전 00_읽는법), 정책 적용이 사전 행을 찾는 키가 그대로 되며, 계약 4.1이 예정한 "값 목록 별도 정의"에 구조 변경 없이 들어간다. 대안 B = 상위 유형(`local_unsuitable` · `regulatory`) + finding에 `dictionary_ref` 키 추가 — "콘텐츠 유형"이라는 계약 의미에 더 가깝지만 계약 4.1에 없는 키를 추가해야 한다. 어느 쪽이든 값 목록은 계약에 등재해야 하므로 [BE 합의]. 정하기 전까지 코드에서 확정하지 않는다.
- **finding 단위**: 사전 항목당 1개(같은 항목이 여러 블록에 걸려도 하나, 근거 블록은 합집합). 항목은 서로 독립이다 — 한 항목의 `absent`가 다른 항목에 영향을 주지 않는다(#4-4).
- **`allowed` 행도 finding이 된다**(예 `f_03`). ③-1은 판정값을 모르므로 구분할 수 없고, 구분하지 않아야 정책값 변경 시 재계산이 성립한다(1절). `allowed`를 verdict로 만들지 않는 것은 ③-1'의 일이다.
- `status`: 규제(규칙) = `present`. 현지부적합(AI) = `present`(제외하는 맥락) · `absent`(제외하지 않는 맥락) · `uncertain`(맥락 판단 불능).
- **`evidence_source`는 실제 근거다.** 규칙 매칭 = `text`. AI 판정은 응답에서 `evidence_source ∈ {text, image, image_and_text}`를 항목별로 받아 그대로 쓴다(2.6절 검증). 이미지를 동봉했다는 이유로 `image_and_text`를 쓰지 않는다. `image`(이미지만 근거)면 `evidence_block_ids`는 비어 있을 수 있다. [계약 4.1]
- **근거 객체 `matches`**: 규칙 매칭의 위치 · 패턴 · 원문 텍스트. `content_findings`(계약 구조)에는 넣지 않고 `JudgeResult`의 형제 필드로 두며, ③-1'의 **정상 입력**이다(디버그 기록이 아니다). `problem_text`는 여기서 나온다(3.3절). 저장 위치 [D13]: 정책 재계산(계약 9장)이 저장된 finding만으로 가능하려면 `matches`도 저장돼야 한다. 추천 = `content_findings`의 finding에 `matches` 키를 추가하는 계약 확장(4.1). 대안 = `audit_log.detail`의 입력 finding 스냅샷에 포함(재계산 시 audit에서 읽어야 함). [BE 합의]
- **누락 · absent · NULL**: 매칭이 없어 검사되지 않은 항목은 finding을 만들지 않는다(누락). `absent`는 "검사해서 해당 없음", 누락은 "검사 범위 밖". `checked.items`가 검사 범위이고 `event_log.payload`에도 남긴다(계약 9장). `content_findings=NULL`은 ③-1 실패 · 미실행(2.6절)에만 쓴다(#45). 누락을 "검사 완료"로 표시해도 되는 범위는 [D3-3] 승인 2번.
- `detected_by`(rule / llm)는 계약 4.1에 없다(#48). `matches`가 있으면 규칙 finding임을 알 수 있으므로 별도 키를 두지 않는다. 계약 확장은 [BE 합의].
- **혼합 섹션**(현지부적합 읽는법: 살려야 할 내용이 섞이면 `needs_fix`): v1은 AI가 판정값을 낮추지 않는다. `irrelevant` · `needs_fix` 모두 제외 버킷이라 버킷 결과는 같고 안내문만 달라진다. AI 출력의 `reason`에 혼합 여부를 서술하게 하고, 필드화는 #45 · #7 결정 후. [설명서 §3 · 잠정]

### 2.6 ③-1b 응답 검증과 실패 · `open-questions.md` #46 [D7]

- 응답: JSON 스키마 강제 `{"items": [{"id": "LC-02", "status": "present|absent|uncertain", "evidence_source": "text|image|image_and_text", "evidence": ["b3", "b4"], "reason": "..."}]}`. 검증: 보낸 항목 ID가 정확히 한 번씩 · 모르는 ID 없음 · `status` 3종 · `evidence_source` 3종 · `evidence`는 현재 섹션 블록 임시 ID만 · `evidence_source`에 `text`가 포함되면 `evidence` 1개 이상, `image`면 비어 있어도 됨 · `reason` 비어 있지 않음.
- **③-1 실패의 결과 형태(잠정안, ①·③ 방침 승계 아님)**: 호출 실패 · 시간 초과 · 검증 실패는 `JudgeResult.status = "failed"`, `content_findings = null`(계약 4.1의 "판정 미완료"), `error`에 사유. 규칙 매칭은 성공했더라도 `matches`는 기록에만 남기고 `content_findings`에는 넣지 않는다 — 부분 결과를 저장하면 "판정 완료"로 읽히기 때문이다. 다른 섹션은 계속 처리한다. 추천 이유: ③-1은 `analyze()` 밖의 독립 단계이고 섹션 단위 미완료 상태가 계약에 이미 있다. 대안: ③처럼 실행 전체 실패 전파.
- **실패 섹션에 대한 ③-1' 동작은 3.4절에서 정한다.** 이 둘을 함께 정하기 전에는 정책 단계를 구현하지 않는다(D7은 "잠정 구현 후 BE 합의"가 아니라 정책 구현의 선결 조건).
- 재시도는 애플리케이션에서 하지 않는다. 시간 제한은 개발용 잠정 60초. 오류 코드 · 워커 재시도 · `NULL` 섹션의 사용자 표시(계약 7.2 "완료되지 않은 상태를 문제 없음으로 표시하지 않는다")는 [BE 합의].
- 부분 실패(한 섹션 안 일부 항목만 응답 이상)는 검증 실패로 섹션 단위 실패다.

- [D9] 검출은 규제 분류를 보지 않고 전체 규제 행으로 매칭하며(2.2절), 필터는 여기서 한다. 이유: finding을 분류와 무관하게 보존하면 분류 변경(예: 잘 모름 → otc) 시 AI · 규칙 재실행 없이 정책만 재계산된다(계약 9장). 다른 분류의 행끼리 서로 억제하는 문제도 생기지 않는다 — 예외 처리는 적용 행 선택 **뒤**에 한다(3.2절 순서). 대안: 검출부터 필터(매칭 수 감소, 재계산 불가).

### 3.2 처리 순서와 매핑 규칙 — `[설명서 §3 · §4 · 잠정]` · `open-questions.md` #7 · #43 · #44 [D2] [D10]

**순서** (모두 결정적, 데이터 `policy_rules.json`으로 관리):

1. **적용 행 선택**: `status ∈ {present, uncertain}`인 finding 중 규제 항목은 `regulatory_class` 필터를 통과한 행만, 현지부적합 항목은 전부.
2. **중복 · 허용 예외 처리** [D2] — **개별 매칭 단위**로 적용한다. 적용 행 사이에서만, 두 `Match`의 원문 구간이 같은 블록에서 겹칠 때 예외 쌍을 검사한다. 추천 = **명시적 예외 쌍 목록**(`policy_rules.json`의 `overrides`, 예: `{"keep": "RG-015", "drop": ["RG-013"]}`, `{"allowed": "RG-035", "drop_overlapping": ["RG-023"]}`)으로만 처리하고 목록에 없는 겹침은 **둘 다 보존**한다. 이유: "문자열이 길다"는 것만으로 의미상 우선권이 생긴다는 근거가 없다. RG-015가 RG-013을 덮는 것은 사전 노트가 밝힌 관계이므로 그 관계를 데이터로 적는 것이 맞고, 겹침 일반 규칙은 근거를 데이터 담당에게 받아야 한다([원문 확인] · 데이터 담당). `allowed` 행은 이 단계에서 예외자로 쓰이고 verdict는 만들지 않는다. **finding의 verdict 유지 조건**: 예외로 억제되는 것은 겹친 그 매칭 하나이며, 같은 finding에 억제되지 않은 매칭이 하나라도 남으면 그 finding은 verdict를 만든다 — 한 섹션에 RG-015 조건형 문장(안의 RG-013 매칭은 억제)과 별도의 RG-013 금지형 문장이 함께 있으면 RG-013 verdict가 남고 `problem_text`는 남은 매칭에서 고른다(3.3절). 모든 매칭이 억제된 finding만 verdict를 만들지 않는다. 억제된 매칭은 결과에서 지우지 않고 `suppressed[]`에 `match_key` · `suppressed_by`로 남긴다. v1 사전에서 실제 겹칠 수 있는 쌍은 RG-015/RG-013(·RG-014)뿐이며 RG-035/RG-023, RG-016/RG-013은 한국어 변형이 겹치지 않는다(규제사전 확인) — 목록의 초기값은 데이터 담당 확인 후 채우며, **확인 전에는 `overrides`를 빈 목록으로 두어 모든 겹침을 보존한다.** 이것은 정보 보존 방침이지 충돌 해결 방침이 아니므로, **미확정 겹침을 최종 제외 계산에 어떻게 넣을지**를 따로 정한다(D2-b, 정책 실측 전 필수):

   | 안 | 미확정 겹침(예: RG-015 조건형 안의 RG-013 금지형)의 처리 | 위험 |
   |---|---|---|
   | **추천 (i) 보수적 계산 + 확인 표시** | 겹친 매칭을 **모두** 계산에 넣는다(금지형이 있으면 제외 권고). 겹친 verdict들에 `conflict_group`(같은 겹침 집합 ID)을 붙여 BE · 사용자 확인 대상임을 식별하게 하고, 실측에서 겹침 빈도를 센다. 근거 확인 후 `overrides`가 채워지면 자동으로 해소된다 | 과잉 제외(조건형 문장이 제외됨). 판정은 되살리기 가능한 권고이므로(설명서 §0) 과소 제외보다 낫다 |
   | (ii) 겹침 집합을 제외 계산에서 빼고 확인 대상으로만 | 겹친 verdict는 만들되 버킷 권고에는 반영하지 않고 확인 신호만 | 과소 제외(금지형 문장이 포함으로 흘러 번역됨). 확인 신호 `SignalCode`가 BE에 있어야 성립 |

   **승인(2026-09-28): (i)를 실험용 잠정안으로.** 예외 쌍을 확인하기 전의 처리 방침이며 올바른 규제 해석을 확정한 것이 아니다. 조건:

   - 충돌로 생긴 제외는 **확정된 규제 위반이 아니라 "규칙 충돌에 따른 잠정 제외"**로 구분한다. 해당 verdict에 `conflict_group`이 있으면 그 verdict는 잠정이며, `reason`(사전 사유 스냅샷)을 바꾸지 않고 별도 필드로 구분한다.
   - `conflict_group`에는 집합 ID뿐 아니라 **관련 사전 ID 목록과 각 매칭 근거(`match_key` · 블록 · 원문 구간)**를 보존하고, **사용자 확인 화면까지 전달**한다. 디버그 기록에만 남기면 부족하다. 저장 형식은 [BE 합의]이나 전달 자체는 조건이다.
   - 겹치지 않은 독립적인 금지형 매칭은 정상적으로 제외 계산에 반영한다(같은 finding 안에서도 겹친 매칭만 충돌 표시).
   - 평가에서는 충돌로 인한 제외를 **별도로 집계**하고 판정 성공으로 바로 세지 않는다(7절).

   대안: 긴 구간 우선 일반 규칙(근거 필요).
3. **매핑**: 아래 표.
4. **집계**: 버킷 권고와 대응 기록.

| finding | 사전 판정값 | 대체 표현 | `section_verdict` 후보 | 버킷 권고 |
|---|---|---|---|---|
| RG present | `allowed` | — | 만들지 않음(2번의 예외자로만 사용) | 영향 없음 |
| RG present | `conditional` | 규정 표기 | `verdict_status=conditional` | 포함 |
| RG present | `rewritable` | 완충 표현(필수) | `verdict_status`: [D11] | 포함 |
| RG present | `regulated` | 있음 | `verdict_status=regulated` + `alternative_expression` | 포함 |
| RG present | `regulated` | 없음 | `verdict_status=regulated`, 대체 표현 없음 | **제외** |
| LC present | `irrelevant` | — | `verdict_status=irrelevant` | **제외** |
| LC present | `needs_fix` | — | `verdict_status=needs_fix` | **제외** |
| LC absent | — | — | 없음 | 영향 없음 |
| LC / RG `uncertain` | — | — | [D12] | [D12] |

- `verdict_type`(배지 6종) · `exclusion_reason`(사유 코드)은 **③-1'이 내지 않는다.** 둘 다 `verdict_status` + 대체 표현 유무에서 BE가 한 곳에서 파생한다(설명서 F-SEC-04, `docs/openapi.yaml` "verdictType은 파생 · 읽기 전용"). 따라서 `auto_local_needs_check` 신설 여부는 BE 몫이며 AI 출력에 사유 코드가 없다. [BE 합의]
- `rewritable` [D11]: 두 자료의 선택지 — **엑셀 읽는법**은 "로더가 `regulated`로 바꿔 적재", **사용설명서 §4**는 "`regulated`로 바꾸거나 스키마 CHECK에 값을 추가". 추천 = ③-1' 출력에서 `regulated`로 정규화하고 원값을 `source_verdict_status: "rewritable"`로 함께 낸다. 이유: API `VerdictStatus` enum에 `rewritable`이 없고, 두 자료가 공통으로 제시하는 선택지가 변환이며, 원값을 남기면 BE가 나중에 보존안(CHECK · enum 확장)을 택해도 정보가 남는다. [BE 합의] 전에는 코드에서 정하지 않는다.
- `uncertain` [D12]: 추천 = **제외 버킷 권고 + 해당 사전 판정값 그대로 + verdict에 판정 확신 상태를 별도 필드로 보존**. `reason`은 어느 경우에도 사전 사유의 스냅샷(3.3절)이며 "확인 필요" 같은 문구를 덧붙이지 않는다 — 불확실한 판정이 확정된 부적합처럼 전달되지 않게 두 의미를 분리한다. 구분은 두 곳에 남는다: (1) 저장되는 `content_findings`의 `finding.status=uncertain`(계약 4.1, AI의 판정 사유는 `finding.reason`) (2) `PolicyResult` verdict의 `finding_status`(`present` · `uncertain`, 계약 밖 키 — 저장 여부와 사용자 확인 신호(`SignalCode`)로의 파생은 [BE 합의]). BE가 verdict 행만 읽고 finding을 읽지 않는 화면이 있으면 (2)의 저장이 필요하다. 이유: 판정은 되살리기 가능한 권고이고(설명서 §0), 포함으로 흘리면 미국 부적합 요소가 그대로 번역된다. 대안 = 포함 권고 + 신호만. "둘 다 애매하면 needs_fix" 규칙의 확대가 아니라 별도 결정이다.
- **섹션 집계** #44: 버킷 권고 = 제외형 verdict가 하나라도 있으면 `exclude`, 아니면 `include`. **단 3.4절의 미완료 조건이 먼저다.** verdict 후보는 전부 보존(섹션당 여러 행). 정렬은 API 정렬 불변식(regulated → policy → irrelevant)이 있으므로 BE가 한다. AI는 심각도 순(금지형 regulated > irrelevant > needs_fix > conditional > 교체형/완충형)을 기록에만 남긴다.
- 하나의 finding이 verdict 하나를 만든다. finding↔verdict 대응(억제 포함)은 출력에 포함해 `audit_log.detail`로 간다. [계약 4.2]
- `dictionary_id`: 사전 행의 DB id는 워커가 변환한다. AI 출력은 사전 항목 ID(`RG-003`)와 사전 버전을 준다. [`db-map.md` 2절]

### 3.3 출력 — `PolicyResult`

```json
{
  "schema_version": "1",
  "section_key": "sec_12_03",
  "status": "ok",
  "bucket_recommendation": "exclude",
  "verdicts": [
    {"verdict_key": "v_01", "finding_key": "f_02", "dictionary_ref": "RG-003",
     "verdict_status": "regulated", "source_verdict_status": "regulated", "finding_status": "present",
     "problem_text": "워터프루프", "alternative_expression": null,
     "basis_article": "§ M020.50(g)", "evidence_url": "https://…", "reason": "…(사전 reason 스냅샷)"}
  ],
  "suppressed": [{"match_key": "m_07", "finding_key": "f_05", "suppressed_by": "m_03"}],
  "applied": {"regulatory_class": "combination", "applied_classes": ["otc", "common"],
              "dict_coverage": "partial_class_combination",
              "dictionary_version": {"regulation": "…", "local": "…"}, "rules_version": "…"}
}
```

- `problem_text`: 규제 = **억제되지 않은** `matches` 중 첫 매칭(블록 순서 · 위치 순)의 `matched_text`(원문 구간, 정규화 전 텍스트를 `raw_span`으로 잘라낸 것). 나머지는 대응 기록에 남긴다. 억제되지 않은 매칭이 없는 규칙 finding은 verdict를 만들지 않고, `matches`가 아예 없는 규칙 finding은 입력 오류다. 현지부적합 = `evidence_block_ids`가 가리키는 **현재 섹션 블록**의 `source_ko`를 블록 순서대로 이은 것(길이 상한 `policy.problem_text_max_chars`, 넘으면 자르고 `…` 표시). 블록 텍스트는 ③-1'의 정상 입력이다(3.5절). `evidence_source=image`라 근거 블록이 비어 있으면 `problem_text=null`(`section_verdict.problem_text`는 NULL 허용, 마이그레이션 0001)이고, AI의 판정 서술은 저장되는 `finding.reason`에 있다(verdict `reason`에 넣지 않는다) — 이 경우의 화면 표시는 [BE 합의].
- `reason` · `basis_article` · `evidence_url`은 **판정 시점 사전 값의 스냅샷**(설명서 §4 근거 표시, F-SEC-05)이며 AI 서술 · 확신 표시 · 처리 메모를 섞지 않는다. AI 서술은 `finding.reason`, 확신 상태는 `finding_status`([D12]). [설명서 §4 · 잠정]
- `applied`는 `audit_log.detail`(적용 정책 식별자 · 버전 · 입력 finding 스냅샷 · verdict 목록 · 대응)과 `event_log.payload`(정책 버전 · 캐시 키)의 재료다. [계약 4.2, 9장]
- 저장 컬럼과의 대응은 `db-map.md` 3.4 · 3.7. 계약 밖 키(`source_verdict_status` · `suppressed` · `applied` · `bucket_recommendation` · `status`)는 저장 대상이 아니라 워커 · 감사 기록용임을 명시한다. [BE 합의]

### 3.4 미완료 · 실패 입력에 대한 동작 [D7] — 정책 구현의 선결 조건

| `JudgeResult.status` | `content_findings` | ③-1' 동작 | `PolicyResult` |
|---|---|---|---|
| `ok` | 목록(빈 목록 포함) | 3.2절 정상 처리 | `status=ok`, 권고 · verdict |
| `skipped`(호출 대상 아님, 안 A) | `{findings: [...]}` 규칙 finding만 | 정상 처리(검사 완료로 본다 — [D3-3] 승인 2번 범위 안에서만) | `status=ok` |
| `failed` | `null` | **정상 처리하지 않는다.** verdict를 만들지 않고 권고도 내지 않는다 | `status=incomplete`, `bucket_recommendation=null`, `verdicts=[]`, `error` 전달 |
| 없음(③-1 미실행) | 없음 | 실행 거부(입력 오류) | — |
| `ok`이나 `regulatory_class` 누락(D9-c) | 목록 | **정상 처리하지 않는다.** 재시도 불가 입력 오류 | `status=input_error`, `bucket_recommendation=null`, `verdicts=[]`, `error` |

- **규칙**: 미완료 입력에서는 어떤 경우에도 `include` 권고를 만들지 않는다. "제외형 verdict가 없으면 include"는 `status=ok`에서만 적용한다.
- **규제 검출은 성공하고 AI만 실패한 경우**: v1은 섹션 전체를 `failed`로 다루고 규칙 결과로 부분 verdict를 만들지 않는다. 이유: `content_findings`에 부분 결과를 저장하면 계약상 "판정 완료"로 읽히고, 부분 verdict(예: 금지형 → 제외)만 보이면 사용자가 나머지 항목도 검사됐다고 오해한다. 규칙 매칭 결과는 `judge_debug`에 남아 재시도 시 재사용할 수 있다. 대안: `status=partial`로 규칙 verdict만 생성하고 권고는 `null` — 저장 형식에 부분 상태가 필요하므로 [BE 합의] 후에만.
- 워커는 `incomplete` 섹션을 재시도 대상으로 다루고, 사용자 화면에서 "문제 없음"으로 보이지 않게 해야 한다(계약 7.2). 표시 방식은 [BE 합의].

### 3.5 ③-1'의 정상 입력에 블록 텍스트를 포함 [D13]

- `policy.run(judge_result, blocks, ctx, cfg)` — **현재 섹션의 블록 목록(`TextBlock[]`, ③ 출력)을 정상 입력으로 받는다.** 필요한 이유: 현지부적합 `problem_text`(3.3절)와 `evidence_block_ids`의 존재 검증. 추천 이유: 블록 텍스트는 이미 계약 데이터(`text_block.source_ko`)로 저장되므로, 나중에 저장된 finding으로 정책만 재계산할 때(계약 9장) 워커가 DB에서 같은 블록을 다시 넘길 수 있다 — 결과에 텍스트를 중복 보존할 필요가 없다. 대안: `JudgeResult`에 항목별 근거 텍스트를 보존(`evidence_texts`) — 저장량이 늘고 블록 수정 시 불일치가 생긴다.
- 정책 재계산에 필요한 저장 데이터는 `content_findings` + `matches` + 블록 + 사전 + `regulatory_class`다. [D13]의 저장 · 입력 범위를 근거 종류별로 나누면:

| 근거 종류 | 재계산에 필요한 것 | 저장 위치(추천) | 상태 |
|---|---|---|---|
| 규칙 매칭(RG · LC 패턴) | `matches`(패턴 · 블록 · 원문 구간 · 원문 텍스트) | finding에 `matches` 키 추가(계약 4.1 확장). 대안 `audit_log.detail` 스냅샷 | [BE 합의] |
| LC 텍스트 근거 | `evidence_block_ids` + 그 블록의 `source_ko` | ID는 finding에 있음(계약). 텍스트는 저장하지 않고 `text_block`에서 워커가 넘김. finding 시점과 현재 블록 `revision`이 다르면 재계산이 아니라 ③-1 재실행 대상 | [BE 합의: revision 불일치 판단] |
| LC 이미지 전용 근거(`evidence_source=image`) | 없음 — 근거 텍스트가 없다 | `problem_text=null`, AI 서술은 `finding.reason`(저장됨). 화면에서 근거 이미지 영역을 보여 주려면 좌표가 필요하나 v1 AI 출력에는 없다(계약 4.1에도 없음) | [BE 합의: 표시 방식] |

- `evidence_block_ids`가 현재 섹션 블록에 없으면 입력 오류다(재계산 시 블록이 삭제 · 재분석된 경우 포함 — 이때는 ③-1 재실행 대상이며, 판단은 워커 [BE 합의]).

## 6. 프롬프트 요지 (`pipeline/prompts/judge_context.md`, 초안은 구현 시)

- 역할: 한국 화장품 상세페이지 섹션이 미국 판매에서 그대로 쓸 수 없는 "한국 전용 요소"를 담고 있는지, 주어진 항목별로 판정.
- 항목마다 `제외하는 맥락` · `제외하지 않는 맥락`을 그대로 제시하고, 셋 중 하나로 답하게 한다. 최종 제외 여부 · 되살리기 · 번역은 묻지 않는다.
- 근거는 현재 섹션 블록 ID만. 앞뒤 섹션은 참고. **근거 출처(텍스트 / 이미지 / 둘 다)를 항목마다 보고**하게 한다.
- 사전 밖 표현 · 새 맥락(#4-3): v1은 묻지 않는다(항목 외 자유 서술 금지). 보강 대상 기록은 실측 육안 확인에서 사람이 한다.

## 7. 실측 · 평가 계획 (구현 후)

- 입력: `blocks-input-v1` 섹션 100개(정답 아님, #57). `regulatory_class`는 실측용으로 원본별로 사람이 지정(대부분 cosmetic, 선크림 원본은 otc).
- 1회차는 [D3-2] 안 B(`call_scope=all`, LC 8개)로 돌린다. **관찰값(집계만, 결론 아님)**: 항목별 원시 매칭 수(매칭 방식 B, 참고로 A' 후보 수도 계산) · 예외 쌍 발동 수 · 매칭 없는 섹션에서 LLM이 `present`를 낸 건 · 매칭 있는 섹션에서 `absent`가 나온 건 · status 분포 · `evidence_source` 분포 · 검증 실패 · 비용 · 지연 · 버킷 권고 분포 · `incomplete` · `input_error` 수 · **충돌(`conflict_group`)로 인한 제외 권고 수(별도 집계, 판정 성공으로 세지 않음)** · `dict_coverage` 분포.
- **원인 분류(육안 검수)**: "매칭 없이 `present`" 건을 실제 부적합 여부와 원인(OCR 미검출 / 사전 패턴 부족 / 블록 분리 / LLM 오탐)으로 나누고, 매칭 방식 B의 미탐(OCR 오류 · 블록 분리 · 미등록 표현)을 같은 검수에서 센다. [D3-3] · [D1] 판단은 이 분류 결과로 하며, 관찰값만으로 하지 않는다.
- 육안 확인: 매칭 → status → 버킷을 섹션별 오버레이(`inspect judge`)로 보고, OCR · 병합 오류로 인한 것과 판정 오류를 구분해 센다(#57). 판정 명세는 ③ v2 형식으로 별도 작성.
- `variant_expressions.ko` 초안(#55)의 미탐은 데이터 담당에게 목록으로 돌려준다.
- 사전 밖 표현 관찰(#4-3)은 보강 후보 목록으로만 기록한다.

**위치** — 추천:

- 폴더 `pipeline/data/dict/`는 **구조상 승인됨**(사용자, 2026-09-28). 실제 데이터의 git 포함은 **미룸** — 나중에 포함하기로 해도 로더 구조는 바뀌지 않는다(경로 설정만 바뀐다). `dev.md` 1절 · 5절 반영은 구현 착수 시.
- 이유: 단계가 DB 없이 파일로 돌아야 하고(`dev.md` 4절), `docs/ai`에는 값을 두지 않는다(README 4.4). 내용이 공개 조문 · 실측 통계라 비밀은 아니지만 공유 범위가 확인되기 전까지 저장소에 넣지 않는다.

**형식** — JSON(UTF-8, pydantic 검증):

- 로더가 읽는 열만 옮긴다. 규제: `규제사전` 탭의 남색 열 + `근거` 탭의 `is_primary=Y` 행. 현지부적합: `01_현지부적합사전` 전체 + `02_판정규칙`의 "넓게 잡는 패턴 · 패턴에 넣지 않은 단어"는 README에만. 시트 전용 열(`confidence` · `source` · `version` · `note` · `판단 근거`)은 **제외** — 담당자 실명이 노트에 있고 판정 근거가 아니다. 단 `confidence`가 `high`인 행만 들어왔음을 README에 적는다.
- 다중값(`; `)은 배열로. 열 이름은 원본 그대로 두고(`variant_expressions.ko`), DB 컬럼명으로 바꾸지 않는다(대응은 `db-map.md` 3.7의 후보이며 BE 확인 전).
- ③-1 로더는 패턴 · 항목명 · 맥락 2열만 노출하고, ③-1' 로더는 정책 필드를 노출한다(같은 파일, 다른 뷰). ③-1 코드가 정책 필드에 접근하지 않음을 테스트로 고정한다.
- 파일 머리 `meta`: 원본 파일명 · 탭 · 원본 SHA-256 · 추출일 · 행 수 · `dictionary_version`. 버전 문자열은 원본이 밝힌 버전 + 대조일(`regulation@v9/2026-09-22`, `local@v5?/2026-09-22` — v5/v7 불일치(#50) 확인 전까지 `?` 표시).
- `policy_rules.json`: 3.2절 매핑표(`verdict_status` × 대체 표현 유무 → `bucket` · 출력 `verdict_status`) + 예외 쌍 목록(`overrides`) + `rules_version`. 매핑이 계약에 채택되기 전까지 "설명서 §3 · §4 기반 잠정"을 파일 안에 명시. 예외 쌍의 초기값은 데이터 담당 확인 후.

**버전 관리**:

- 정규화 JSON은 git 밖이므로 이력은 **데이터 묶음 보관**으로 대신한다: `build_dict.py`가 만든 JSON + `meta`(원본 파일명 · 원본 SHA-256 · `dictionary_version`) + `SHA256SUMS`를 한 폴더로 묶어 `merge-input-v1`과 같은 방식(`dev.md` 5절 고정 입력본 규칙)으로 별도 보관한다. 같은 묶음을 다른 PC에서 배치하면 `build_dict.py --verify`로 해시를 대조한다.
- 재현성은 **실행마다 `dictionary_version` + 파일 SHA-256 + `match_rules_version` + `rules_version`을 실행 기록 · `event_log.payload`에 남기는 것**으로 확보한다. 어떤 실행이 어떤 사전 묶음을 썼는지 해시로 추적한다. 캐시 무효화 판단(#49)은 1절 재실행 조건표를 따른다 — 어떤 열이 바뀌었는지는 `build_dict.py`가 이전 파일과 비교해 요약(패턴 / 맥락 / 정책 필드)을 출력한다.
- 운영 시 DB에서 읽을지 파일을 쓸지는 [BE 합의](#3-5). v1 코드는 "사전 핸들" 인터페이스를 두어 파일 로더와 DB 로더를 바꿔 끼울 수 있게 한다.
