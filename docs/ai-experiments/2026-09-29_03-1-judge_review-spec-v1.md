# ③-1 · ③-1' 육안 검수 명세 v1 — 1차 실측용 초안(2026-09-29, 실측 전 고정)

> 성격: 실측 1회(`blocks-input-v1` 100섹션, `call_scope=all`)의 결과를 사람이 검수할 때 쓰는 명세. 판정 품질의 정답 기준이 아니라 **원인 분류와 집계 규칙**이다. 정답 라벨이 없으므로 정확도 · 재현율을 내지 않고, 관찰값과 원인별 건수를 낸다. ③ 판정 명세 v2(`2026-09-28_03-merge_review-spec-v2.md`)와 같은 취급이며 검수 중 해석 차이가 생기면 보정 후 v2로 올린다.
> 입력: 섹션별 `judge/<key>.json`(`JudgeResult`) · `policy/<key>.json`(`PolicyResult`) · `judge_debug/<key>.json` · 오버레이 PNG(`inspect --judge`). 분류는 `2026-09-29_03-1-judge_class-assumption.json`의 **가정**이다.

## 1. 검수 단위

| 단위 | 대상 | 기록 |
|---|---|---|
| S 섹션 | 100섹션 각각 | 실행 상태(`ok` · `skipped` · `failed`), 정책 상태(`ok` · `incomplete` · `input_error`), 권고(`include` · `exclude` · 없음) |
| F 항목 판정 | 섹션 × 현지부적합 LC 8개 = 최대 800건(`call_scope=all`이라 매칭 없는 항목도 판정됨) | LLM `status`(P/A/U) · `evidence_source` · 근거 블록 · 사람 판단 · 불일치 원인 |
| R 규칙 매칭 | 규제 RG 매칭이 있는 finding | 매칭 원문이 그 표현에 해당하는지(사람 판단) · 규제 분류 가정과의 관계 |
| V verdict · 권고 | 정책 결과 | 권고 동의 여부 · 불일치 원인 · 충돌(`conflict_group`) · 억제 |

## 2. 사람 판단 값

- F: **해당**(exclude_when에 해당) · **비해당**(keep_when이거나 관련 내용 없음) · **판단불가**(이미지 · 텍스트로 사람도 정할 수 없음). 사람 판단은 원본 섹션 이미지를 보고 하며, LLM 답을 먼저 보지 않는다(오버레이의 상태 표시는 확인 뒤에 대조).
- 혼합 섹션(살려야 할 내용이 섞임)은 프롬프트 규칙대로 해당 항목이 있으면 **해당**이다. 섞임 여부는 메모로만 남긴다.
- R: 매칭 원문이 사전 항목의 표현인지 **예 · 아니오 · 불명**. `SPF` 단독 매칭(RG-021)처럼 조건 확인 항목은 "예"로 두고 메모에 "조건형"이라 적는다.
- V: 권고에 **동의 · 비동의 · 보류**(분류 가정이 틀리면 결과가 바뀌는 경우는 보류로 두고 원인 5).

## 3. 불일치 원인 분류 — F · R · V 공통, 하나만 고른다

| 코드 | 원인 | 예 |
|---|---|---|
| 1 | OCR 누락 · 오인식 | 이미지에는 있는 가격이 블록 텍스트에 없거나 `원`이 `윈`으로 읽힘 |
| 2 | 사전 패턴 · 맥락 정의 부족 | `₩` · `KRW` 표기가 패턴에 없음, 맥락 2열이 이 경우를 다루지 않음 |
| 3 | 블록 · 섹션 분리로 인한 문맥 손실 | 가격과 조건이 다른 섹션에 갈라져 있음, 블록이 조각남 |
| 4 | LLM 오탐 · 미탐 · 불확실 판정 | 텍스트 · 이미지에 근거가 있는데 반대로 답함, 판단 가능한데 `uncertain` |
| 5 | 분류 가정 · 정책 매핑 문제 | 가정한 `regulatory_class`가 틀려 규제 행이 잘못 적용됨, 매핑표(설명서 기반 잠정)의 결과가 어색함 |
| 6 | 원인 미확정 | 위 어느 것으로도 정할 수 없음 — 메모 필수 |

- 매칭 실패(패턴이 걸리지 않음)는 그 자체로 최종 미탐이 아니다. `call_scope=all`에서는 패턴 없이도 LLM이 판정하므로, 미탐은 F 단위에서 LLM 답과 사람 판단을 대조해 센다.
- 하나의 불일치에 원인이 둘이면 더 앞선 단계(작은 번호)를 고르고 메모에 나머지를 적는다.

## 4. 별도 집계 — 원인 분류에 넣지 않는다

| 집계 | 정의 |
|---|---|
| 충돌에 따른 잠정 제외 | `PolicyResult.conflicts`가 있고 해당 verdict의 `conflict_group`이 붙은 섹션 · verdict 수. 판정 성공 · 실패로 세지 않는다 |
| 호출 · 응답 검증 실패 | `JudgeResult.status=failed`(`judge_debug`의 `call_failed` · `validation_failed`)와 그에 따른 정책 `incomplete`. 시간 초과 · 검증 실패 사유별로 센다 |
| 억제된 매칭 | `PolicyResult.suppressed`(현재 `overrides`가 비어 있어 0이어야 한다 — 0이 아니면 입력 오류) |
| 검사 범위 | `dict_coverage` 분포(가정한 분류 기준) · `checked.items` |

## 5. 관찰값 — 검수와 별개로 실행 기록에서 집계

status 분포(P/A/U, 항목별) · `evidence_source` 분포 · 매칭 없는 항목에서 `present`가 나온 건(원인 분류 전에는 관찰값) · 매칭 있는 항목에서 `absent`가 나온 건 · 권고 분포 · 토큰 사용량(입력 · 출력 · 사고) · 지연(중앙값 · 90% · 최대) · `failed` · `incomplete` 수.

## 6. 절차

1. 실측 출력에서 섹션별 오버레이 PNG를 만든다(`inspect --judge … --policy …`).
2. 검수자는 원본 섹션 이미지로 F · R을 먼저 판단하고 판정표에 적은 뒤 LLM · 정책 결과와 대조해 불일치 원인을 고른다.
3. V는 가정한 분류를 전제로 판단하고, 분류가 틀렸을 가능성이 결과를 바꾸면 보류(원인 5).
4. 판정표는 `runs/<실측 폴더>/review/`(로컬)에 두고, 기록 파일에는 원인별 · 항목별 건수와 별도 집계만 옮긴다.
5. 검수 중 명세 해석이 갈리면 그 사례를 모아 보정하고 v2로 올린다. 이번 실측의 판단(큰 결함 여부 · D3-3 · D1)은 보정된 명세로 집계한 뒤에 한다.
