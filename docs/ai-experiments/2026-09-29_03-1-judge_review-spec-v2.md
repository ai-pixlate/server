# ③-1 · ③-1' 육안 검수 명세 v2 — v1의 최소 보정(2026-09-29, 사용자 지시)

> v1(`2026-09-29_03-1-judge_review-spec-v1.md`)에서 1차 검수 중 해석이 갈린 사례를 바로잡기 위한 **최소 보정**이다. F(항목 판정) · V(권고) · 원인 6종 · 별도 집계는 v1 그대로이며 여기 적힌 것만 바뀐다. 전체 API 재실행은 하지 않고, 해석이 갈린 사례만 v2 기준으로 다시 기록한다(`…_judge_run-v1.md` 5.1절).
> 검수자가 에이전트일 때는 결과를 "에이전트 1차 검수"라고 부른다. "사람 판단"은 사용자가 원본 이미지를 직접 본 경우에만 쓴다.

## 1. R 규제 매칭 — 기록 단위는 **매칭**이다(finding이 아니다)

한 finding에 매칭이 여럿이면 매칭마다 한 줄. 열 세 개를 **분리해** 적는다.

| 열 | 값 | 뜻 |
|---|---|---|
| `string_match` | 예 / 아니오 | 매칭 원문이 사전 변형 목록의 문자열과 같은가(정규화 후). 검출이 만든 매칭은 원칙적으로 예. 아니오면 검출 결함 |
| `boundary` | 독립 / 내부 | 매칭 구간이 독립된 어절(앞뒤가 공백 · 구두점 · 줄 끝 · `#`)인가, 다른 어절 **안의 부분 문자열**(예: `브라이트닝` 안의 `라이트닝`)인가. **검색 경계 문제**를 가르는 열이며 데이터 담당의 매칭 방식(어절 시작 일치 · 조사 허용 — 확인 대기)과 현재 구현(공백 제거 부분 문자열)의 차이가 드러나는 곳 |
| `context_valid` | 예 / 아니오 / 불명 | 그 표현이 실제로 사전 항목이 뜻하는 **규제 주장 문맥**인가(커버 표현 · 브랜드명 · 부정문 · 톤업 같은 물리 보정은 아니오 또는 불명). **표현의 문맥 문제**를 가르는 열 |

- 조건형(RG-021 `SPF` 단독)은 `context_valid=예`로 두고 메모에 "조건형".
- 규제 항목은 LLM이 판정하지 않으므로 현지부적합의 `keep_when` 보정이 여기에는 작동하지 않는다. `boundary=내부`나 `context_valid=아니오`가 포함 배지(교체형 · 완충형 · 조건형)에 남으면 그대로 배지가 된다 — 검수에서 이 두 열을 별도 집계한다.
- "매칭 없음"은 v1과 같이 미탐으로 세지 않는다. 관찰값으로만 기록하고 데이터 담당 자료로 돌린다.

## 2. LC 항목 경계(LC-01 기획 구성 · LC-03 증정품 / LC-05 이벤트)

해석이 갈린 사례는 **사례로만 기록**한다(`notes`). 사전의 `exclude_when` · `keep_when`을 검수자가 넓히거나 좁혀 새 정책을 만들지 않으며, 경계 조정은 데이터 담당 · 사용자 합의 뒤 사전 맥락 2열의 변경으로 한다. 두 항목에 모두 해당하면 둘 다 "해당"으로 적고 메모에 중복을 적는다.

## 3. 그 밖의 표현 규칙

- 집계 표에는 "에이전트 1차 검수와 N/N 일치"라고 쓴다. 각 에이전트가 서로 다른 섹션을 나눠 봤으면 교차 검증이 아니라는 점을 함께 적는다.
- 비용은 실측 토큰 사용량만 적고, 단가 기반 금액은 "미검증 추정"으로 표기한다. 총토큰 배수는 입력 · 출력 · 사고 토큰 구성 차이를 반영하지 못하므로 운영 선택의 확정 근거로 쓰지 않는다.
