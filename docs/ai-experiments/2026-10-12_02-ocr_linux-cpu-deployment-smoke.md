# 2026-10-12 ② OCR — Linux CPU 배포 스모크와 메모리 관찰

> 기록일: 2026-10-12. 시험 일시·반복 횟수의 상세 기록은 미확보.
> 기준 코드: develop `f8a1e67b2e531741590c51ff14c9bb75c81ce114`.
> 출처: 사용자가 전달한 배포 담당(Claude)의 시험 보고. 기록 작성자는 이 OCR 시험을 재실행하지 않았으며, 기준 커밋의 코드만 별도로 대조했다.
> 실험 기록이며 운영 설정 채택, OCR 품질 승인 또는 배포 완료를 뜻하지 않는다. 원본 이미지·결과 JSON·로그·이미지 digest·실험 스크립트는 이 기록에 첨부하지 않았다.

## 1. 질문

- 기준 커밋의 OCR 이미지를 Linux CPU에서 실행하면 정상 OCR 결과를 얻는가?
- oneDNN 비활성화가 관찰된 실행 오류를 회피하는가?
- 모델 로드를 포함한 단일 표본의 메모리 사용량이 현재 EC2에서 실행 가능한 수준인가?
- 관련 정본: `docs/ai/pipeline.md` ② 및 구현 유의 사항, `docs/ai/contract.md` 2.5의 영역 score, `docs/ai/dev.md` 6절. 긴 섹션 임시 분할은 `docs/ai/open-questions.md` #31·#32의 별도 후속이다.

## 2. 표본

- 합성 섹션 1개, 폭 600 × 높이 560px.
- 표본 파일·해시·문구·기대 정답: 없음(미제공).
- 실제 상품 이미지의 대표 표본, 긴 섹션 또는 다수 섹션 시험은 아니다.
- 인식 영역 수와 score 존재를 확인했으며 인식 정확도는 평가하지 않았다.

## 3. 조건

- 배포 담당은 로컬 PC(8코어, Docker 메모리 4GB)에서 기준 커밋의 앱 이미지와 OCR 이미지를 빌드했다고 보고했다. EC2에서 OCR을 실행한 결과가 아니다.
- 기준 Dockerfile은 Python 3.12 계열이다. 실제 Python 패치 버전 및 이미지 digest는 미제공이다.
- 기준 `pipeline/requirements-ocr.txt`의 고정 버전은 `paddlepaddle==3.3.1`, `paddleocr==3.7.0`, `paddlex==3.7.2`이다. 설치된 패키지 전체 목록은 미확보이며, OCR 이미지의 `pip check` 통과만 보고받았다.
- 기준 설정: 검출 `PP-OCRv5_server_det`, 인식 `korean_PP-OCRv5_mobile_rec`, 전처리 `none`.
- 비교 A: 기준 커밋의 정상 OCR 경로.
- 비교 B: 같은 표본·실행에서 실험 컨테이너 안의 판정만 변경해 oneDNN을 비활성화. 저장소 애플리케이션 코드에 반영된 수정이 아니며, 운영 적용 대상이 아니다.
- 정확한 CLI 인자, 우회 스크립트, 메모리 측정 도구·집계 방식(RSS 또는 컨테이너 기준 등), 캐시 상태, 반복 횟수: 없음(미제공). 이 요약만으로 동일 실험을 완전히 재현했다고 주장하지 않는다.

## 4. 결과

판정 기준: 프로세스 종료 코드 0, 인식 영역 1개 이상, 각 영역의 score 존재를 모두 만족하면 단일 표본 실행 성공이다. 문구 인식 정확도나 전체 서비스 성공은 별도다.

### 4.1 배포 담당이 보고한 실측

- 기본 실행: `ConvertPirAttribute2RuntimeAttribute` 오류, 종료 코드 **2**. 실행 실패.
- oneDNN 비활성화 비교: 종료 코드 **0**, 인식 영역 **5개**, 모든 영역에 **score 존재**. 해당 표본 실행 성공.
- 합성 섹션 실행의 최대 메모리: **2,104MiB**, 모델 로드 포함으로 보고됨. 비교 A/B 중 측정 대상의 상세 구분과 측정 원본은 미제공이다.
- 당시 대상 EC2: 전체 약 **909MiB**, 가용 약 **487MiB**, 스왑 4GB로 보고됨. 이는 관찰 시점의 자원 상태이며 지속 보장값이 아니다.
- 실제 긴 섹션 실행, 동시 실행, 운영 EC2 추론, 전체 잡·큐 통합 검증: 미실시.

### 4.2 기준 커밋 코드 대조

- `pipeline/stages/ocr.py`의 `PaddleOcrEngine`은 `sys.platform == "win32" and device == "cpu"`일 때만 `enable_mkldnn=False`를 전달한다. Linux CPU에는 이 명시적 비활성화가 적용되지 않는다.
- 인식 결과의 `rec_scores`는 각 `OcrRegion.score`에 저장된다.
- `pipeline/config/default.toml`에는 `split_threshold_px=4000`, `tile_px=2000`, `tile_overlap_px=300`이 있다.
- 그러나 `ocr.run()`은 섹션 높이가 4,000px를 초과하면 `NotImplementedError`로 중단한다. **2,000px 타일 OCR은 현재 구현된 동작이 아니다.** 타일 설정이 있다는 이유로 메모리 측정이나 지원 범위를 타일 단위로 해석하면 안 된다.

## 5. 판단

**보류 — 기준 커밋의 Linux CPU OCR 배포를 진행하지 않는다.**

oneDNN 비활성화 비교는 수정 방향의 근거지만, 정확한 원인과 적용 범위를 확정한 결과는 아니다. 실험 컨테이너의 우회를 그대로 배포하지 않고 AI 담당의 별도 코드 수정·검증을 요청한다. 단일 표본의 메모리 수치는 운영 요구량을 확정하기에 부족하며, 현재 EC2 메모리보다 큰 사용량이 보고됐다. 스왑이 있다는 사실만으로 정상 처리 시간·안정성을 보장할 수 없다.

### AI 담당 수정 요청

1. 동일 이미지·입력으로 Linux CPU 오류를 재현하고 oneDNN 설정 또는 의존성 호환성 문제를 해결한다. 가능하면 배포 담당에게 표본 해시·실행 명령·버전 목록·정제된 오류·측정 방법을 받아 재현 조건을 보완한다.
2. oneDNN 비활성화를 사용한다면 적용 범위와 근거를 명시한다. 기존 Windows CPU 동작을 유지하고, 새 환경 변수나 런타임 monkey patch에 의존하지 않는 정상 OCR 경로로 수정한다.
3. 모델·인식 임계값·출력 계약을 유지한다. 의존성 변경이 필요하면 변경 이유와 영향을 함께 검토한다.
4. 수정 이미지에서 동일 표본의 종료 코드 0, 인식 영역 존재, score 보존을 확인하고 기존 OCR 회귀 테스트와 이번 설정 분기의 검증을 수행한다.
5. 실제 입력 폭을 가진 지원 범위 내 긴 섹션에서 모델 로드 포함 최대 메모리·실행 시간을 측정한다. 4,000px 초과 타일 분할은 이번 오류 수정에 임의로 포함하지 않고 별도 후속으로 유지한다.
6. 수정 커밋·검증 결과·남은 제한을 배포 담당에게 인계한다. develop 반영 후 새 배포 작업에서 SHA를 다시 고정하고 이미지를 다시 빌드한다. 기준 커밋으로 만든 기존 이미지를 수정된 최종 배포 이미지로 취급하지 않는다.

AWS 설정·실행 자원 결정·DB 마이그레이션·GPU 배포·스타일 렌더 연결은 이 OCR 수정 요청의 범위 밖이다.
