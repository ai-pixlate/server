# ③ OCR 후처리 — 같은 후보 영역 안 교차 블록의 LLM 병합 점검(2026-10-23)

## 1. 질문

`merge.xycut`을 켜면 LLM 묶음 안의 모든 줄을 (가로줄 순번, x, `region_key`)로 다시 정렬한다(`pipeline.md` 7.2절). 같은 후보 영역 안에서 gutter가 두 칸을 갈라 놓은 경우 LLM이 두 칸을 합치면 줄이 번갈아 섞일 수 있다(`open-questions.md` #86). 이 위험이 실제 입력에서 얼마나 생기는지, 그리고 다른 원인(높이비로 갈린 같은 가로줄, 한 블록이 다른 블록의 줄 사이에 끼인 경우)의 교차가 있는지 본다.

## 2. 표본

`blocks-input-v1`(③ 이후 개발용 고정 입력본, `status.md` 2절) 32원본 · 100섹션. OCR 결과와, 후처리를 끈 상태의 ③ 최종 블록(`llm_assist` v1 실제 출력 1회분)을 썼다. 이 블록은 정답 데이터가 아니다(`open-questions.md` #57).

## 3. 조건

- 코드: `feature/ocr-postprocessing`(develop `7ac9be9` 기준 + 2단계 구현). 기본 config에 `merge.xycut = true`만 바꿨다. 값은 잠정값 그대로다.
- 새 LLM 호출 없음. 도구 `docs/ai-experiments/tools/merge_post_gutter_check.py`. 산출물은 `pipeline/out/merge-post-gutter-check_2026-10-23/`(git 제외 — `summary.json` · `cases.json` · `cases.md` · `crops/` 33장).
- 점검 1(노출): xycut 휴리스틱(LLM 없음)에서 같은 후보 영역의 LLM 전송 블록 쌍 중 가로줄 범위가 교차하는 쌍을 센다. 공유 가로줄의 두 조각 사이에 gutter가 있으면 `gutter`, 없으면 `h_ratio`, 공유 가로줄 없이 범위만 겹치면 `nested`(끼인 블록)로 분류했다.
- 점검 2(대리 지표): 끈 상태의 최종 블록을 "그 실행이 한 문단으로 본 범위"로 보고, 그 범위가 xycut에서 같은 영역의 교차 블록 여러 개에 걸치면 xycut 재조립(`merge.assemble`) 결과와 나란히 비교했다. xycut 블록들의 영역 합이 끈 상태 문단과 정확히 같은 사례(exact)만 순서를 비교할 수 있다. 실제로 xycut에서 LLM이 같은 묶음을 낼지는 이 점검으로 알 수 없다.

## 4. 결과

판정 기준: 점검 1은 원인별 교차 쌍 수. 점검 2는 exact 사례에서 재조립 순서가 끈 상태와 같은지, 다르면 섹션 이미지에서 어느 쪽이 화면 읽기 순서에 가까운지(아래는 에이전트 관찰이며 사람 판단이 아니다).

### 4.1 사람 검수 의견(2026-10-23, 채팅 전달 · 정성 의견)

사용자가 검수 페이지(33건)를 보고 TSV 대신 채팅으로 의견을 전달했다. 사례별 판정 · 분류 · 개선 건수는 기록되지 않았으며 여기서도 만들지 않는다.

- **검수 제외(미평가)**: 사례 상당수가 실제 번역 대상이 아닌 제품 라벨 영역이었다. 사용자는 제품 라벨을 번역할 필요가 없는 영역으로 보고 이번 읽기 순서 검수에서 제외했다. 따라서 33건 전체를 검수 완료로 보지 않으며, 제품 라벨로 보아 제외한 사례는 미평가다. 정확한 제외 건수와 사례 ID는 집계되지 않았다.
- **의견**: 검수한 사례에서는 위첨자 · 각주 기호의 배치와 읽기 순서가 확실히 나아졌다. 곡선으로 배치된 글자의 읽기 순서도 나아졌다.
- **해석 한계**: 사용자의 정성적 관찰이며 문자 인식 정확도나 전체 표본의 개선율을 측정한 결과가 아니다. 검수한 사례 수 · ID도 기록되지 않았다. 사용자가 제품 라벨로 판단한 것과 ④ 라벨 판정기가 그 블록을 실제로 제외하는지는 별개이며, 이번 의견으로 라벨 판정 성능이 검증된 것은 아니다. 위 에이전트 관찰의 위첨자 `**`가 줄 앞으로 간 1건은 그대로 남긴다(사용자 의견과 별개의 개별 사례 관찰).

### 4.2 별도 OCR 결함 — "이런 분들에게 추천해요"(GS-03_018/sec_1_02)

읽기 순서 개선과 별개인 원시 OCR의 오검출 · 오인식 후보다.

- 이미지에서 원문에 없는 세로 막대처럼 보이는 문자가 OCR 결과에 더해져 있다. 큰 글자 영역 세 개(`이런` · `분들에게` · `추천해요`) 외에 '게'와 '추' 사이에 작은 중첩 영역이 검출됐다.
- 고정 입력본(`blocks-input-v1`)의 ② OCR JSON에 **저장된 값**(이번에 OCR을 다시 돌리지 않고 조회만 함): 영역 `reg_0005`, 텍스트 `I`(U+0049), 인식 신뢰도 0.277, bbox x 545 · y 297 · w 55 · h 45 — 왼쪽 `분들에게`(x 297~576) · 오른쪽 `추천해요`(x 573~844)와 겹친다. 큰 글자 세 영역의 신뢰도는 0.9998 이상이다.
- 끈 상태(`이런 분들에게 추천해요` / `I`)와 xycut 재조립(`이런 분들에게` / `I` / `추천해요`) **양쪽에 같은 조각이 있다.** 재조립은 이 조각의 위치만 바꿨고, 조각이 생긴 것은 ③ 후처리와 무관한 ② 결과다.
- 원인은 확정하지 않는다. 인접 글자의 세로획을 별도로 검출해 문자로 읽었을 가능성은 있지만, 실제 인식에 들어간 crop을 확인하기 전에는 판단하지 않는다. 저장된 텍스트가 `I`라는 것은 이 입력본의 기록일 뿐, 다른 실행 · 환경에서 같은 문자로 읽히는지도 확인하지 않았다.
- 기존 `open-questions.md` #40(한 섹션 안에서 겹친 OCR 검출의 정리)의 후속 조사 후보로 연결한다. 후속 검토 후보는 검출 임계값, 검출 입력 해상도, 상자 확장 비율, 필요 시 줄 단위 재인식이다. 이번에는 실험 · 구현하지 않았다.
- `|` · `I` 같은 문자의 일괄 삭제나 인식 신뢰도 기준 상향은 채택하지 않았다(② 영역 보존 원칙, `pipeline.md` 7절).

## 5. 판단

보류. 승인된 재정렬 규칙(가로줄 순번 → x)과 영역 분리 규칙은 바꾸지 않는다. 우선 확인하려던 gutter 두 칸 교차는 이 표본에서 관측되지 않았다. 다른 원인의 교차에서는 재정렬이 끈 상태보다 화면 순서에 가까워 보이는 사례가 많았지만 에이전트 관찰이다. 위첨자 기호가 줄 앞으로 가는 사례는 4단계 품질 · 파라미터 확인(가로줄 허용치 · 높이비)에서 다룬다. 사람의 정성 의견은 수집했으며(4.1, 검수 명세 `2026-10-23_03-merge_post-review-spec-v1.md` · 검수 페이지 `docs/ai-experiments/tools/merge_post_review_page.py`), 남은 품질 · 파라미터 확인과 활성화 판단은 후속 단계에서 진행한다. 같은 조건의 진단은 이제 LLM 없이도 `merge_post_debug/`의 `interleaving_pairs`로 남는다(`pipeline.md` 7.1절).

사람 검수 의견(4.1, 2026-10-23)은 위첨자 · 각주 기호와 곡선 배치 글자의 읽기 순서가 나아졌다는 정성 의견이며, 제품 라벨로 본 사례는 미평가다. 판단은 여전히 보류다 — 이 의견으로 기본 활성화 승인 · 파라미터 확정 · 전체 품질 검증 완료를 표시하지 않는다. 남은 것은 4단계 품질 · 파라미터 확인이며(진행 여부는 사용자가 정한다), 4.2의 OCR 결함은 ③ 후처리와 별도로 #40에서 다룬다.
