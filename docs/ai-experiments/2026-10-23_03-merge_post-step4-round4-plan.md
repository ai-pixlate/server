# ③ OCR 후처리 4단계 4차 계획 — y 절단 LLM 병합 허용안의 18섹션 LLM 실행 · 사전 예산 승인 요청(2026-10-23)

이 문서는 **실행 계획과 사전 예산 승인 요청 자료**다. 실험 결과 기록이 아니며, 아래 6절의 승인 전에는 실제 모델을 호출하지 않는다(`docs/ai-baseline/protocols/v1/execution.md` "AI 실행자의 사전 예산 승인"의 형식을 따른다). 이번 준비 단계에서 유료 시험 호출도 하지 않았다.

## 1. 목적

3차 조사(`2026-10-23_03-merge_post-step4-round3.md`)에서 과분할 대응으로 기하 규칙(A1 · A2)보다 "y 절단으로만 나뉜 후보 영역끼리는 LLM 병합 허용" 안이 사람 판정과 구조상 가장 잘 맞았다. 이 안을 실제 LLM(`llm_assist` v1)으로 돌려 다음을 확인한다(`open-questions.md` #86).

- 사람이 "이어져야 함"으로 본 6건을 LLM이 실제로 합치는가.
- 사람이 "나뉘어야 함"으로 본 y 절단 2건(`GS-02_013/sec_1_02:reg_0001` `효과는 압도적으로` / `자극은 최소한으로`, `GS-02_014/sec_1_05:reg_0003`)을 LLM이 합치는가. x 절단 3건(`GS-03_012/sec_1_01`)은 구조상 계속 막힌다.
- 칸 분리 대표 섹션 · B3 검수 섹션에서 새 오류(칸 합침 · 읽기 순서 섞임 · 역할 변화)가 생기는가 — 영역을 넘은 묶음 분리(`region_splits`) · 가로줄 범위 교차(`interleaved`) 기록 포함.
- 현행(B3, 후보 영역 경계 고정)도 같은 18섹션을 돌려 LLM을 포함한 ③ 경로를 처음 확인한다(지금까지는 휴리스틱만 검증).

## 2. 범위

| 항목 | 내용 |
|---|---|
| 입력 | `blocks-input-v1`(입력본 지문 `f54ea91b…2433af9`)의 ② OCR 결과 |
| 섹션 | 18개(3차 기록 4.5): GS-01_001/sec_1_01 · GS-01_002/sec_1_04 · sec_1_06 · sec_1_08 · sec_1_12 · sec_1_19 · GS-02_008/sec_1_04 · sec_1_06 · GS-02_009/sec_1_01 · sec_1_03 · GS-02_013/sec_1_02 · GS-02_014/sec_1_05 · sec_1_11 · GS-03_008/sec_1_02 · GS-03_012/sec_1_01 · GS-03_014/sec_1_01 · GS-03_018/sec_1_02 · sec_1_08 |
| 변형 | **B3**(현행 — 기본 config + `merge.xycut = true`, 후보 영역 경계 고정) · **B3_yonly**(y 절단으로만 나뉜 후보 영역을 한 "칸 묶음"으로 보고 LLM 병합 허용, x 절단은 계속 경계) |
| 모델 · 설정 | `merge.llm_model` `gemini-3.8-flash` · 온도 0 · 시간 제한 60초(현행 config). 프롬프트 `merge_assist.md` + `merge_assist_region.md`(두 변형 같음, 1,875자) |
| 호출 | 섹션당 1회 × 2변형 = **36회**. 보낼 블록이 0개인 섹션은 없다(점검 모드 확인). 애플리케이션 재시도 없음 |
| 코드 기준 | `feature/ocr-postprocessing` `590f067` + 실험 도구 변경(미커밋). 파이프라인 코드 · config는 바꾸지 않는다 |

**B3_yonly 구현(실험 도구 `yonly` patch, 채택 규칙 아님)**: 휴리스틱(블록 · 줄 · 역할)은 B3와 같다(100섹션 확인, 4절). LLM에 보내는 `region`만 "분할 트리의 순수 y 분할 부분 트리" 단위의 칸 묶음 번호로 바꾸고, 조립 정렬 키 앞에 원래 후보 영역 순서를 넣어 위아래 영역의 줄이 섞이지 않게 한다. 영역을 넘는 묶음의 분리 · 역할 재판정(Q1 처리)은 칸 묶음을 넘을 때만 적용된다. 18섹션에서 보내는 region 수는 B3 236 → B3_yonly 137이다. 프롬프트 보충문은 바꾸지 않았다 — 보충문의 "후보 영역"이 이 변형에서는 칸 묶음을 뜻한다.

## 3. 실행 · 판정 방법

```
python docs/ai-experiments/tools/merge_post_step4.py llm-run --round round4 --name B3 \
    --input pipeline/samples/local/blocks-input-v1 --out pipeline/out/merge-post-step4-round4_<날짜> \
    --approved-budget-usd <승인 상한> --max-calls 36
python docs/ai-experiments/tools/merge_post_step4.py llm-run --round round4 --name B3_yonly ...(같은 인자)
python docs/ai-experiments/tools/merge_post_step4.py llm-report --out pipeline/out/merge-post-step4-round4_<날짜> \
    --checkset <1차 checkset.json> --review-tsv <1차 검수 TSV>
```

- 실제 호출은 `--approved-budget-usd` · `--max-calls`와 `GEMINI_API_KEY`가 모두 있어야 시작한다. 호출 예정 수가 `--max-calls`를 넘으면 시작하지 않는다. 출력 폴더가 비어 있지 않으면 덮지 않고 멈춘다. 호출 실패는 재시도하지 않고 실패로 남긴다(재실행은 다시 승인받는다).
- 섹션마다 `merge/`(결과) · `merge_debug/`(LLM 기록 — 페이로드 · 프롬프트 SHA · 응답 · 사용량 · `region_splits` · `interleaved`) · `merge_post_debug/`(후처리 진단)를 남긴다.
- 판정: `llm-report`가 1차 사람 판정 S1 12건(제외 2건 빼고)의 최종 블록 수를 낸다. 영역 분리 · 교차 기록과 새 사례는 사람 정성 검수로 본다. LLM 출력은 정답이 아니며 1회 실행이다(온도 0이어도 같은 응답이 보장되지 않는다).

|---|---|
