# ③ OCR 후처리 4단계 5차 계획 — y 절단 LLM 병합 허용안의 확대 · 반복 실행 · 사전 예산 승인 요청(2026-10-26)

이 문서는 **실행 계획과 사전 예산 승인 요청 자료**다. 실험 결과 기록이 아니다. 아래 6절의 승인 전에는 실제 모델을 호출하지 않는다(`docs/ai-baseline/protocols/v1/execution.md` "AI 실행자의 사전 예산 승인" 형식). 이번 준비 단계에서 유료 시험 호출도 하지 않았다.

## 1. 목적

4차(`2026-10-23_03-merge_post-step4-round4.md`)에서 B3_yonly(y 절단으로만 나뉜 후보 영역끼리 LLM 병합 허용)는 다음 결과를 냈다.

- 사람 판정 사례에서 새로 합친 블록 8개가 모두 사람 검수에서 받아들여졌다(7.1).
- 8블록 밖에서는 에이전트가 잘못된 병합을 찾지 못했다(7.2).

다만 4차에는 세 가지 한계가 있었다. 사용자는 이 결과로 채택을 단정하기 어렵다고 봤다(2026-10-26).

- 18섹션은 1차 검수 사례가 있는 섹션 위주로 골랐다.
- 1회 실행이었다.
- 페이로드가 같은 섹션에서도 역할이 바뀌어 실행 변동이 확인됐다.

5차는 이 한계를 줄이려고 다음 두 가지를 확인한다(`open-questions.md` #86).

- **A. 다른 섹션**: 4차에서 보지 않은 섹션에서 B3_yonly가 잎을 넘어 새로 합친 블록이 사람 기준으로 받아들일 만한가. 독립된 제목 · 제품 설명을 묶는 잘못된 병합이 생기는가.
- **B. 반복 실행**: 4차 18섹션을 같은 조건으로 두 번 더 돌린다.
  - 4차 8블록 병합이 다시 나오는가.
  - 4차 7.2의 구성 · 역할 차이가 변형 차이인지 실행 변동인지 가른다. 같은 변형끼리의 차이와 변형 사이의 차이를 견준다.
  - 4차에서 실패한 `GS-01_002/sec_1_04`도 다시 실행된다.

## 3. 실행 · 판정 방법

```
OUT=pipeline/out/merge-post-step4-round5_<날짜>
T=docs/ai-experiments/tools
# A. 다른 섹션(변형마다)
python $T/merge_post_step4.py llm-run --round round5 --name B3 --input pipeline/samples/local/blocks-input-v1 \
    --out $OUT/new --sections $T/merge_post_step4_round5_sections.txt --approved-budget-usd <승인 상한> --max-calls 59
python $T/merge_post_step4.py llm-run --round round5 --name B3_yonly ...(같은 인자)
# B. 반복 실행(rep2 · rep3, 변형마다)
python $T/merge_post_step4.py llm-run --round round5 --name B3 --input ... --out $OUT/rep2 --approved-budget-usd <승인 상한> --max-calls 18
...(B3_yonly, rep3도 같은 방식)
# 비교(호출 없음)
python $T/merge_post_step4.py llm-diff --input ... --a $OUT/new/B3 --b $OUT/new/B3_yonly --out-json $OUT/diff_new.json
python $T/merge_post_step4.py llm-diff --input ... --a <4차>/B3_yonly --b $OUT/rep2/B3_yonly --out-json $OUT/diff_yonly_rep1_rep2.json
...(변형마다 rep1–rep2 · rep1–rep3 · rep2–rep3, 반복마다 B3–B3_yonly)
```

- 안전장치는 4차와 같다.
  - 실제 호출은 `--approved-budget-usd` · `--max-calls` · `GEMINI_API_KEY`가 모두 있어야 시작한다.
  - 호출 예정 수가 상한을 넘거나 출력 폴더가 비어 있지 않으면 멈춘다.
  - 실패는 재시도하지 않고 실패로 남긴다. 실패 섹션 재실행은 다시 승인받는다.
- 실행 중 누적 추정 비용이 승인 상한에 가까워지면 다음 실행을 시작하지 않고 멈춘다. 실행 단위는 변형 하나의 `llm-run` 1회다.

**판정**

- **A — 사람 검수**: `llm-diff`가 찾은 "B3_yonly에서 잎을 넘어 새로 합쳐진 블록"을 모두 4차와 같은 검수 페이지로 만든다(`merge_post_step4_round4_review_page.py --sections … --store-key …`, 1차 판정 없음).
  - 질문: "이 결과를 하나의 문단 · 편집 블록으로 묶어도 되는가?"
  - 판정: 현행이 적절 / y 병합이 적절 / 둘 다 허용 / 둘 다 부적절 / 판단 어려움
  - 블록 수는 실행 전에는 알 수 없다. 4차 17섹션에서는 8블록이 나왔다.
- **A — 에이전트 관찰**: 잎 안의 구성 차이 · 역할 차이는 4차 7.2처럼 그림으로 보고 기록한다. 사람 판단이 아니다.
- **B — 재현**: 4차 8블록이 rep2 · rep3에서 같은 구성으로 다시 나오는지 본다. rep2 · rep3에서 새로 잎을 넘은 블록이 나오면 A와 같은 검수 페이지에 넣는다.
- **B — 변동 비교**: 같은 변형끼리(B3–B3, B3_yonly–B3_yonly) 실행 사이의 구성 · 역할 차이 건수와 변형 사이의 차이 건수를 나란히 적는다. 건수만 적고 비율로 일반화하지 않는다.
- LLM 출력은 정답이 아니다. 온도 0이어도 같은 응답이 보장되지 않는다.

**채택 판단에 쓸 기준은 사용자가 정한다.** 예를 들어 "새 섹션에서 '현행이 적절' · '둘 다 부적절' 판정이 나온 y 병합 블록을 몇 개까지, 어떤 종류까지 받아들일지" 같은 것이다. 에이전트는 결과를 위 형식으로 내고 기준을 임의로 정하지 않는다.
