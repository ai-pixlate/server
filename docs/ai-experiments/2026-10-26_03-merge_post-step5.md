# ③ OCR 후처리 5단계 — 보류 기능 3종 후보 조사 · 개별 비교(2026-10-26)

## 1. 질문

4단계 종합 정리(`2026-10-26_03-merge_post-step4-summary.md`) 3절의 5단계다(`open-questions.md` #86). 보류 기능 3종을 다음 순서로 확인한다.

1. 실제 OCR 결과에 각 기능이 고칠 오류가 있는가.
2. 규칙이 그것을 맞게 고치는가.
3. 정상 글자를 훼손하는가.

| 기능 | 내용 |
|---|---|
| ① 숫자 속 o/O 교정 | 숫자 사이에 낀 o/O를 0으로 바꾼다 |
| ② 겹친 앞 글자 제거 | 겹친 상자가 앞 단어 끝 글자를 다시 읽은 것을 지운다 |
| ③ 맨 앞 따옴표 제거 | 체크 · 글머리 아이콘을 따옴표로 읽은 것을 지운다 |

채택 여부는 사용자가 정한다. 이 기록은 조사 · 실험 · 검수 자료 준비까지다.

## 2. 원 제안 조건(참고 구현 그대로)

출처는 seed-builder PR #1(헤드 `fc72ecd`, 미병합)의 `amazon/reorder_ocr_v2.py`다(2026-10-26에 다시 읽음). 원래는 OCR 상자 글자(`text_clean`)에 적용했다. 우리 실험에서는 같은 규칙을 원시 영역 하나의 글자에 적용한다.

| 기능 | 조건 |
|---|---|
| ① `fix_chars` num_o | 정규식 `(?<![A-Za-z])(\d[\doO]*(?:[.,][\doO]+)*)(?=%\|\b)`. 숫자로 시작하고 숫자 · o · O · 쉼표 · 점만 있는 덩어리에서 o/O를 0으로 바꾼다. 영문자 바로 뒤의 숫자는 제외한다. 원 제안 예: `1o,ooo` · `1oo%` · `SPF 5O` · `13.O` |
| ② `strip_stray` | 다음 네 조건을 모두 만족하면 앞의 그 한 글자(와 띄어쓰기)를 지운다 ↓ |
| ③ `fix_chars` quote | 정규식 `^['`‘’]\s+(?=\S)`. 맨 앞의 작은따옴표 · 백틱 + 띄어쓰기만 지운다. 큰따옴표는 진짜 인용일 수 있어 두었다 |

② `strip_stray`의 네 조건:

1. 상자 글자가 `^([A-Za-z0-9,.;:])\s*(?=\S)`에 맞는다. 영문자 · 숫자는 바로 뒤에 띄어쓰기가 있어야 하고, 기호 `, . ; :`는 붙어 있어도 된다.
2. 같은 XY-cut 잎에서, 세로 중심 차이가 상자 높이의 1/2 이하인 같은 줄에 왼쪽 이웃이 있다.
3. 그 이웃과의 간격이 높이 × 0.3 이하다(붙음 또는 겹침).
4. 지울 글자가 이웃 글자의 마지막 글자와 같거나(대소문자 무시) 생김새 집합 `{1 I i l | d t}` · `{o O 0 p d b q a e c g}` 안에서 비슷하다.

원 제안 예: `Deep` + `o Hydration`, `choose` + `e your`, `and` + `d radiant.`.

**#40과의 관계**: ②는 띄어쓰기로 떨어진 한 글자(영문 · 숫자 · 기호)만 다룬다. "이런 분들에게 I 추천해요"(`GS-03_018/sec_1_02`)처럼 큰 글자 사이에 낀 중첩 영역은 대상이 아니다. 이 사례에서 `I`는 영역 하나 전체이고 왼쪽 글자 `게`와 비슷한 모양도 아니다. 이번 실험은 ②를 #40 전체로 넓히지 않았다.

## 4. 방법

도구는 `docs/ai-experiments/tools/merge_post_step5.py`(호출 없음), 산출물은 `pipeline/out/merge-post-step5_2026-10-26/`(git 제외)이다.

1. **`scan`** — 영역마다 규칙 적중(rule)을 찾는다.
   - 규칙이 놓친 것과 잘못 고칠 위험을 보려고 넓은 탐색(wide)도 함께 모았다.
   - ① 숫자와 o/O가 붙은 글자, ② 한 글자 + 띄어쓰기로 시작, ③ 따옴표류(`' \` ‘ ’ " “ ”`)가 있는 글자.
2. **원본 대조** — 후보의 섹션 이미지 crop을 에이전트가 직접 봤다. 대상은 ① 14개 전부, ② 영문 · 기호로 시작하는 18개 전부, ③ 8개다. **사람 판단이 아니다.**
3. **`compare`** — 기준(기본 config + `merge.xycut = true`, 채택된 B3 · 칸 묶음 규칙)에 기능을 하나씩 켜고 LLM 없는 휴리스틱 결과를 비교했다.
   - 적용 위치는 전각 변환과 같은 `Line.text` 조립 단계다. 실험 프로세스 안에서만 `_Line.text`를 바꿔 끼웠다.
   - 원시 영역(`regions[].text`)은 그대로다. 실행 전후로 같음을 확인했다.
   - 기존 LLM 결과(4차 · 5차 A `B3_yonly`)의 최종 블록에도 같은 교정을 사후 적용해 봤다. 교정된 입력에 대한 LLM 응답은 아니다(가정).
4. **`selfcheck`** — 합성 사례로 규칙의 교정 · 누락 · 훼손을 확인했다. **규칙 확인용이며 실제 품질 개선 근거가 아니다.**
5. **`page`** — 사람 검수 페이지를 만들었다(6절).

- **휴리스틱 비교**: 3섹션 · 5블록의 `source_ko`가 바뀌었다. 블록 구성 · 역할 변화는 0이다. 1:1 치환이라 글자 수는 그대로다.

### 5.3 ② 겹친 앞 글자 — 원본 대조(에이전트 관찰)

- 규칙 적중 0이다. 넓은 탐색 40개 중 한국어로 시작하는 22개(`내 ` · `더 ` · `단 ` · `등 ` 등)는 모두 정상 한 음절 낱말이다. 규칙은 영문 · 숫자 · 기호만 보므로 대상이 아니다.
- 영문 · 기호로 시작하는 18개를 이미지로 봤으나, 겹친 상자가 앞 단어 끝 글자를 다시 읽은 사례는 없었다. 내역은 다음과 같다.
  - **정상 관사 · 단어 · 글머리 기호**: `a cosmetic formulation` · `A long-term` · `A comparative…` · `- A new…` 등. 규칙 미적용이 맞다.
  - **잘린 앞 단어 꼬리**: `I Studies`. 겹침이 아니다.
  - **흐린 논문 이미지 · 회전 글자의 OCR 잡음**: `o Mattn` · `e ar` · `e teel…` · `2 1-40.4` · `A RAL`.
- **합성 확인**: 원 제안 예 3개는 지운다. 정상 관사 `a`가 비슷한 모양 글자로 끝나는 단어에 붙어 있으면 지워 훼손한다(`Extra` · `Spa` + `a …`). #40 모양(`분들에게` + `I 추천해요`)은 건드리지 않는다.
- **결론**: 이 입력본(한국어 인식 모델)에서는 이 기능이 고칠 오류가 나오지 않았다. 표본 부족이다.

### 5.4 ③ 맨 앞 따옴표 — 원본 대조(에이전트 관찰)

- 규칙 적중 0이다. 넓은 탐색 38개를 따옴표 종류로 나누면 큰따옴표만 24 · 작은따옴표류만 13 · 둘 다 1이다.
- 체크 · 글머리 아이콘을 맨 앞 따옴표로 읽은 사례는 없었다. 이미지로 본 8개는 다음과 같다.
  - **실제 인용 2**: `2025.09.15 북미 아마존'레티날(RETINAL)'…`, `'레티날 샷 타이트닝 부스터'를 개발했습니다.`(번역 대상 본문)
  - **아포스트로피 1**: `심톨'S PICK!`
  - **위첨자 오인식 5**(아래)
- 이미지의 `‘ 레티날 샷…` 사례는 여는 따옴표 뒤가 시각적으로 떠 있다. OCR이 띄어 읽었다면 규칙이 실제 인용부호를 지웠을 모양이다(합성 확인).
- **다른 오류 유형(이번 기능 대상 아님)**: 위첨자 기호 ® · *가 따옴표로 읽힌 사례가 번역 대상 텍스트에 5건 있었다. 맨 앞이 아니라 낱말 뒤라 ③ 규칙과 무관하다. 이미지로 보지 않은 나머지 30개 중에도 비슷한 사례(`M.E.L.A Spotless Ex"` · `…특허성분"과`)가 있어 보이나 확인하지 않았다.

  | 섹션 | 원시 OCR | 이미지 |
  |---|---|---|
  | `GS-02_008/sec_1_05` | `에이샷'으로` | `에이샷®으로` |
  | `GS-02_009/sec_1_01` | `Matrixyl' 3000` | `Matrixyl® 3000` |
  | `GS-03_002/sec_1_01` | `단2주'만에` | `단 2주* 만에` |
  | `GS-03_002/sec_1_01` | `내추럴 톤업"` | `내추럴 톤업**` |
  | `GS-03_005/sec_1_01` | `즉각 톤업'까지` | `즉각 톤업*까지` |

- **결론**: 이 입력본에서 이 기능이 고칠 오류는 나오지 않았다. 표본 부족이다.

### 5.5 줄 조립 · `source_ko` · 문자 구간 영향

- **적용 위치**: 전각 변환과 같이 `Line.text`(영역 글자를 띄어쓰기로 이은 줄)와 그것을 이은 `source_ko`에만 적용한다. 원시 영역의 `text` · `score` · `poly` · `bbox`는 그대로다(계약 2.5).
- **① o → 0**: 1:1 치환이라 같은 조립 문자열이면 글자 수 · 코드 포인트 위치가 그대로다. ② · ③은 글자를 지워 `source_ko`가 짧아진다.
- **문자 구간(span)**: 계약상 그 실행 `source_ko`의 코드 포인트 `[start, end)`다(`contract.md` 4.4). ⑤ 매칭은 교정된 `source_ko`에서 다시 계산되므로 형식 변경은 필요 없다.
  - 다만 교정이 매칭 결과를 바꿀 수 있다. 예: `SPF 5O` → `SPF 50`이면 사전 표현에 걸릴 수 있다.
  - 입력 지문이 바뀌므로 재분석 대상이다(전각 변환과 같음).
- **계약 · 상위 문서**: 기능을 채택하면 `source_ko`가 "원시 OCR을 이은 원문"에서 더 멀어진다(특히 삭제). `open-questions.md` 3절 F에 적힌 전각 보정과 같은 범주로, "글자 보정 문장" 정의를 상위 계약에 반영하는 일이 생긴다. 이번에는 구현하지 않으며, 채택하면 F 항목 문구를 넓히는 것을 제안한다.
- **BE 영향(후속 문서용, 이번에 BE 확인 · 요청 없음)**: 교정을 켜면 같은 원본에서도 `source_ko`가 달라진다. 영향 대상은 화면 원문 표시 · 입력 지문 · 재분석 · 캐시이고, 기존 `be-handoff.md` 10.2의 `source_ko` 의미 · 지문 항목과 같은 종류다. 채택이 정해지면 10.2 표에 기능 이름을 덧붙인다.

  | B | ① 규칙이 놓친 실제 오류 후보 3 | 오류가 있는가 |
  | C | 잘못 고칠 위험 · 정상 사례 9(① 3 · ② 4 · ③ 2) | 오류가 있는가 |

- 카드마다 표시 없는 crop · 대상 영역 틀 · 접어 둔 섹션 전체 · 원시 OCR과 교정 후 글자 · 범위 · 에이전트 관찰이 있다.
- 판정 선택은 필수가 아니다(채팅 의견 전제).

### 6.1 사람 검수 의견(2026-10-26 사용자 채팅, 1차)

판정은 사람 판단이다. 의견을 받은 카드만 적는다.

| 카드 | 사람 의견 | 비고 |
|---|---|---|
| A `GS-02_009/sec_1_01` reg_0002 (`MATRIXYL°300O*3%` → `…3000*3%`) | 교정 전과 후가 같아 보인다. 오히려 MATRIXYL 뒤의 위첨자 ®가 잘못 추출됐다(`°`) | 아래 "페이지 보완" 참고 |
| A `GS-02_009/sec_1_01` reg_0014 (`*MATRIXTYL@300O:` → `…3000:`) | 교정 전과 후가 같아 보인다 | 아래 "페이지 보완" 참고. 에이전트 관찰: 여기서도 ®가 `@`로 읽혔다 |
| C `GS-02_014/sec_1_11` reg_0024 · `GS-02_009/sec_1_02` reg_0009 | 적절하다 — 실제 인용부호를 그대로 두는 것이 맞다 | 맨 앞 따옴표 규칙은 적용되지 않았다 |
| D `GS-02_008/sec_1_05` reg_0006 · `GS-02_009/sec_1_01` reg_0003 | 위첨자 ®가 `'`로 잘못 추출됐다 | 에이전트 관찰과 같다 |
| D `GS-03_002/sec_1_01` reg_0027 · `GS-03_005/sec_1_01` reg_0012 | 위첨자 *가 `'`로 잘못 추출됐다 | 같다 |
| D `GS-03_002/sec_1_01` reg_0029 | 위첨자 **가 `"`로 잘못 추출됐다 | 같다 |

- **1차 시점에 의견을 받지 않은 카드**: A의 나머지 6건(영문 참고문헌 4 · 논문 이미지 1 · 제품 라벨 1), B 3건, C 7건(숫자 잡음 3 · 겹친 앞 글자 4). A 6건은 아래 2차에서 받았다.
- **페이지 보완(2026-10-26)**: MATRIXYL 2건은 원시 OCR이 `300O`(영문 대문자 O, U+004F)이고 교정 후가 `3000`(숫자 0, U+0030)이다. 그런데 페이지 글꼴에서 O와 0이 거의 같게 보였다. "같아 보인다"는 이 표시 문제일 가능성이 높아, 교정이 틀렸다는 판정으로 세지 않는다. 바뀐 글자를 노란색으로 강조하고 문자 이름 · 코드 포인트를 적도록 페이지를 고쳤다(A 8장). A 2건의 교정 맞음 여부는 다시 확인받을 대상이다.
- **2차 의견(2026-10-26, 표시 보완 뒤)**: 사용자는 "번역 대상 2건은 교정 전에도 o가 아닌 0이었고, 실제로 바뀐 글자는 번역 대상이 아닌 글자들 중 일부였던 것 같다"고 봤다. 원시 OCR 파일을 코드 포인트로 다시 확인한 결과는 이 의견과 다르다.
  - `blocks-input-v1` · `merge-input-v1` · `downstream-input-v1` · `logo-input-v1` 네 사본 모두 같았다.
  - reg_0002: `°` `3` `0` `0` **`O`(U+004F)** `*`
  - reg_0014: `@` `3` `0` `0` **`O`(U+004F)** `:`
  - 즉 원시 OCR의 넷째 자리는 영문 대문자 O이고, 규칙은 이 한 글자를 숫자 0으로 바꾼다. 원본 이미지는 `3000`이다.
  - 사용자가 파일 근거를 확인한 뒤 **2건 모두 교정 맞음**으로 판단했다(2026-10-26 채팅). 따라서 A의 번역 대상 2건은 사람 검수에서 "교정 맞음"이다.
- **A 나머지 6건(2026-10-26 채팅)**: "번역 대상은 아니지만 실제로 모두 교정된 것을 확인했다" — 영문 참고문헌 연도 4 · 논문 이미지 `100%` 1 · 제품 라벨 `SPF 50+` 1, **모두 교정 맞음**(범위는 번역 대상 아님).
- **A 합계**: 사람 검수 8/8 교정 맞음 — 번역 대상 2 · 번역 대상 아님 6. 훼손으로 본 사례 없음.
- **아직 의견이 없는 카드(2차 뒤)**: B 3건(규칙이 놓친 오류 후보) · C 7건(숫자 잡음 3 · 겹친 앞 글자 4).
- **위첨자 오인식(D 유형)**: 사람이 확인한 사례가 5건에서 6건으로 늘었다(reg_0002의 ® → `°`, 사람 의견). reg_0014의 ® → `@`도 같은 유형으로 보인다(에이전트 관찰). 이번 기능들의 대상이 아닌 별도 유형이며, 다룰지는 사용자 결정이다.

## 7. 권고(에이전트 판단 — 채택은 사용자가 정한다)

| 기능 | 권고 | 근거 |
|---|---|---|
| ① 숫자 속 o/O | **추가 검증 뒤 조건부 채택 후보** | 규칙이 고친 8건 모두 사람 검수에서 교정 맞음으로 확인됐다(번역 대상 2 · 아님 6, 6.1). 규칙이 놓친 B 3건은 사람 의견을 받지 않았다. 실제 오류 11건 중 8건을 고쳤고 실제 훼손은 0이다(에이전트 관찰). 다만 번역 대상 텍스트의 개선은 2건뿐이고 나머지는 참고문헌 · 논문 이미지 · 라벨이다. 숫자+O 실제 코드의 훼손 위험은 표본에 없어 확인하지 못했다. 사람 검수(A · B)로 8건이 확인되면 원 규칙 그대로 채택을 고려할 수 있다. 놓친 사례(`SPF5O` · `(2o1e)` · 한글 접합)까지 넓히는 것은 새 규칙이라 별도 실험이 필요하며 지금은 권하지 않는다 |
| ② 겹친 앞 글자 | **보류** | 실제 오류 0 · 규칙 적중 0이라 이 입력본에서 개선 근거가 없다. 합성에서 정상 관사 훼손 모양이 확인됐다. 원 제안의 오류는 다른 인식 모델 · 영문 이미지에서 본 것이다. 인식 모델을 바꾸거나 영문 원본을 다룰 때 다시 본다. #40(중첩 검출)과는 별개다 |
| ③ 맨 앞 따옴표 | **보류** | 실제 오류 0 · 규칙 적중 0이다. 실제 인용부호를 지울 위험(띄어 읽힌 여는 따옴표)이 합성으로 확인됐다. 실제 인용부호 2건은 그대로 두는 것이 맞다는 사람 의견을 받았다(6.1). 대신 번역 대상 텍스트에서 위첨자 ® · *가 따옴표 · 기호로 읽히는 다른 오류가 보였다(사람 확인 6건, 6.1). 이 유형을 다룰지는 새 과제로 사용자 결정이 필요하다(지금은 기록만) |
