# ③ OCR 후처리 — y 절단 LLM 병합 허용안 채택 설계안(2026-10-26)

이 문서는 **설계안**이다. **2026-10-26 사용자 승인 — D1~D4 모두 권장안(a)**("채택 설계안의 D1~D4를 모두 권장안(a)으로 승인해. 설계안대로 구현하고 5절 검증까지 해줘"). 구현 · 검증 결과는 8절. 근거는 4차(`2026-10-23_03-merge_post-step4-round4.md`)와 5차(`2026-10-26_03-merge_post-step4-round5.md`) 실행 · 사람 검수다(`open-questions.md` #86).

## 1. 바꾸려는 규칙

| | 지금(승인 규칙, 2026-10-22) | 채택안 |
|---|---|---|
| 휴리스틱 블록 | 후보 영역(분할 트리의 잎)을 넘지 않는다 | 그대로 |
| LLM 병합 | 후보 영역을 넘지 않는다. 넘은 묶음은 영역별로 나누고 조각에 휴리스틱 역할을 다시 적용한다 | **칸 묶음**을 넘지 않는다. 같은 칸 묶음 안의 후보 영역끼리는 합칠 수 있다. 넘은 묶음은 칸 묶음별로 나누고 조각에 휴리스틱 역할을 다시 적용한다(처리 방식은 같고 경계만 넓어진다) |
| LLM 입력 `region` | 후보 영역 번호 | 칸 묶음 번호 |

**칸 묶음**은 분할 트리에서 y 절단(위아래 여백)으로만 이어진 후보 영역의 묶음이다. 후보 영역 순서(깊이 우선)에서 **이웃한** 두 후보 영역 사이 경로(공통 조상 → 각 잎)의 절단이 모두 y면 같은 칸 묶음으로 잇는다. 나란한 칸을 가르는 x 절단은 계속 경계다. 번호는 1부터 그 순서대로 매긴다(실험 `yonly` patch와 같은 정의).

> **정정(2026-10-26, 구현 중)**: 처음 이 절에는 "두 후보 영역 사이 경로가 모두 y면 같은 칸 묶음이고, 한 칸 묶음의 잎은 깊이 우선 순서에서 연달아 나온다"고 적었다. 뒤 문장은 틀렸다. 경로만 보면 위 제목과 아래 문단처럼 사이에 다단 영역이 낀 두 영역도 같은 묶음이 되고, 그 묶음은 읽기 순서에서 연달아 있지 않다. 실험 patch는 이웃한 영역끼리만 이었으므로 이런 경우를 잇지 않았다. 사람 검수를 받은 쪽은 실험 동작이므로 정의를 "이웃한 두 영역" 기준으로 바로잡고 그대로 구현했다(8절).

바뀌지 않는 것:

- 휴리스틱(블록 · 줄 · 역할 · 블록 순서), 스위치 기본값(`merge.xycut = false`), 응답 검증 · 실패 규칙
- 출력 스키마(`MergeResult` 필드). 계약(`contract.md`) 변경은 없다.

알려진 영향(5차 기록 4.2 · 4.3, 에이전트 관찰):

- **과분할 개선**: 사람이 이어져야 한다고 본 6건이 합쳐졌다. 3회 실행에서 모두 같은 결과였다.
- **라벨 오병합**: 패키지 라벨에서 떨어진 요소를 합친 사례가 1회 실행에서 나왔다. 사람 검수에서 범위 밖으로 봤다(D4).
- **후보 영역 안 병합 감소**: 라벨 오병합과는 별개의 부수 효과다. 같은 후보 영역 안에서 LLM이 묶는 일이 현행보다 일관되게 줄었고, 대상은 주로 패키지 · 문서 · 그래프 글자였다. 즉 과분할 개선만 일어난 것은 아니다. 좋고 나쁨은 판정하지 않았고, 이번 채택의 선행 실험으로 요구하지 않는다.

## 4. 코드 변경 범위

### 4.1 `pipeline/stages/merge.py`

실험 patch는 `block_region`을 칸 묶음 번호로 덮고 정렬 키 앞에 잎 번호 × 1,000,000을 넣었다. 운영 코드에서는 다음처럼 바꾼다.

- **잎 번호는 그대로 두고 칸 묶음을 따로 둔다.** `block_region`(잎) · `line_rank`(잎 안 순번)의 뜻이 그대로라 기존 실험 도구(`merge_post_compare.py` · `merge_post_gutter_check.py`)도 그대로 돈다.

| 위치 | 변경 |
|---|---|
| `_Layout` | `block_group: dict[str, int]`(블록 키 → 칸 묶음 번호), `leaf_group: list[int]`(잎 → 칸 묶음, 진단용) 추가 |
| 새 함수 `_column_groups(tree)` | 분할 트리에서 깊이 우선 잎 순서로 칸 묶음 번호를 매긴다. 재귀 없이(기존 `test_many_regions_do_not_hit_recursion_limit` 기준) |
| `_heuristic` | xycut일 때 `block_group`을 채운다(단독 블록 포함 — 단독 블록은 찾은 잎의 칸 묶음) |
| `build_payload` | `region` = `block_group` |
| `assemble`(layout 있음) | 아래 표 "읽기 순서 키" 참고 |
| `_post_diagnostics` | 블록 · 영역 항목에 `group` 추가. `interleaving_pairs`(같은 잎 안)는 그대로 |
| 모듈 · 함수 설명 | "영역을 넘는 묶음" 설명을 칸 묶음 기준으로 고친다 |

**읽기 순서 키(`assemble`)** — 묶음 안 줄 순서와 묶음의 최종 위치에 같은 기준을 쓴다.

- 기준: 후보 영역 순서 → 가로줄 순번 → x → `region_key`.
- 영역마다 가로줄 순번이 1부터 다시 시작하므로, 키 맨 앞에 항상 후보 영역(잎) 번호를 둔다.

| 쓰임 | 지금 | 채택안 |
|---|---|---|
| 나누기 기준 | `block_region`(잎) | `block_group`(칸 묶음) |
| 묶음 안 블록 정렬(첫 멤버 = 묶음 대표) | `block_rank`만 — 잎 안에서만 맞다 | (`block_region`, `block_rank`) |
| 묶음 안 줄 정렬 | `line_rank` = (가로줄 순번, x, `region_key`) | (줄이 속한 블록의 `block_region`, `line_rank`) |
| 묶음의 최종 위치 | (대표의 `block_region`, `block_rank`) | 그대로. 대표가 위 정렬의 첫 멤버, 곧 읽기 순서상 가장 앞선 멤버이므로 위치도 같은 기준을 따른다 |
| 가로줄 범위 교차 판정 | 가로줄 순번 구간 | (잎, 가로줄 순번) 구간. 다른 잎끼리의 결합은 교차로 세지 않는다 |

지금 코드에서는 묶음 안 블록을 `block_rank`만으로 정렬한다. 영역을 넘는 묶음이 생기면 아래 영역 블록이 대표가 되어 묶음이 뒤로 갈 수 있다. 실험 `yonly` patch는 정렬 키 앞에 잎 번호 × 1,000,000을 넣어 이를 피했다. 운영 코드는 키를 튜플로 명시한다.

`REGION_PROMPT_PATH` · 보충 프롬프트 원문 · 응답 검증 · `run` · `analyze()` 연결은 바꾸지 않는다(D2(a) · D3(a)).

   - **응답을 넣기 전**: 운영 코드가 만든 프롬프트 지문(`prompt_sha256`)과 LLM 입력 지문(`payload_sha256`)이 기록과 같은지 먼저 확인한다. 다르면 그 섹션은 재생하지 않고 차이로 보고한다.
   - **비교 대상**: 최종 블록의 구성(원시 영역 목록) · 순서(`block_order`) · 텍스트(`source_ko` · 줄 텍스트와 줄 순서) · 역할
   - 새로 더하는 진단 필드(`group` 등)는 과거 파일과 같을 필요가 없다. `merge_debug`의 `region_splits` · `interleaved`는 참고로만 대조한다.
3. xycut 끔 경로는 기존 결과와 같다(기존 테스트 · 100섹션 휴리스틱 비교).
