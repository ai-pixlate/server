### 1.2 V6 실측 기록과의 비교 가능성

PRD의 「V6 1차 실측」(F-TRN-04 L · OI-65 「보고값 97% · 측정 조건 확인 중」)은 PoC 저장소 `ai-pixlate/ai-poc`의 「번역 길이 팽창률」 측정이다

| 항목 | PoC V6(골든) | 이번 실험 |
|---|---|---|
| 표본 | 골든 96섹션 · 569세그먼트(PoC 블록 병합) | v1.0.1 베이스라인 GS-01 · 02 · 491블록(제품 파이프라인) |

| 글꼴 · 자간 | Arial · 자간 0 | Pretendard 400/600 · 역할별 자간(−0.01~−0.03em) |
| 글자 크기 | em = 줄 높이 × 1.35 | ⑦ 측정 `est_font_px`(v1.0.1의 em_ratio 0.9 기준, #85 잠정) |

  촬영 경로가 아니다. 1.1.0 서버 이미지는 Pillow(`pillow-typeset/3`, 자간 없음)라 실제 서비스 렌더와 다르다(4절 해석).
- 브라우저 · 폰트 · FE: Playwright 1.61.0 번들 Chromium 149.0.7827.55 headless, Windows 11(TextMetrics 정수화 환경), DPR 2 판정 · 픽셀 대조,
  Pretendard v1.3.9 OTF(승인 설정 파일), FE `integration/second-round-20261106` `87aee91`(이후 FE 측정 모듈 변경 없음 확인).
- 조정 수단(PRD F-TRN-04 ⑦의 실험 해석):
  - **B 줄바꿈 위치** — 번역문의 명시적 개행을 풀어 브라우저 자연 줄바꿈에 맡긴다(글자 불변). 줄 수가 늘면 기각, 넘침이 줄 때만 채택.
  - **E 영역 확장** — 같은 섹션의 다른 text_block 박스(라벨 · 로고 · 번역 제외 블록 포함)와 섹션 경계에 닿기 전까지만, 간격 0 · 겹침 0.
    가로 넘침은 정렬 방향으로 폭(left → 오른쪽, right → 왼쪽, center → 양쪽, 필요한 만큼만 이분 탐색), 세로 넘침은 높이(엔진 ink 경계까지).
    사진 · 그래픽 등 이미지 요소와의 겹침은 판단하지 못한다.
  - **S 폰트 축소** — 시스템 배율을 하한까지 내려 들어가는 가장 큰 배율을 이분 탐색(정밀도 0.005).
- 후보: 단독 S90(하한 0.90 = PRD −10% 잠정) · S80(0.80 = PoC V6 조건) · B · E, 조합 BES90(B → E → S, PRD 「축소는 최후 수단」) ·
  BSE90(B → S → E), 진단 NEED(하한 0.30까지 필요한 배율만 잼, 측정 없음).
- 적용 규칙(후보): 블록마다 **해소될 때만 적용** — 끝까지 넘치면 조정하지 않은 원래 입력을 둔다. 시도한 최종 상태와 남은 원인은 기록만 한다.
- 탐색 기준: `quant_aware`(기본) — 엔진 초과 2px 이하 방향만 픽셀 대조로 다시 확인(이 PC의 TextMetrics 정수화 보정). `engine` — 합의 기준 그대로.
  최종 판정은 조정 입력을 `measure`로 다시 재서 합의 기준(엔진)과 픽셀 해석을 모두 보고한다.
- 부작용 지표: 적용 배율 · 글자 크기(375px 기준 환산 = 원본 px × 375 / 섹션 폭 — 화면 기준 폭 환산이며 가독성 하한은 정해지지 않았다) ·

## 4. 결과

판정 기준: 「해소」는 탐색 기준으로 넘침이 없어져 조정을 적용한 블록이다. 조정 입력을 `measure`로 다시 잰 결과는 합의 기준(엔진 정상)과
픽셀 해석(엔진 정상 + 정수화 범위 · 0.5px 이하라 그림으로는 영역 안)을 함께 적는다. 부작용은 실제로 적용된 블록만 센다. 그림 확인은
에이전트가 본 것이며 사람 검수가 아니다. 수치는 2개 상품 표본 안의 결과이며 전체로 넓히지 않는다.

조정 전(`before/`, 491블록): 엔진 넘침 437 · 그중 픽셀 기준으로도 넘친 409 · 측정 실패 2. 탐색 기준 `quant_aware`의 조정 대상은 409블록이다.
조정하지 않은 블록은 모든 후보의 재측정에서 ink 좌표까지 같았다(재현성).

### 4.2 부작용

- **높이 확장은 그림을 바꾸지 않는다.** 글자 배치는 박스 높이와 무관해서, 높이만 늘린 블록은 렌더 픽셀이 조정 전과 같고 판정 영역만 넓어진다.
  BES90에서 높이를 늘린 블록의 높이 배율 p10 · 중앙 · p90 · 최대 = 1.19 · 1.88 · 3.02 · 5.35, 폭을 늘린 블록의 폭 배율 = 1.04 · 1.14 · 1.69 · 2.57.
- **이미지 요소와의 겹침을 막지 못한다.** 장애물은 다른 text_block 박스뿐이라, 원래 영역 밖에 놓인 글자 자리의 배경 경계 픽셀 비율
  (경계 강도 32 이상, 실험 분류값 5% 이상)이 높은 블록이 BES90 328 중 62(19%)였다. 그림 확인: `Eye Wrinkle Improvement When Used Together`(GS-02 #758)
  는 둘째 · 셋째 줄이 피부 사진 위에 있고, `A small amount, the size of an Oryza Sativa (Rice) Kernel`(GS-02 #736)은 손가락 그림 위에 있다.
  조정 전에도 넘쳐 있던 자리이며, 확장은 이를 「넘침 아님」으로 바꿨다. 단색 배경으로 분류된 확장(GS-02 #717)은 다음 블록 바로 위까지
  두 줄이 들어간 무난한 결과였다. 경계 비율 지표는 확인한 두 사례를 잡았지만 임계값은 검증하지 않았다.
- **간격 0은 측정 오차를 감당하지 못한다.** 확장 후 글자 ink가 맞닿은 이웃 박스에 걸친 블록이 BES90 25 · E 7(BSE90 0) — 모두 1.42px 이하로,
  정수화로 엔진 ink가 바깥으로 잡힌 결과다(픽셀로는 겹치지 않음).
- 섹션 밖 · 최종 이미지 밖(Q-07): BES90 적용 블록에서 조정 전 6 · 1 → 조정 후 0 · 0. 확장은 섹션 안으로만 해서 새 경계 이탈은 없었다.
- 글자 크기: 375px 환산 크기는 조정 전부터 작은 블록이 많다(⑦ 측정 크기 그대로) — 절대 하한을 정하려면 원본 크기 분포를 먼저 봐야 한다(PRD M의
  V4 실측 예고). 축소가 새로 만든 저하는 위 표의 「새로 미만」만이다. 축소 폭은 375px 환산 최대 3.8px(BES90).

### 4.3 해결되지 않는 사례와 원인(BES90, 71/409)

- 원인: 71 모두 「여백 없음(다른 블록 · 섹션 경계) + 축소 하한 도달」. 그중 한 단어가 영역 폭보다 넓은 블록 5.
- 역할: title 47 · caption 17 · body 7. 남은 방향: 아래 66 · 오른쪽 6. 조정 전 초과량 / 영역 높이 중앙 1.13.
- 대표: `Gentle Even on Sensitive Skin`(GS-01 #39) — 한 줄 영역의 제목이 영어로 두 줄이 되고 바로 아래 다른 제목이 있어 넓힐 자리가 없다. 한 줄에
  맞추려면 축소만으로 0.54배가 필요하다. 미해결 71의 축소만 필요 배율 중앙 0.61 · p75 0.69.
- 이 사례들은 PRD대로 「수렴하지 않은 블록 = 폭 초과 표시 · 문장 수정」 대상이다(자동 축약 없음).

### 4.4 측정 환경과 탐색 기준의 영향

- 합의 기준(`engine`) 그대로 탐색하면: 축소만으로 0.30까지 줄여도 437 중 302가 들어가지 않고(필요 배율 ≥0.90 4.3%), BES90 해소 269 · S90 38.
  정수화로 생긴 왼쪽 1px 안팎의 넘침은 글자를 줄여도 사라지지 않아, 이 PC에서는 「들어갈 때까지 줄이는」 루프가 끝까지 줄이는 쪽으로 치우친다.
- `quant_aware`는 그 2px 이하 방향만 픽셀로 다시 확인한 실험 기준이다. 서버 기준 환경(Linux Playwright)에서 정수화가 없다면 그 환경의 엔진
  판정이 이 실험의 `quant_aware`에 가까울 것으로 보이나 확인하지 않았다.

### 4.5 처리 부담

- 측정 1회(브라우저 안, FE 엔진): 0.43~0.45ms(이 PC, 같은 블록 50회 평균). 이 도구의 Python ↔ 브라우저 왕복을 넣으면 약 5ms.

### 4.6 PoC V6와의 방향 비교

- V6(골든 569세그먼트): 줄바꿈 + 80% 축소 뒤 남은 초과 97%, 폭 배율 중앙 2.27. 이번: 축소만으로 0.80 이상에서 들어가는 블록 28.6%(남은 71%).

## 5. 판단

**보류** — 정본 · 운영 코드 · config · 계약을 바꾸지 않는다. 아래는 구현 기준 **후보**다.

추천 순서 · 한도 후보와 근거:

1. **순서: 줄바꿈 위치 → 영역 확장 → 폰트 축소(최후 수단)** — BES90은 BSE90과 해소 수가 같으면서 축소 블록이 46 대 318, 12px 아래로 새로 떨어진
   블록이 3 대 30이다. PRD의 「축소는 최후 수단」과 맞는다.
2. **줄바꿈 위치 = 명시적 개행 해제(자연 줄바꿈)** — 줄 수를 늘리지 않고 글자를 바꾸지 않는다. 효과는 작지만 부작용이 없었다. `line_break_applied`의
   의미를 이 해석으로 정할지는 결정이 필요하다.
3. **폰트 축소 하한 −10% 유지(후보)** — 단독 효과는 15%뿐이지만 −20%로 늘려도 29%이고 새로 작아지는 블록이 늘어난다(1 → 12). 축소를 주 수단으로
   삼을 근거가 없다. 절대 px 하한은 원본 크기 분포 측정 뒤 정한다(이번 결과로 정하지 않는다).
4. **영역 확장은 「텍스트 박스와 겹치지 않음」만으로는 부족** — 해소의 대부분을 만들지만 높이 확장은 그림을 바꾸지 않고 판정만 바꾸며, 19%가
   사진 · 그래픽 위다. 채택하려면 이미지 요소 겹침 규칙(배경 경계 비율 같은 근사 또는 다른 근거)과 높이 확장 한도 · 간격(측정 오차 이상)이 필요하다.
   이번 값(간격 0 · 한도 없음 · 경계 5%)은 후보로도 그대로 쓰지 말 것.
5. **해소될 때만 적용** — 끝내 넘치는 블록에 부분 축소 · 확장을 남기지 않았다(가독성만 해침). 부분 적용 여부는 결정이 필요하다.
6. **측정 환경을 먼저 고정** — 정수화 환경에서는 축소 탐색이 치우친다. 서버 기준 환경에서 같은 실험을 다시 해야 수치를 기준으로 쓸 수 있다.
