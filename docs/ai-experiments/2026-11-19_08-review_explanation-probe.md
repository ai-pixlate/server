# 2026-11-19 ⑧ 번역문 LLM 규제 판정 — 판단 이유(설명) 실측 · 프롬프트 비교

## 1. 질문

- LLM 규제 판정(`translation_review`)이 실제 모델에서 만드는 판단 이유(`reason`)가 문제 표현 · 판정 · 공급 근거와 맞는가. 사용자가 읽고 이해할 수 있는가. 공급되지 않은 규제 이유 · 조문을 만들어내는가.
- 실제 응답이 운영 인계 형식 · BE 채택 전 검증기(`validate_report`)를 통과하는가.
- (2차) 판단 이유 작성 지침만 바꾼 프롬프트가 판정을 바꾸지 않고 판매자가 읽기 쉬운 설명을 내는가.
- 관련: `open-questions.md` #84(실측) · #91(판단 이유 전달), `contract.md` 5.3, `be-handoff.md` 8.13.

- **번역 관찰(검사와 별개)**: 실제 섹션 번역 한 블록(`GS-01_002.sec_1_03` blk_004)에 줄바꿈이 문자 그대로 `\n`으로 들어갔다.

- **판정이 달라졌다.** 판정 규칙 문구는 v3와 같은데 v1 · v3와 다른 쌍이 7개 생겼다 — 주름 세럼 임상 섹션의 수치 블록 3개("-28.54% Reduction" 등)를 주름 개선 위험으로, 미백 바디로션 고객 고민 섹션 3개 블록("brightening lotion" 언급)을 미백 위험으로, SPF 시험 문구 1개를 조건 확인 필요에서 해당 없음으로. 설명 절의 문구 차이나 실행 편차로 판정이 흔들릴 수 있다는 뜻이다(원인은 분리하지 않았다). 고객 고민 섹션은 다른 제품에 대한 고객의 말이라 과잉 경고일 가능성이 있다(에이전트 1차 검수).

### 4.6 사람 검수 — v4 표현 유지 · 출처는 문장 뒤 괄호

사용자 검수(2026-11-19): v4 표현은 그대로 두고 문장 뒤 괄호에 조문(출처 성격)을 넣는 것이 좋다. 모델이 조문을 쓰게 하지 않고, 판정이 근거로 단 evidence의 값을 코드에서 붙이는 방식으로 화면 예시를 만들었다(모델 재호출 없음, 공유 시트 "화면 예시 A · B" 열): A = "설명 (201(g)(1))" · B = "설명 (출처: FDA 경고 서한 201(g)(1))". 이 방식은 모델이 조문을 지어내거나 잘못 표기할 여지가 없고, v3의 조문 표기 실패도 생기지 않는다.

예시 B 정정(2026-11-20):

- B의 출처 이름은 사전 값이 아니다. 실험 스크립트가 근거 종류(`source_type`, "Warning Letter" · "OTC 모노그래프")를 대응표로 "FDA 경고 서한" · "FDA OTC 모노그래프"로 바꾼 임의 표기이고, 근거 종류는 문서 이름도 아니다. 사전 근거의 문서 이름(`document`)은 규제사전 xlsx에 열이 없어 비어 있다.
- 예시 A · B의 근거는 사전의 대표 근거(`is_primary`)가 아니라 판정이 단 evidence 중 첫 번째에서 골랐다. 실제 표시는 기존 규칙대로 대표 근거에서 고른다.
- 그래서 예시 B는 표기로 수용하지 않는다(사용자 2026-11-20). 출처를 밝히는 의도는 B가 맞다. OI-58 구분(`basisArticle` = 조문 식별자만, `verdict_basis` = 사람이 읽는 근거 요약 + 링크)을 따라 출처 이름은 `verdict_basis`에 싣는 안으로 미합의 제안 `be-handoff.md` 8.13 E4에 반영했다 — 사전 문서 이름 채우기 · `verdict_basis` 추가 · FE 괄호 표시 변경이 필요하다.
- **확정(사용자 2026-11-20): 지금은 괄호에 출처를 넣지 않는다.** 화면에는 v4 설명만 보인다. 출처는 API 문서가 수정된 뒤에 넣는다.

### 4.7 판정 차이 원인 — 같은 조건 반복(v1 · v3 · v4 × 4회)

v4에서 v1과 판정이 달라진 7쌍이 있는 3섹션만 세 프롬프트를 같은 조건(쌍 상한 40 · 시간 제한 180초)으로 4회씩 다시 돌렸다(`runs/…/variance/`, 36회, 저장 보고 모두 `validate_report` 통과).

| 쌍 | v1 | v3 | v4 |
|---|---|---|---|
| 주름 세럼 임상 — 수치 블록 3개("-28.54% Reduction" 등) × 주름 개선 | 해당 없음 3 · 위험 1 (블록마다 같음) | 해당 없음 2 · 위험 2 | 해당 없음 2 · 위험 2 |
| 주름 세럼 임상 — 주름 개선 문구 5개 | 위험 4 | 위험 4 | 위험 4 |
| 미백 바디로션 고객 고민 — "brightening lotion" 언급 3개 × 미백 | 해당 없음 1(성공 1회) | 성공 0회 | 해당 없음 1 · 위험 1 |
| 선크림 SPF 표기 · 시험 문구 × SPF 수치 | 판단 불가 4 | 판단 불가 2 | 판단 불가 3 |

- **판정 차이의 원인은 프롬프트 문구가 아니라 실행마다의 흔들림이다.** 같은 프롬프트 안에서도 수치 블록 · 고객 고민 문장은 판정이 갈렸고, 세 프롬프트의 빈도는 비슷하다(4회 표본이라 비율 차이는 해석하지 않는다). 앞서 v4에서만 SPF 시험 문구가 해당 없음이 된 것도 반복에서는 다시 나오지 않았다(3회 모두 판단 불가). 분명한 주장 문구(주름 개선 5개 · SPF 50+)는 세 프롬프트 모두 매번 같았다.
- 흔들린 쌍은 판단이 갈릴 만한 경계 사례다: 주장 문구 옆의 수치 결과 블록, 다른 제품에 대한 고객의 말 속 언급. 이런 문맥을 어떻게 볼지는 판정 규칙(계약 D12 — 부정 · 인용 · 가정은 문맥 단서이며 결론 규칙이 아니다)의 정책 사안이다.
- **응답 잘림의 원인은 사고 토큰이다.** 잘린 호출은 사고 토큰이 13,564~15,728로 출력 상한 16,384의 대부분을 썼고, 실제 답 길이는 642~2,805토큰이었다. 완료 호출의 답은 1,090~4,209토큰. 쌍 상한을 40으로 낮춰도 30쌍 한 분할 섹션(미백 고객 고민)이 12회 중 9회 잘렸다 — 쌍 수가 아니라 판단이 어려운 문맥에서 사고가 길어지는 문제다. 사고 토큰 상한 설정 또는 출력 상한 조정이 필요하다(설정 · 코드 변경, 사용자 확정 사안).

### 4.8 응답 잘림 수정 — 사고 토큰 상한(`translation_review.thinking_budget`)

코드에 사고 토큰 상한 키를 추가했다(기본 -1 = 설정 안 함, 이전 동작 · 요청 지문 그대로). 값은 override로만 비교했다. 프롬프트는 v4.

| 조건(쌍 상한 · 시간 제한) | 사고 상한 | 실행 | 결과 | 사고 토큰 | 호출당 총토큰 최대 |
|---|---|---|---|---|---|
| 40 · 180초, 3섹션 | 없음(v4, 4.5 · 4.7) | 32 | 잘림 다수(미백 고객 고민 12회 중 9회 등) | 최대 15,728 | 21,305 |
| 40 · 180초, 3섹션 | 6,144 | 8 | 잘림 1 · 시간 초과 1 | 11,556~15,727(상한을 넘김) | 21,305 |
| 40 · 180초, 3섹션 | 2,048 | 8 | 모두 완료 | 0 | 9,387 |
| 120 · 60초(기본), 전체 10섹션 | 2,048 | 20 | 잘림 0 · 시간 초과 4(100쌍 안팎을 한 번에 판정한 큰 섹션) | 0 | 15,213 |
| **40 · 60초(기본), 실제 7섹션** | **2,048** | 14 | **잘림 0 · 시간 초과 0** · 위치 특정 실패 1 | 0 | 9,722 |

- 이 모델(`gemini-3.8-flash`)은 사고 상한을 정확한 제한으로 지키지 않는다 — 2,048은 모든 호출에서 사고 0(사실상 끔), 6,144는 상한을 넘겨 다시 잘렸다.
- 사고를 끈 결과 분명한 주장(주름 개선 · 모공 · SPF 표기)의 판정은 그대로였고, 달라진 쌍은 4.7의 경계 사례(수치 블록 · 고객 고민)뿐이다. 설명 형식 점검(영어 · 조문 0)도 v4와 같다. 판정 품질의 일반화는 이 표본으로 하지 않는다.
- 남은 실패 1건은 긴 블록에서 위치 발췌(anchor)를 번역문과 글자 그대로 맞추지 못한 응답 검증 실패다(#84 반복 위치 한계와 같은 종류, retryable=true — 재시도 대상).
- 사고 토큰 수 상한은 이 모델이 지키지 않아, 사용자 결정(2026-11-19 — "많이 생각할 작업이 아니다")에 따라 **사고 단계 키 `translation_review.thinking_level`**(default · minimal · low · medium · high, 기본 default = 설정 안 함)로 바꿨다. 위 표의 상한 실험은 그 전 키(`thinking_budget`, 삭제)로 한 것이다.

| 조건 | 실행 | 결과 | 사고 토큰 | 호출당 총토큰 최대 |
|---|---|---|---|---|
| `thinking_level=low` · 쌍 40 · 60초(기본), 전체 10섹션 × 2 | 20(호출 46) | **잘림 0 · 시간 초과 0** · 위치 특정 실패 1(retryable) | 46호출 모두 0 | 9,639 |

- low에서도 이 표본에서는 모델이 사고를 쓰지 않았다(단계 설정이라 더 어려운 입력에서는 조금 쓸 수 있다 — 확인하지 않음). v4(사고 기본)와 판정이 다른 쌍은 4.7의 경계 사례(수치 블록 · 고객 고민 · SPF 시험 문구)뿐이고, 설명 형식 점검도 v4와 같다(영어 · 조문 0, 문장 틀 미준수 3).

## 5. 판단

보류 — 이 표본의 실행과 에이전트 1차 검수에서 판단 이유가 판정 · 문제 표현 · 공급 근거와 어긋난 사례와 공급되지 않은 조문 인용은 발견하지 못했다. 판정 정확도 · 안정성은 이 표본으로 판단하지 않는다.

- 판단 이유 생성은 유지한다. 사용자 표시 문장으로 쓸지와 형식은 BE · FE 합의 대상이다(`be-handoff.md` 8.13).
- v2는 **기각** — 사람 검수에서 영어 표현 인용이 맞지 않다고 봤다. 어투만 v3로 이어 간다.
- v3는 **기각** — 사용자가 조문을 빼기로 정했다(조문 표기로 시도 실패 · 법령 이름 없는 조문 번호).
- v4는 **표현 채택(사람 검수 2026-11-19), 운영 반영은 보류** — 설명 형식은 사용자가 승인했다. 출처 괄호는 지금 넣지 않고 API 문서 수정 뒤에 코드에서 붙인다(4.6, 확정 2026-11-20). v1과 7쌍 달라진 판정은 실행마다의 흔들림으로 확인했다(4.7) — v4 채택을 막는 사유가 아니다. 경계 사례의 판정 흔들림과 사고 토큰으로 인한 응답 잘림은 프롬프트 설명 절과 별개의 후속 과제다. 채택하면 `pipeline/prompts/translation_review.md`에 반영하고 프롬프트 SHA가 바뀐다(LLM 의미 입력 키 변경).
- 관찰된 위험(합의 · 후속 실측 대상): ① 출력 상한 응답 잘림 40회 중 11회 · 60초 시간 제한 4회 중 2회 실패 — 연결하면 「⚠ 검사하지 못했습니다」로 끝나 설명이 전달되지 않는다. 출력 상한 · 분할 크기 · 시간 제한은 config 기본값(사용자 확정 사안)과 BE 실행 정책 사안이다. ② 부정형 문장에서 같은 입력의 판정이 갈렸다(1차). ③ 같은 위치에 서로 다른 항목의 경고가 두 개 생길 수 있다. ④ 단정형 이유가 나올 수 있다(v1). ⑤ v1 설명에 입력 내부 참조(`r2`)가 노출될 수 있다.
