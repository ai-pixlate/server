# GS-03 Windows 실행 안정화 비과금 검증 (2026-11-27)

## 1. 질문

PR #161의 `d983c00` 이후 `forrtl: error (200): program aborting due to window-CLOSE event` 중단을 조사하고, Codex/부모 터미널 종료와 실험 프로세스의 수명을 분리할 수 있는지 검증한다. 제품 `bfa3b700` 로직·모델·프롬프트는 변경하지 않는다.

## 2. 표본과 근거

- 중단 회차: `.cache/gs03-supplement-20261127-r3-job06` (원본 보존).
- 읽기 전용 DB: `px_baseline_gs03_supplement_20261126_r3_recovery2`, Task 265 / Block 232.
- 새 조사 증거: 저장소 루트 `.cache/gs03-windows-stability-20261127` (로컬 전용, Git 미포함).
- `readonly-task265.json`, `legacy-detached-reproduction/`, 각 통합 테스트의 `verification.json`, `supervisor.jsonl`, `process-logs/`, `task-definition.xml`.
- 고정 Python 3.12 가상환경의 torch 2.7.1+cu118, paddle 3.3.1을 CPU로 로딩한 합성 작업 및 실제 multiprocessing spawn. 모델 가중치·추론·DB 변경·API 요청 없음.

## 3. 조건과 구현

기존 `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` 실행은 실제 가상환경 Python 자식의 콘솔 독립성을 보장하지 않았다. 새 실제 실행은 `gs03_scheduled` → Windows Task Scheduler → base `pythonw` 감독자 → 고정 가상환경 `pythonw` 작업 → spawn 자식으로 시작한다. 스케줄러는 현재 로그인 사용자의 InteractiveToken/최소 권한으로 실행하고 암호를 저장하지 않는다.

- 예약 트리거·자동 재시작 없음. 같은 요청의 중복 실행은 배타 claim으로 차단한다. 이미 시작한 실험은 기존 검증에서도 거부한다.
- 콘솔 없는 Python 실행과 프로세스별 stdout/stderr(네이티브 표준 핸들 포함), PID/PPID, 시작·종료 기록을 사용한다. 관찰한 자손은 OS 핸들을 유지해 실제 종료 코드를 수집한다. 짧게 생성·종료되어 폴링에 잡히지 않은 프로세스까지 완전 추적했다고 주장하지 않는다.
- 종료 이벤트를 무시하는 handler는 설치하지 않는다. 기존 `gs03_launch --detach`는 거부한다. 과거 helper는 재현용으로만 남긴다.
- Task Scheduler는 Codex 터미널의 환경 변수를 자동 상속하지 않는다. 로컬 비밀 JSON을 `--environment-file`로 지정할 수 있고, 실제 작업 시작 전 `GEMINI_API_KEY` 존재를 검사한다. 값은 요청/로그/Git에 기록하지 않는다. 파일은 접근 제한된 로컬 경로에 보관해야 한다.
- 범위: 부모 앱·터미널 종료에 대한 독립성. 사용자 로그아웃·재부팅·전원 종료·OS의 작업 강제 종료까지 생존을 보장하지 않는다. 실험 중 로그인과 깨어 있는 전원을 유지해야 한다.

Microsoft 근거: [프로세스 생성 플래그](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags), [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [CTRL_CLOSE_SIGNAL](https://learn.microsoft.com/en-us/windows/console/ctrl-close-signal), [Task Scheduler 설정](https://learn.microsoft.com/en-us/windows/win32/taskschd/tasksettings).

## 4. 결과

### 원인 확인 수준

- 과거 launch 기록 PID 1320과 실제 DB lease owner PID 37700은 다르다. 과거 stderr에는 PID와 OS 종료 코드가 없어, 어느 PID가 `forrtl`을 출력했는지와 이벤트 발신자는 확정할 수 없다.
- 기존 방식 재현에서 wrapper 13232 → 실제 worker 40548 → spawn 25180을 확인했다. worker/child가 같은 **0이 아닌 콘솔 HWND**를 가졌고 Job Object에 속했다. 따라서 기존 분리 방식의 한계는 실제로 확인했다.
- 그 합성 작업에 WM_CLOSE를 보냈지만 과거 `forrtl` 오류는 재현되지 않았고 완료했다. 원래 중단의 완전한 재현이나 특정 라이브러리의 결함 확정으로 해석하지 않는다.
- 당시 01:43~01:46 UTC Windows Application/System 이벤트에는 해당 기록이 없다. Security 로그 접근은 거부됐고 Sysmon 채널은 없으며 TaskScheduler Operational은 비활성이다. 기록 부재를 정상 종료의 증거로 쓰지 않는다.

### 실제 Windows 통합 테스트

판정: 부모 종료가 자식 완료보다 먼저 발생하고, 작업·spawn 자식은 무콘솔 상태에서 완료하며 로그 및 OS 종료 코드 0, 감독자 성공, 스케줄러 LastTaskResult 0을 모두 만족해야 통과한다.

| 부모 종료 방식 | 최신 검증 증거 디렉터리 | 결과 |

## 5. 판단과 다음 실행

실행 환경 개선은 위 부모 종료 시험 범위에서 채택한다. 실제 GS-03 모델 작업을 실행한 검증은 아니다.

Task 265의 동일 attempt 재개는 불가하다. 현재 제품은 pending task만 acquire하며, 만료 running task에 인계 자료가 없으면 정상 recovery에서도 실패로 처리한다. retry 2/2여서 자동 재시도나 JOB-06 추가 시도 대상이 아니다. 이번 조사에서는 recovery sweep, JOB-07, lease 해제 또는 상태 변경을 실행하지 않았다.

다음 최소 후보는 **새 격리 복제본에서 공식 JOB-07로 N4 중단/N3 복귀 후 SEC-04로 새로운 하류 실행**이다. v1.0.1 `app/routers/jobs.py:abort_job`, `app/flows/downstream.py:proceed`에서 지원하는 경로다. 기존 N2 입력을 유지할 수 있지만 `_clear_previous`가 하류 번역·인페인트·렌더 파생값을 지우므로 Block 232 한 번만 재시도하는 범위가 아니다. 복제본의 N4 전체 및 이후 N5/N6를 다시 수행하는 **별도 실험**으로 취급해야 한다. 기존 task 재시도 수를 초기화하지 않는다.

실행 전 필요한 사항:

1. 새 복제본의 공식 JOB-07→SEC-04 경로, DB·객체·예산 승계 및 예상 호출량을 비과금으로 검증한다. 현재는 코드 경로 확인까지만 완료했다.
2. 누적 164회/$10.25462925와 요청 164 미확정 예약을 유지해 호출·금액 상한 내 가능 여부를 산정한다.
3. 새 N4 전체 실행과 후속 단계의 유료 범위를 별도로 승인받는다. 기존 단일 JOB-06 승인으로 실행하지 않는다.
4. 승인 후에만 스케줄러 경로로 시작한다. 현재 중단 회차를 새 실행기에 넣거나 claim 파일을 삭제하지 않는다.

실제 실행 형식(미실행): 고정 가상환경 Python으로 `-B -m tools.baseline.gs03_scheduled <새 준비 회차> --url-file <전용 DB 비밀 파일> --environment-file <로컬 환경 JSON> --execute-models`. 이 진입점은 현재 준비된 recovery manifest의 기존 검증을 재사용하며, 위 새 JOB-07 실험은 별도 준비·검증 후 연결해야 한다. 상태는 `windows_task.ps1 -Request <scheduled-request.json> -Action status` 및 프로세스별 로그로 확인한다. 감독자 완료는 제품 산출물 완성을 대체하지 않는다.

## 6. 반영

PR #161 실행 도구와 비과금 회귀 테스트만 수정. 제품 코드, Baseline·원본 r3·중단 JOB-06 DB/증거, 공식 평가 결과 변경 없음. 추가 모델 요청·생성·유료 실행·병합 없음.

### 회귀 검증 재현

- 고정 가상환경에서 `python -X utf8 -B -m unittest discover -s tests -p "test_baseline*.py"`: 182개 중 179개 통과, 실제 Windows opt-in 3개 건너뜀 (10.734초).
- 실제 부모 종료 시험: `PIXLATE_WINDOWS_LIVE_TESTS=1`, `PIXLATE_WINDOWS_PROBE_ROOT=<새 로컬 증거 폴더>`를 지정하고 `python -X utf8 -B -m unittest discover -s tests -p test_baseline_windows_service.py -v`. Task Scheduler 접근 가능한 Windows 로그인 세션에서만 실행한다. 테스트는 자체 생성한 부모 프로세스/Job Object만 종료하며 기존 실험 프로세스를 대상으로 삼지 않는다.
