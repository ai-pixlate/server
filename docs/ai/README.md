## 2. 우선순위 — 충돌 시

상위 정본 사이에 전역 서열은 없다. **사안의 소유 문서가 이긴다.** [계약 0장]

| 사안 | 상위 정본 | 레포 문서 |
|---|---|---|
| 서비스 흐름 · 설계 원칙 · MVP 범위 | 개발계획 v3.6 | `pipeline.md` |
| 모델 산출 값 · 함수 경계 · JSON 구조 · 좌표계 · 계산 규칙 | 스키마 계약 v3.5 | `contract.md` |
| 컬럼 타입 · 제약 · 인덱스 | BE 정본 ERD | (`db-map.md`는 이름 대응만) |
| 채택 기술의 검증 근거 · 파라미터 실측 근거 | PoC 요약 | `pipeline.md` 3·4·7절 |

- PoC 요약은 상위 계약에 없는 **구현 근거·검증 근거**로 쓴다. 흐름·계약을 PoC로 뒤집지 않는다.
- 에이전트는 별도 PoC 레포를 직접 구현 근거로 사용하지 않는다. PoC 결과는 `docs/ai` 정본 문서에 반영된 내용만 따른다. `[PoC n장]` 태그는 근거 추적용이다.
- 레포 문서가 소유 상위 정본과 어긋나면 상위 정본이 우선하고 **레포 문서를 고친다.** 상위 정본을 고쳐야 할 사안은 `open-questions.md` 3절에 올린다.
- 문서에 없는 것은 코드에서 정하지 않는다. `open-questions.md`에 항목을 추가하고 멈춘다.

**BE 통합 추가 합의(2026-10-06~07)**: 사용자가 전달하고 확정한 BE·AI 합의는 [통합 결정 기록](integration-decisions.md)의 D1~D11로 추적한다. 이번에 승인된 범위의 소유 문서에 `[통합 Dn]`을 붙여 반영하며 기존 상위 계약에 원래 있던 문장으로 표시하지 않는다. 상위 원문 개정·DB/API 반영·운영 적용이 끝났다는 뜻은 아니다. PM 최종 결정은 D9에, ⑧ 용어집 선별 사용자 결정(2026-10-11)은 D10에, 역할별 스타일 기본값의 사용자 승인(2026-10-12)은 D11에 반영했다 — D11은 별도 PM 회신 기록이 아니다. 구현·자료 확보·회신 작업은 `open-questions.md`에서 추적한다. 이 기록은 2.1의 데이터 전달 자료와 구분한다.

**PM 회신·PRD 한정 사용(2026-10-07)**: D8은 요구사항정의서 v3.5.4의 관련 조항만 방안 확정의 근거로 사용한다. 전체 PRD를 이 폴더의 계약으로 이관하지 않는다. PM 추가 승인·원문 확인·기존 합의 충돌을 구분하고 충돌은 재합의 전 코드에 반영하지 않는다. 출처 시트·조항·셀은 integration-decisions.md D8에 기록한다. 2026-10-08 PM은 v3.5.6 업데이트와 회신 우선 적용을 알렸다. D9는 PR 코멘트에 근거하며 이번에 v3.5.6 원문을 열람한 것은 아니다. BE·AI 기술 합의와 PM 결정을 통합 구현 기준으로 사용한다.

## 3. 표기 규칙

- **출처 태그**: 파이프라인·계약·구현 규칙 문장 끝에 `[개발계획 2.1]` `[계약 3.2]` `[PoC 0장]` `[`pipeline.md` 3절]` 형식. `pipeline.md` `contract.md` `db-map.md`에서 태그 없는 규칙 문장은 넣지 않는다. **예외**: 이 README의 문서 운영 규칙(4절 · 6절)과 `dev.md`(레포 구조 결정) · `status.md`(현황)는 각 문서 자체가 소유하므로 상위 문서 태그 대상이 아니다.
- **전달 자료 태그**: `[설명서 §3]` `[규제사전]` `[현지부적합 00_읽는법]` 형식(2.1). 이 태그가 붙은 문장은 계약 채택 전 자료의 서술이며 확정 규칙이 아니다. 채택되면 계약 태그로 바꾼다.
- **통합 합의 태그**: `[통합 D1]`~`[통합 D11]`은 `integration-decisions.md`의 승인 기록을 가리킨다. 소유 문서의 이번 추가 합의에만 사용한다. `원칙 확정`과 `구현 전 명세`·`PM 검토 대기`를 구분하며 상위 원문의 버전은 임의로 올리지 않는다.
- **상태값**: `확정` 그대로 구현 / `미정` 결정 필요, `open-questions.md`에 있음 / `BE 확인 필요` BE와 합의 후 구현 / `데이터 담당` 데이터 정의 대기. 규칙·값·계약이 정해졌는지를 나타내며 소유 문서에 쓴다.
- **구현 상태**: 코드가 어디까지 됐는지(`미구현` · `통합 전` · `로컬 검증` · `실측 전` · `구현 완료` 등)는 `status.md`에만 쓴다. 다른 문서는 구현 상태를 적지 않고 `status.md`의 해당 단계 행을 가리킨다.
- **자리표시자**: 없음. `{{PROMPTS_DIR}}`는 `pipeline/prompts/`로 치환했다(`dev.md` 2절, 2026-09-20).

## 4. 운영 규칙

### 4.1 파라미터 값

- 값의 정본은 **`pipeline/config/default.toml`**(`dev.md` 2절). `pipeline.md` 3절은 키의 의미 · 결정 상태 · 출처만 적고 값은 적지 않는다. 키는 config와 같아야 한다.
- **실험 중 값 변경은 문서에 반영하지 않는다.** 실행 인자 override(`--set 표.키=값`)로만 바꾼다.
- 사용자가 **"확정"이라고 말할 때만** config 기본값 · `pipeline.md` 3절의 결정 열 · (해당 시) `open-questions.md` 5절을 함께 갱신한다.
- 실험 기록(비교 표 · 시도한 값 · 판단)은 `docs/ai` 밖의 별도 폴더에 남긴다. 폴더는 `docs/ai-experiments/`. 규칙은 그 폴더의 README.md. 정본 폴더에는 확정된 결과만 들어온다.

### 4.2 상위 문서 개정 시

1. 상위 문서의 변경 조항 목록을 받는다.
2. 출처 태그로 영향 문장을 찾는다 — `grep -rn "\[개발계획 2.1\]" docs/ai/`.
3. 해당 문장만 고친다. 태그 없는 문장이 걸리면 "출처 누락"으로 보고한다.
4. 각 파일 머리의 근거 버전을 올린다. `open-questions.md`에서 해결된 항목은 5절로 옮긴다.
5. `contract.md`는 요약본이므로 요약 범위 밖 변경은 무변경 처리하고 그 사실만 기록한다.
6. **상위 문서 1버전 = 1커밋.**

### 4.3 조항 번호 안정성

상위 정본(개발계획 · 스키마 계약)을 개정할 때 **기존 조항 번호를 유지하고 추가 조항은 뒤에 붙인다.** 이 폴더의 출처 태그가 조항 번호에 묶여 있다. 문서 운영 규칙이며 개발계획의 설계 원칙이 아니다. 이 절이 규칙의 소유처다.

### 4.4 이 폴더에 넣지 않는 것

- 개발 전 PoC의 실패 기록 · 판단 경위 · 표본 등급 · 지출 — 별도 PoC 레포에 있다(개발계획 수립용, 개발 중 갱신하지 않음)
- 개발 중 실험 기록 — 4.1의 별도 폴더에 둔다
- 컬럼 타입 · 제약 · 인덱스 — ERD / API 규격 · `SignalCode` — API 소유
- 규제 표 · 정책 데이터 · 용어집의 실제 값 — 데이터 담당
- 프롬프트 원문 — `pipeline/prompts/`에 두고 문서에는 경로만
- 모델 가격 · 속도 실측치, 사람 이름, 키 · 자격증명
- 12월 범위 상세

## 6. 레포 루트 에이전트 지침과의 관계

이 레포는 BE와 공용이다. 루트 `CLAUDE.md` / `AGENTS.md`에는 아래 **한 줄만** 넣는다. AI 파이프라인 작업 규칙은 이 README가 소유하며 루트 파일에 복제하지 않는다.

```markdown
- AI 파이프라인(문서 `docs/ai`, 코드 `pipeline/`) 관련 작업은 시작 전에 `docs/ai/README.md`를 읽고 그 규칙을 따른다.
```

### 6.1 에이전트가 따르는 규칙 — 이 README가 소유

- 작업 시작 전 1.2에서 작업 종류에 맞는 문서만 읽는다. `status.md`는 단계를 구현·수정할 때만 읽고, 6.2의 조건에 맞을 때만 갱신한다.
- 문서 우선순위는 2절에 따른다. 해당 사안의 소유 상위 정본과 충돌하면 그 상위 정본이 우선한다.
- 파라미터 값의 정본은 config 파일이다(4.1). 실험 중 값 변경은 문서에 반영하지 않으며, 사용자가 "확정"이라고 말할 때만 config 기본값과 `pipeline.md` 3절의 결정 열을 함께 갱신한다.
- 문서에 없거나 `미정` · `BE 확인 필요`로 표기된 것은 코드에서 정하지 않는다. `open-questions.md`에 항목을 추가하고 사용자에게 묻는다.
- `pipeline.md` `contract.md` `db-map.md`에 규칙 문장을 추가할 때는 출처 태그를 붙인다(3절). 상위 정본 또는 사용자가 승인한 통합 합의(D1~D11)에 출처가 없는 파이프라인·계약 규칙은 추가하지 않는다.
- 이 규칙은 AI 파이프라인 작업에만 적용된다. BE 작업에는 적용하지 않는다.

### 6.2 `status.md` 갱신 조건

이 절이 `status.md` 갱신 규칙의 소유처다. 다른 문서의 갱신 안내와 다르면 이 절을 따른다.

- **갱신한다**: 단계의 구현 상태가 바뀔 때만 갱신한다. 구현·연결이 끝나 상태가 바뀌었을 때, 남은 큰 과업이 생기거나 끝났을 때, 다음 착수가 바뀌었을 때다. 그 변경을 담은 브랜치에서 함께 고친다.
- **갱신하지 않는다**: 코드 검토 · 질문 답변 · 문서 대조, 실험·실측 중간 결과, 상태가 바뀌지 않는 수정(오타 · 리팩터링 · 주석).
- **결과를 남기는 곳**: 검토 결과는 채팅 또는 PR 코멘트에, 실험·실측 기록은 `docs/ai-experiments/`에, 작업 경위는 커밋 · PR 본문에 남긴다.
- **갱신 범위**: 1절 현황 표의 해당 행과 2절 다음 착수만 고친다. 세션 로그(3절)는 추가하지 않는다.
