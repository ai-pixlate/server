# contract.md — AI 파이프라인 입출력·계산 규칙 (요약본)

> 근거: 개발계획 v3.6 · 스키마 계약 문서 v3.5(2026-09-17)
> 성격: **기존 상위 계약의 요약 + 명시적으로 승인된 통합 추가 합의.** `[계약 n]`은 기존 원문 요약, `[통합 Dn]`은 `integration-decisions.md`의 2026-10-06~07 추가 합의다. 원본 요약의 해석은 원문을 따르며, 추가 합의를 원문에 이미 반영된 것으로 취급하지 않는다. 추가 합의는 원칙 확정·미구현이며 DB/API 상세는 별도 소유 문서에서 정한다.
> 소유 범위: 모델이 산출하는 값 · 함수의 경계 · JSON 내부 구조 · 좌표계 · 제외 조건 · 캐시와 재처리 규칙 [계약 0장]. 서비스 흐름은 `pipeline.md`, 컬럼 타입·제약·인덱스는 BE 정본 ERD, 함수 키↔DB 컬럼 매핑은 `db-map.md`.
> 표기: `BE 확인 필요` — 원본에 "API가 소유"로 적힌 항목. `미정` — 원본에 없거나 "별도 정의"로 남은 항목. 어느 쪽도 값을 여기서 정하지 않는다.
> 함수·API 키와 DB 컬럼 이름은 서로 다를 수 있다. 워커가 임시 식별자를 DB 식별자로 변환해 저장한다. JSON 내부 키는 별도 DB 컬럼을 뜻하지 않는다. [계약 0장]

## 1. 함수 경계

실행 순서는 `pipeline.md` 1절. 여기서는 각 함수·단계가 어느 구간을 담당하는지와 경계만 정한다.

| 함수·단계 | 담당 구간 (`pipeline.md` 번호) | 절 |
|---|---|---|
| `analyze()` | ① 섹션 분해 · ② 텍스트 추출 · ③ 병합·역할 분류 | 1.1 |
| AI 섹션 판정 | ③-1 | 1.2 · 4.1 |
| 정책 적용 | ③-1' | 1.2 · 4.2 |
| 제품 라벨 판정 · 브랜드 로고 제외 | ④ · ⑤ (섹션 확인 이후) | 1.3 · 2.2 · 2.3 |
| 스타일 추출 · 인페인팅 · 번역 | ⑦ · ⑥ · ⑧ (처리 대상 확정 이후, 병렬 가능) | 1.3 · 5장 |
| 재검증 | 검수 중 번역문 수정 시 | 5.1 · 7.2 |

함수 이름은 `analyze()` 외에는 원본 계약에 없다 — 나머지는 단계 이름으로 부른다.

### 1.1 `analyze()` — 초기 분석 [계약 1.2]

수행: 섹션 분해 → 섹션별 OCR → 줄·문단 병합 및 역할 분류.

- LLM 병합 보정은 **추가 병합과 역할 재판정만** 수행하며 블록 분할은 하지 않는다.
- 수행하지 않음: 스타일 추출, AI 섹션 판정, 정책 적용, 제품 라벨 판정, 브랜드 로고 제외.
- `text_block.style`은 초기 분석 시 `NULL`.
- 입력 파일은 워커가 준비한 **로컬 경로**로 전달한다. 함수는 S3에 직접 접근하지 않는다.

출력:

| 단위 | 출력값 |
|---|---|
| 섹션 | `section_key`, `source_image_id`, `section_order`, `top_offset`, `height` — `range`는 외부 필드로 추가하지 않고 `top_offset`·`height`로 구간을 계산한다. 운영 타입·경로는 `dev.md` 3.1 [통합 D3] |
| 텍스트 블록 | `block_key`, 소속 `section_key`, `source_ko`, `source_lines`, `bbox`, `role`, `ocr_confidence` |

순서 관리: 원본 간 `source_image.upload_order` · 원본 내 섹션 `section.section_order` · 섹션 내 블록 `text_block.block_order`.

운영 인계는 `analyze()` → `AnalyzeResult` 버전 1을 유지한다. 워커가 실행 환경의 절대 로컬 경로를 준비하고 검증·업로드·저장을 맡으며 AI는 DB/S3에 직접 접근하지 않는다. 임시 키→DB ID 변환은 BE 책임이고 모르는 키는 저장 실패다. 개발용 Split·DB JSON 버전은 별개이며 호환 규칙 변경은 BE 합의 후 버전에 반영한다. 각 단계 결과·참조 관계를 일관되게 저장하고 부분 저장을 N3 준비 완료로 노출하지 않는다. [통합 D3]

### 1.2 AI 섹션 판정과 정책 적용 [계약 1.3]

- AI 섹션 판정 입력: 섹션 이미지 + 텍스트 블록(+ 필요 시 앞뒤 섹션 텍스트). **텍스트가 없는 섹션도 이미지 기반 판정 대상.**
- AI 섹션 판정 출력: 콘텐츠 특성과 확인 필요 여부(→ 4.1 `content_findings`).
- 정책 적용: 판정 결과 × 정책 데이터 → 유지·제외 권고와 확인 필요 여부(→ 4.2 `section_verdict`).
- 두 단계의 입력과 결과는 구분해 관리한다. **정책 변경만으로 AI 추론을 다시 실행하지 않는다.**
- 정책 적용의 구현 소유자는 **AI 서버**다(사용자 결정 2026-09-28). 정책 계약(허용값 · 매핑)의 담당은 별개로 미정(`open-questions.md` #7). [`open-questions.md` 5절 #6]
- 규제사전 조회에 필요한 상품 규제 분류(`regulatory_class`)는 원본 계약의 ③-1 입력에 없다 — **계약 공백**(10장, `open-questions.md` #47). [설명서 §4]

### 1.3 섹션 확인 이후 [계약 1.1, 1.4]

- 제품 라벨 판정 이후의 처리는 **포함으로 확정된 섹션**에 대해서만 수행한다.
- 라벨 또는 로고로 판정된 블록은 스타일 추출·번역·인페인팅·번역문 조판을 포함한 하류 처리에서 제외한다. 해당 원본 시각 요소는 유지한다.
- 제외 확정 섹션에는 제품 라벨 판정부터 하류 작업을 생성하지 않는다.
- 스타일 추출·인페인팅·번역은 처리 대상 확정 후, 입력이 준비되면 병렬 실행할 수 있다.

## 2. 텍스트 블록 계약 [계약 2장]

| 필드 | 정의 |
|---|---|
| `source_ko` | 병합된 블록의 한국어 원문 |
| `source_lines` | 원시 OCR 영역과 줄 구성 정보를 보존하는 JSON 배열 (2.5) |
| `bbox` | 섹션 로컬 좌표의 원본 블록 영역 `{x,y,w,h}` |
| `role` | `title` `body` `caption` `price` `caution` 중 하나 |
| `ocr_confidence` | 블록을 구성하는 OCR 영역 신뢰도의 **최솟값**. 영역이 없으면 `NULL` |
| `is_product_label` | 제품 용기·패키지에 인쇄된 텍스트 여부 |
| `is_brand_logo` | 브랜드명 전체 일치에 따른 로고 판정 여부 |
| `is_excluded` | DB가 두 판정 플래그의 OR로 자동계산 (2.4) |
| `style` | 처리 대상 블록의 글자색·배경색·글자 크기·정렬. **JSON 키 이름·값 형식·허용값은 미정**(10장) — `pipeline.md`의 `font_color` · `bg_color` · `est_font_px` · `align`은 PoC 산출 키이며 계약값 아님 |
| `trans_1` | 의미와 문맥을 보존한 번역문 |
| `overflow` | 현재 배치 영역의 폭 또는 높이 초과 여부 (6.2) |
| `auto_adjust` | 사용자 배치 영역 조정값 (6.1) |
| `compliance_flags` | 현재 revision에 유효한 확인 필요 신호의 근거 (7.1) |

### 2.1 역할 [계약 2.1]

`role`은 5종(`title` 제목 · `body` 본문 · `caption` 캡션 · `price` 가격 · `caution` 주의문구). NOT NULL, 허용값은 DB CHECK.
제품 라벨 여부는 역할과 독립. **제품명 전용 역할은 정의하지 않는다.**

### 2.2 제품 라벨 판정 [계약 2.2]

- 입력: 텍스트 블록 + 섹션 이미지.
- 제품 용기·패키지에 인쇄된 텍스트 → `is_product_label=true`.
- 라벨로 판정되더라도 원문·좌표·역할 등 분석 결과는 보존한다.

### 2.3 브랜드 로고 제외 [계약 2.3]

`text_block.source_ko` 전체와 `brand.name_ko`, `brand.name_en`을 정규화한 뒤 **완전 일치** 비교.

정규화 순서: ① NFKC → ② 소문자 → ③ 공백·문장부호 제거. 정규화 결과가 빈 문자열인 값은 비교 대상에서 제외.

- 전체 일치 → `is_brand_logo=true`. 비교가 정상 완료되고 불일치 → `false`.
- 부분 문자열 일치는 사용하지 않는다.
- 불일치 자체를 로고 매칭 실패 경고로 취급하지 않는다. OCR 실패는 인식 문제로 다룬다.
- 로고 이미지 매칭·심볼형 로고 인식은 MVP 이후.

### 2.4 미판정과 제외 조건 [계약 2.4]

두 판정 플래그: `NULL` 미판정 / `false` 해당 없음 / `true` 해당. 단, 라벨 true에 따른 로고 NULL은 비교 생략 완료로 해석한다. [계약 2.4] [통합 D1]

`is_excluded`는 자동계산이며 앱이 직접 기록하지 않는다.

```sql
is_product_label OR is_brand_logo
```

| 조건 | `is_excluded` |
|---|---|
| 하나라도 `true` | `true` |
| 둘 다 `false` | `false` |
| `true`가 없고 미판정이 남아 있음 | `NULL` |

**하류 작업 생성 조건 — 모두 만족해야 함:**

1. 섹션 확인 단계가 완료됨 — 작업 진행 상태로 판단. `section.bucket` 기본값만으로 완료를 판단하지 않는다.
2. `section.bucket = 'include'`
3. `text_block.is_excluded IS FALSE`

**통합 완료 조합** — 아래 값은 현재 실행에서 산출했거나 현재 입력에 대해 유효하다고 확인한 경우만 인정한다. 옛 DB 값이 존재하는 것만으로 완료로 보지 않는다. [통합 D1]

| 라벨 | 로고 | 완료·하류 처리 |
|---|---|---|
| true | NULL | 라벨 제외 · ⑤ 생략 완료 |
| false | true | 로고 제외 · ⑤ 완료 |
| false | false | ④⑤ 완료 · 다른 생성 조건을 만족하면 하류 대상 |
| 그 밖 | 그 밖 | 정상 완료로 인정하지 않음. 라벨 NULL은 로고가 boolean이어도 미완료 |

섹션의 모든 블록이 정상 완료 조합이어야 ④⑤ 완료로 인정한다. 블록 0개는 호출 없이 생략 완료다. `is_excluded` 생성식은 위 OR의 3값 논리를 따른다. 현재 0003의 `IS TRUE`식은 일치하지 않으므로 **후속 마이그레이션 반영 전 하류 큐를 생성하지 않는다**. 새 조합·컬럼을 임의로 도입하지 않는다. [통합 D1]

### 2.5 원시 OCR 정보 `source_lines` [계약 2.5]

```json
[
  {
    "line_key": "line_01",
    "text": "원문 예시",
    "bbox": {"x": 10, "y": 20, "w": 120, "h": 24},
    "regions": [
      {
        "region_key": "region_01",
        "text": "원문 예시",
        "score": 0.98,
        "poly": [[10,20],[130,20],[130,44],[10,44]],
        "bbox": {"x": 10, "y": 20, "w": 120, "h": 24}
      }
    ]
  }
]
```

- 모든 좌표는 섹션 로컬. 병합 후에도 원시 영역의 식별자·좌표·신뢰도를 보존한다.
- **인페인팅 대상 판정에는 블록 `ocr_confidence`가 아니라 원시 영역별 `score`를 사용한다.**
- `source_lines[].regions[].score`는 영역별 텍스트 인식 신뢰도(0~1)로 합의했다. 현재 PaddleOCR에서는 `rec_scores[i]`다. 블록 `ocr_confidence`는 구성 영역 score 최솟값(영역이 없으면 NULL)이다. ⑥의 0.5 기준은 유지하되 이번 정의 합의가 임계값 품질 검증을 뜻하지 않는다. 기존 상위 원문 반영은 별도다. [통합 D3]
- 빈 문자열 블록과 기존 role·원시 영역을 보존한다. 빈 블록의 role을 의미 분류에 사용하지 않으며 빈 문자열 블록은 번역·텍스트 조판 대상이 아니다. 블록 0개인 섹션과 구분한다. [통합 D3]

## 3. 섹션과 좌표계 [계약 3장]

### 3.1 좌표 기준

- `section.top_offset` · `section.height`는 소속 원본 이미지 기준.
- `text_block.bbox` · `source_lines` 내부 좌표는 섹션 로컬 기준.
- 원본 이미지 기준 세로 좌표 = `section.top_offset + y`.
- MVP 섹션은 원본 전체 폭을 쓰는 세로 구간.
- 원본이 여러 장이면 각 이미지의 좌표계는 독립. 원본 간 순서는 `source_image.upload_order`.

구간은 `[top_offset, top_offset + height)`이며 `range` 필드를 추가하지 않는다. BE가 `section.bbox`를 원본 기준 `{x: 0, y: top_offset, w: 원본 폭, h: height}`로 파생한다. 블록·줄·원시 영역 좌표는 섹션 로컬 정수 픽셀이다. ④의 정규화 0~1000 `box_2d`는 모델 입력용이며 저장 좌표를 대체하지 않는다. [통합 D3]

### 3.2 OCR 임시 분할

- 4,000px 초과 섹션은 OCR 실행을 위해 임시 분할할 수 있다.
- 임시 분할은 OCR 처리 단위이며 **의미 섹션으로 저장하지 않는다.**
- 타일 좌표는 원래 섹션 로컬 좌표로 복원하고, 중첩 영역의 중복 검출을 정리한 뒤 반환한다.

### 3.3 제외와 최종 배치

- 섹션 제외는 원본 좌표를 변경하지 않는다.
- 최종 출력에서 제외 섹션을 제거하고 포함 섹션을 재배치. 출력 위치·순서는 `deliverable_section.stack_offset` · `order_no`.
- 원본의 모든 섹션이 제외되면 해당 원본은 산출물에서 제외.

## 4. AI 섹션 판정과 정책 결과 [계약 4장]

### 4.1 `section.content_findings` — 정책 적용 전 AI 판정 결과

```json
{
  "schema_version": "1",
  "findings": [
    {
      "finding_key": "finding_01",
      "content_type": "before_after",
      "status": "uncertain",
      "evidence_block_ids": [101, 102],
      "evidence_source": "image_and_text",
      "reason": "비교 이미지가 있으나 전후 비교인지 추가 확인 필요"
    }
  ]
}
```

| 키 | 정의 |
|---|---|
| `schema_version` | JSON 구조 버전 |
| `finding_key` | 판정 결과 안에서 finding을 식별하는 키 |
| `content_type` | 판정 대상 콘텐츠 항목. 필드 존재는 확정, **값 목록·항목별 판정 기준은 미정(별도 정의 예정)**. `before_after`는 구조 설명용 예시 |
| `status` | `present` · `absent` · `uncertain` |
| `evidence_block_ids` | 근거 `text_block.id` 목록. 이미지에만 근거가 있으면 비어 있을 수 있음 |
| `evidence_source` | `image` · `text` · `image_and_text` |
| `reason` | 판정 사유 |

- 함수가 반환하는 임시 `block_key`는 저장 시 DB ID로 변환.
- `content_findings=NULL` = 판정 미완료. **항목 누락을 자동으로 `absent`로 해석하지 않는다.**
- 정책상 유지·제외 결정은 finding에 포함하지 않는다.
- `content_type`과 전달 자료의 사전 항목(현지부적합 8행 · 규제 16행)의 연결은 **미정**이며 LC · RG ID를 값으로 임의 확정하지 않는다(`open-questions.md` #4). 원본 계약에 없던 사전·근거 연결은 4.4·4.5의 추가 합의로 보완한다(#48; 세부 JSON 키는 미정). `NULL`(미완료) · 항목 누락 · `absent` · `uncertain`은 서로 다른 상태다(#45). [계약 4.1] [`open-questions.md` #4 · #45 · #48]

### 4.2 `section_verdict` — 정책 적용 결과

- 사용 필드: `verdict_status`, `verdict_type`, `reason`, `basis_article`, `evidence_url` 등. 허용값과 정책 결과의 매핑은 **정책 계약 소유 — 정책 계약의 담당은 미정**(10장).
- `dictionary_id`는 실제 `expression_dictionary` 항목을 근거로 쓴 경우에만 기록.
- 정책 적용 실행 정보는 `audit_log.detail`에 기록: 적용 정책 식별자·버전 / 입력 finding 스냅샷 / 생성한 `section_verdict.id` 목록 / verdict↔finding 대응.
- `section.original_verdict`는 현재 채택한 분석 실행의 사용자 조정 전 정책 결과다(4.4). 사용자의 최종 포함·제외는 `section.bucket`. [통합 D6]
- 정책 데이터는 버전이 있는 별도 데이터. 정책 변경 시 저장된 finding으로 정책 적용 결과를 다시 계산.
- **전달 자료의 정책 분기 — 계약 채택 전**(`open-questions.md` #7). 규제사전: `allowed` → 판정 행을 만들지 않음 / `conditional` → 포함, 충족해야 할 조건 안내 / `rewritable` → 포함, 완충 표현으로 번역 / `regulated` + 대체 표현 있음 → 포함, 대체 표현으로 번역 / `regulated` + 대체 표현 없음 → 섹션 제외. 현지부적합: 패턴으로 후보를 찾은 뒤 AI가 맥락을 확인하며, `irrelevant` · `needs_fix` 모두 기본 제외이고 사용자에게 제공하는 되살리기 안내가 다르다. 이 분기는 자료의 규칙으로 기록한 것이며 저장소 계약에 채택된 것이 아니다. 한 섹션에 여러 검출이 겹칠 때의 집계(#44)와 `uncertain`의 매핑(#45)은 없다. [설명서 §3 · §4]
- **부분 부적합**: MVP는 제외로 판정된 섹션을 통째로 제외하고 부분 가림은 하지 않는다. 제외 판정에만 적용하며 모든 규제 검출이 제외가 되는 것은 아니다. [`open-questions.md` 5절 #8]

### 4.3 불확실·겹침·실패 및 근거 보존 — 통합 추가 합의

- `uncertain`은 완료된 판단 결과로 보존한다. 불확실성만으로 자동 재시도하거나 present·absent·needs_fix로 바꾸지 않는다. 판정 실패·미완료와 구분한다. [통합 D4]
- 규칙 겹침은 적용 항목과 매칭 근거를 보존한다. 겹침 자체 또는 개발용 `conflict_group`을 위반 확정 배지로 쓰지 않는다. [통합 D4]
- AI 판단 이유, 사전의 사유, 겹침 근거는 분리한다. 대표 사유를 화면에 고르더라도 다른 판정을 지우지 않는다. 각 판정은 대응 finding으로 추적하며 사전 항목은 실제 사용했을 때만 연결한다. 블록·매칭 구간은 근거가 있을 때만 연결하고 이미지 전용 근거에는 만들지 않는다. 근거 종류·설명은 보존한다. [통합 D4]
- 사용자 포함·되살리기는 최종 포함 상태를 변경하고 AI 판정 원본을 변경하지 않는다. uncertain을 absent로 바꾸지 않는다. [통합 D4]
- 저장 위치·보존 단위는 4.4에서 확정했으며 세부 JSON 키·API 형식·대표 사유 선택은 후속 명세다. [통합 D6] uncertain·겹침의 사용자 정책은 4.6에서 확인됐으며 알고리즘·API 상세는 미정이다. [통합 D8] 개발용 잠정 제외 정책을 운영 계약으로 승격하지 않는다. [통합 D4]

### 4.4 판정 저장·스냅샷·재분석 — 통합 추가 합의

**현재 전이**: 현지 실패와 규제/기초 분석 실패를 구분하며 N3는 4.6과 11장의 D9 조건을 따른다. 결과 무결성 오류까지 현지 조회 실패 예외로 허용하지 않는다. [통합 D9]

- finding 6필드는 `section.content_findings.findings[]`에, 정책 판정은 `section_verdict` 한 행에 둔다. AI 이유는 finding.reason, 사전 사유는 section_verdict.reason으로 분리한다. 입력 finding·판정 ID·대응·정책 식별자와 버전·사전 스냅샷·복수 근거·검사 범위는 audit_log.detail에 보존한다. 새 테이블을 만들거나 개발용 결과 전체를 저장 계약으로 승격하지 않는다. [통합 D6]
- 실제 사용한 사전의 external_id와 스냅샷 객체는 필수이며 누락 시 저장 실패·N3 진입 불가다. 원래 없는 조문·URL·대체 표현·source_verdict_status는 NULL이다. 복수 근거와 원본 상태는 실행 스냅샷 배열에 둔다. 이는 AI 입력의 필수값을 임의 보충해도 된다는 뜻이 아니다(9.1). [통합 D5] [통합 D6]
- 정책 판정 행이 없어도 실행 검사 범위·사용한 사전 스냅샷·정책 식별자와 버전을 audit에 남긴다. 생성 판정 ID 목록은 빈 목록일 수 있다. finding의 복수 사전·구간은 audit 대응 배열에 보존하며 단수 컬럼에 억지로 분배하지 않는다. 각 판정의 dictionary_id와 복수 대응의 구체 관계는 구현 전 명세다. [통합 D6]
- 문자 구간은 해당 실행 source_ko의 정규화 전 Unicode 코드 포인트 `[start, end)`이며 `matched_text = source_ko[start:end]`다. 당시 원문·구간·매칭 문구를 스냅샷에 복사한다. 나중에 수정·삭제된 블록으로 재해석하지 않는다. API problemText는 대표 문구 하나이며 전체 매칭 목록이 아니다. 대표 선택·전체 근거 API·화면 인덱스 해석은 미정이다. [통합 D6]
- 초기 분석 실행은 job_async_task의 `task_type=ocr`, `unit_type=job` 행이다. 현재 채택 대상인 실행만 이전 audit 기록·새 finding/판정·현재 실행 연결·완료를 한 트랜잭션에서 반영한다. 취소 또는 오래된 실행의 늦은 결과는 교체하지 못한다. job_async_task는 실행 상태 이력, audit_log는 판정 내용 이력이다. [통합 D6]
- 최초 분석에 유효한 기존 결과가 없고 실패하면 content_findings=NULL이다. 재분석 실패는 기존 finding·판정을 보존하며 이를 이번 실행 성공으로 보지 않는다. 실패를 uncertain으로 바꾸지 않는다. 현지 판정/조회 실패의 N3 진행은 D9를 따른다. [통합 D6] [통합 D9]
- original_verdict는 현재 채택한 분석 실행의 사용자 조정 전 정책 결과다. 포함·되살리기는 bucket·exclusion_reason·excluded_stage만 변경하고 finding 상태·원본 판정을 바꾸지 않는다. 성공한 새 분석을 채택할 때 원본도 교체하고 이전 원본은 audit에 보존한다. JSON 키는 미정이다. [통합 D6]

### 4.5 content_type과 finding 범위 — 범위 확정·구현 연결

- content_type은 검사 대상, status는 present·absent·uncertain, external_id는 사용한 사전 식별자다. 콘텐츠 유형에 금지·허용·제외 결론을 넣지 않으며 패턴 검출의 present를 위반 확정으로 해석하지 않는다. [통합 D7]
- 완료 finding은 4.1의 6필드를 갖는다. finding_key는 분석 실행·섹션 범위에서만 유일하며 재분석의 같은 문자열은 다른 finding이다. image는 빈 evidence_block_ids, image_and_text는 실제 텍스트 근거만 연결한다. AI 임시 블록 키는 BE가 이번 실행 DB ID로 변환한다. [통합 D7]
- 사전 연결은 0개 이상이며 실제 사용한 항목을 모두 추적한다. 이번 통합은 섹션·항목당 finding 1건이며 복수 근거를 연결한다. 문맥별 분리는 이번 범위에서 제외한다. [통합 D9] 여러 사전 항목이 한 유형에 대응할 수 있고 한 항목이 여러 검사에 쓰이면 대응표에 적는다. 대응만으로 finding을 합치거나 복제하지 않는다. 사전 없는 이미지 판단도 유형별 기준이 있어야 한다. [통합 D7]
- 미검사 항목은 finding을 만들지 않으며 실행 검사 범위는 audit에 별도 보존한다. 특정 문구·사전 검사의 absent를 유형 전체의 부재로 확대하지 않는다. 미지원·미검사를 other·absent·uncertain으로 변환하지 않는다. [통합 D7]
- 기준·방법이 준비된 유형만 지원한다. 현지 8 + 규제 검출 1의 제품 범위는 확정됐으며 코드·유형별 정의·사전 대응은 #4 구현 작업에서 연결한다. [통합 D9] 목록 확정 전 BE가 허용값을 만들지 않고 확정 후 목록 밖 값은 content_findings 저장 전에 거절한다. before_after 예시·LC/RG ID·채팅의 22유형 후보를 운영 목록으로 채택하지 않는다. [통합 D7]
- 기존 OpenAPI는 content_type을 노출하지 않으며 별도 API 합의 전 프론트 노출은 하지 않는다. 검사 범위·겹침·대응·버전의 audit 키는 구현 전 명세다. uncertain·겹침의 PM 정책은 4.6으로 갱신하며 판정값 매핑은 미결이다. [통합 D8] [통합 D6] [통합 D7]

### 4.6 PM 정책 확인과 적용 경계

- 현지 부적합 uncertain은 기본 제외·현지 확인 필요 배지·AI 사유 한 줄로 표시하며 원본 상태는 uncertain으로 유지한다. 명시적 확인 없이 진행할 수 있고 사용자가 되살릴 수 있다. 현재 규제 판정은 패턴 매칭으로 uncertain을 산출하지 않는다. 이는 판정 실패를 uncertain으로 바꾸는 규칙이 아니다. [통합 D8]
- 완전 포함은 긴 매칭 유지, 일부 겹침·비겹침은 모두 유지, allowed는 판정 행을 만들지 않으며 자신이 감싼 매칭을 억제한다. 한국어 N3·영어 N5 공통 적용 승인은 PM 회신에 근거한다. 동일 문자열의 regulated/allowed 적재 거부, 금지끼리 동일 구간 유지. 순서·정규화·연쇄 포함·동일 구간 조합은 상세 명세 후 구현한다. [통합 D8]
- 규칙 적용 후 남는 판정은 모두 유지하고 제외형 하나라도 있으면 섹션 제외다. 별도 겹침 안내·확인 절차는 두지 않고 각 판정의 자체 배지를 표시한다. 제외 섹션은 포함형 판정도 전부 표시한다. 기존 problemText 한 행의 대표 문구와 섹션에서 전체 판정 행을 보여주는 것은 별개다. 내부 복수 근거 보존은 유지한다. [통합 D8]
- 섹션 위치·문제 문구·기준·근거·되살리기를 제공한다. 규제는 조문과 링크, 현지는 사전 항목명·사전 판단 근거·AI 사유를 구분한다. 원문에서 auto_local·auto_local_failed를 확인했으나 OpenAPI enum·배지/판정값 매핑은 별도 반영이다. [통합 D8]
- combination은 OTC 기준으로 검사하고 한계를 알린다. unknown은 화장품 기준이며 N3/N5 작업 단위 검사 기준에 분류 미확인을 표시한다. 미선택은 차단한다. 이는 사용자 입력값을 덮어쓰는 결정이 아니며 적용 기준·기록의 전달 형식은 #47에서 정한다. [통합 D8]
- **초기 실패**: 현지 AI 판정 실패는 제외·판정 실패, 현지 사전 조회 실패는 제외 없음·NULL·검사 불가 안내로 N3를 연다. 규제 사전/공통 묶음 실패는 N2 자동 재시도 후 오류·재시도다. 분해 실패는 원본 전체 대체 섹션으로 진행하되 후속 OCR·병합이 준비돼야 한다. 기초 분석 결과를 만들 수 없으면 자동 재시도 2회 후 오류·재시도·중단. 식별/스냅샷 손상을 조회 실패 예외로 처리하지 않는다. [통합 D9]
- **검사 범위 확정**: 모든 섹션·현지 8항목을 검사하며 신호는 참고만 한다. 섹션·항목당 1건, 복수 근거를 보존한다. 현지 8 + 규제 표현 검출 1의 범위이며 유형 코드/정의는 구현에 연결한다. cultural·규제 의미 추론·문맥별 분리는 이번 제외다. 되살린 실패 섹션은 재판정 없이 하류로 진행한다. [통합 D9]

## 5. 번역과 인페인팅 [계약 5장]

### 5.1 로컬라이징 번역

- 구조: `gemini-3.8-flash + RAG 용어집`.
- 입력 블록은 원본 순서와 섹션 문맥을 유지.
- 검색된 용어는 `glossary.id`, 원문·번역어, `enforcement`와 함께 전달.
- 실제 규제 매핑 데이터·RAG를 반영한 프롬프트는 기술검증 후 확정 — **미정**.
- `trans_1`은 원본 박스 폭에 맞추기 위해 강제로 축약하지 않는다. `char_limit`은 자동 축약 기준으로 쓰지 않는다.
- 미적용 강제 용어는 `compliance_flags`에 근거 기록.
- **번역문 수정 시 현재 문구에 대해 규제 표현·강제 용어 적용 여부를 다시 검증한다.**

**RG-021·RG-022 이번 범위**: 빈칸 템플릿을 사용하지 않고 원문 수치를 그대로 번역한다. N5 조건부 규제 경고에 사전 사유를 표시하며 시스템이 수치를 추정하거나 상품 검증 완료로 표시하지 않는다. 시험값 입력·템플릿 치환·수치 검증은 12월 검토 범위다. [통합 D9]

영어 금지 표현 사전 재대조·강제 용어 검사는 유지한다. 별도의 번역문 LLM 규제 판정은 현행 구현 범위에 추가하지 않으며, AI가 PM의 제외 경위/12월 방식·일정 질문에 회신할 후속 작업이다. 일정 확약은 아니다. [통합 D9]

### 5.2 인페인팅

- 마스크는 **처리 허용 블록에 속한 원시 OCR 영역**에서 생성. 영역별 `score`와 비어 있지 않은 텍스트 조건 적용.
- 제품 라벨·브랜드 로고 블록은 마스크 생성 대상에서 제외. 보호 영역을 침범하지 않도록 마스크 구성.
- 제외 섹션에는 인페인팅 작업을 생성하지 않는다.
- `section.residual_ratio`는 MVP 필수 산출값 아님, `NULL` 허용. 잔존율 측정·마스크 재팽창 재처리는 MVP 이후.
- 타임아웃 등 실행 실패 재시도는 별도 오류 처리 정책(8장).

## 6. 조판·렌더와 레이아웃 조정 [계약 6장]

### 6.1 원본 영역과 조정 영역

`text_block.bbox`는 원본 OCR 영역으로 보존. 사용자 조정 영역은 `text_block.auto_adjust`:

```json
{
  "schema_version": "1",
  "layout_bbox": {"x": 10, "y": 20, "w": 220, "h": 80},
  "updated_by": "user"
}
```

- `layout_bbox`는 섹션 로컬 좌표. 조정값이 없으면 원본 `bbox` 사용, 있으면 미리보기·최종 렌더 모두 같은 값 사용.
- JSON 갱신 시 담당하지 않는 키는 보존.
- MVP 배치 영역 조정은 섹션 내부에서만. 섹션 크기 변경은 포함하지 않는다.

### 6.2 overflow

- 현재 배치 영역에 대한 렌더 결과로 계산. 폭 또는 높이 중 하나라도 초과 → `true`.
- 초기값 `false`를 렌더 완료의 근거로 쓰지 않는다. **완료된 최신 렌더 결과에 대해서만** 표시.
- 조정 후에도 초과하면 검수 상태 유지. 자동 문구 축약은 하지 않는다.

### 6.3 revision

- 번역문 또는 배치 영역이 변경되면 `text_block.revision` 증가.
- 블록 단위 작업은 `job_async_task.revision`에 대상 블록 revision 기록. 완료 시 현재 revision과 다르면 **오래된 결과로 간주해 반영하지 않는다.**
- 여러 블록을 묶어 처리할 때는 블록별 revision을 작업 입력에 보존하고 결과 반영 시 각각 검증.
- `text_block.revision`과 `job_async_task.revision`은 기존 N5 수정 충돌·번역문·배치 계약에 사용하며 N4 실행 또는 재시도 식별자로 사용하지 않는다(11장). [통합 D2]
- 영역 변경 전후는 `audit_log.detail`, 텍스트 수정 기록은 `edit_signal.before_text` · `after_text`.

## 7. 확인 필요 신호와 재검증 [계약 7장]

확인 필요 신호는 저장된 근거를 조합한 API 파생값. **`SignalCode`는 API 소유 — BE 확인 필요.** AI는 근거만 저장한다.

| 신호 | 근거 |
|---|---|
| 규제 확인 필요 | `compliance_flags`, `section_verdict` |
| 강제 용어 미적용 | `compliance_flags` |
| 번역 실패 | 현재 관련 `job_async_task` 상태 |
| 인식 확인 필요 | `source_ko`, OCR 신뢰도 및 분석 경고 |
| 폭·높이 초과 | 최신 렌더의 `overflow` |
| 제품 라벨 판정 | `is_product_label` |
| 섹션 판정 | `section_verdict`, `original_verdict` |

- 관리자용 신호는 사용자 응답에서 제외. `user_edited`는 신호가 아닌 결과 메타(`text_block.block_status` 근거).
- 로고 이미지 매칭 실패·인페인팅 잔존율 신호는 MVP 이후.

### 7.1 `compliance_flags`

```json
[
  {
    "type": "regulatory",
    "producer": "translation_validation",
    "revision": 3,
    "dictionary_id": 31,
    "section_verdict_id": 201,
    "problem_text": "검증 대상 표현",
    "detected_in": "translation",
    "detected_by": "rule"
  },
  {
    "type": "mandatory_term_unapplied",
    "producer": "glossary_validation",
    "revision": 3,
    "glossary_id": 12
  }
]
```

- `type` · `producer` · `revision` 필수. `type`은 API 신호 코드와 대응.
- 근거 ID는 실제 대응 데이터가 있을 때만 기록.
- `detected_in`: `source` | `translation`. `detected_by`: `rule` | `llm`.
- 사유·조문·대체표현을 `section_verdict`에서 조회할 수 있으면 중복 저장하지 않는다.

### 7.2 재검증 규칙

- 재검증 단계는 **자신이 관리하는 항목만 교체**하고 다른 단계의 항목은 보존. 저장 시 현재 revision을 확인해 동시 갱신으로 유실되지 않게 한다.
- 오래된 revision의 신호는 현재 경고로 표시하지 않는다.
- 입력 변경이 해당 검증에 영향을 주지 않으면 유효성 확인 후 현재 revision으로 승계 가능.
- **검증이 필요한데 완료되지 않은 상태는 "문제 없음"으로 표시하지 않는다.**

## 8. 실패 처리 [계약 8장]

초기 분석 함수 오류 반환 형태:

```text
AnalyzeError(code, retryable, message, source_image_id)
```

`retryable`은 워커가 소비하는 함수 출력값. 워커 기록 필드: `job_async_task.error_code` · `error_message` · `status` · `retry_count` · `max_retry`. 재시도는 `retryable` + 오류 코드별 실행 정책 + 남은 허용 횟수를 함께 확인.

| 상황 | 오류 코드 | 재시도 |
|---|---|---|
| 깨진 파일·미지원 포맷 | `IMAGE_OPEN_FAILED` | 불가 |
| OCR 타임아웃·일시 오류 | `OCR_FAILED` | 허용 횟수 내 가능 |
| 텍스트 0개 검출 | 오류 아님 | 해당 없음 |

- 텍스트가 없는 섹션은 빈 `text_blocks`를 반환.
- 원본 전체에서 텍스트가 검출되지 않으면 분석 경고 기록.
- ① 분해 실패는 원본 전체를 한 섹션으로 대체해 후속 처리를 진행한다. 실제 오류/경고 인계는 #25 구현 작업이다. [통합 D9]
- ③ 병합 보정(`llm_assist`)의 LLM 호출·응답 검증 실패도 원본 계약에 없음. 같은 항목이 **미정**(10장, `open-questions.md` #37).
- ③-1 실패는 현지 실패 진행과 규제/공통 묶음 차단을 구분한다. 4.6의 D9 규칙을 적용하며 실패를 uncertain으로 저장하지 않는다. [통합 D9]

현지 실패는 실패로 보존하면서 4.6의 N3 예외를 적용한다. 규제/공통 묶음 실패는 N2 차단이다. 유효한 선행 입력의 실패 단계만 재시도하며 입력 변경 시 영향 단계부터 처리한다. 기술 오류를 uncertain으로 바꾸지 않는다. N2 자동 재시도 2회 외 단계별 시간/횟수는 구현·운영 기준에서 정한다. [통합 D9]

## 9. 캐시와 결과 갱신 [계약 9장]

캐시는 단계별 입력과 실행 설정을 기준으로 관리.

| 상황 | 처리 |
|---|---|
| 섹션 포함·제외 토글 | 분석 결과 보존 |
| 제외 섹션 재포함 | 유효한 결과 재사용, 미실행 하류 단계는 최초 실행 |
| 정책 변경 | AI 섹션 판정 결과 재사용, 정책 결과 재계산 |
| 번역문 수정 | 규제·용어 검증 **및** 렌더 갱신 |
| 배치 영역 수정 | 렌더 갱신 |
| 라벨·로고 판정 변경 | 처리 대상 재계산, 영향받는 스타일·인페인팅·번역·렌더 결과 갱신. 통합에서는 실행 대표 행·현재 시도로 오래된 결과를 차단하며 블록 revision을 실행 ID로 쓰지 않는다. 구체 연결·검증은 11장과 #16·#64의 구현 전 명세 [통합 D2] |
| 입력·모델·프롬프트·용어집·판정 항목 정의 변경 | 관련 단계 캐시 유효성 재판단 |

- 실행에 사용한 모델·프롬프트·용어집·정책 버전 및 캐시 키는 `event_log.payload`에 기록.
- 최종 저장에는 현재 포함 상태·번역문·배치 영역·revision에 대응하는 결과만 사용.

### 9.1 사전 실행 묶음 — 통합 추가 합의

- BE가 분석 실행 시작 시 DB 적재본으로 버전·해시가 고정된 실행 묶음을 하나 만든다. 원본 파일↔DB 정합성은 적재 시 확인하고, AI는 실행 중 최신 DB나 다른 묶음으로 교체·대조하지 않는다. [통합 D5]
- BE가 묶음 생성 시 원본 사전 ID↔DB PK 및 당시 내용을 확인·고정한다. AI는 사전 참조로 원본 ID를 반환한다. ID 없음·묶음 밖 참조·당시 내용 불일치는 임의 연결·근거 ID 제거로 성공 처리하지 않는다. [통합 D5]
- 서비스 판정값과 `source_verdict_status` 원값을 구분하며 원값 누락을 추정 복원하지 않는다. AI 미지원 값은 공급 전에 거부한다. 개발용 필수값을 DB에서 얻지 못하면 임의 생성하지 않는다. [통합 D5]
- 결과는 실행 묶음의 ID·근거로 저장한다. 최신 DB와 달라졌다는 이유로 결과를 거절하거나 새 묶음으로 자동 재실행하지 않는다. 실행 버전·해시·사유·근거 스냅샷은 분석 실행에 보존하고 현재 사전 행으로 과거 문구를 덮지 않는다. [통합 D5]
- 원본 행 삭제 후에도 복사한 근거를 지우지 않는다. 스냅샷 없이 연결만 남거나 식별 관계가 깨지면 저장 실패다. 삭제 후 참조 무결성을 유지할 방법은 미정이며 스냅샷 보존을 FK 보장으로 간주하지 않는다. [통합 D5]
- 공급 항목별 출처·누락 처리, 정책 규칙 공급·버전·해시, 일관된 조회 시점, 대상 행 선정, 묶음 보존 위치·기간, 공급 형식, 스냅샷 JSON 키, 대체 표현 변환은 구현 전 명세다. 판정 스냅샷 위치는 4.4의 audit_log.detail로 보완했다. [통합 D6] 문자열→배열 규칙 확정 전에는 나누지 않으며 확정 후 BE가 묶음 생성 시 한 번 수행한다. AI 실행 중에는 나누지 않는다. PM 보류 정책의 승인이 아니다. [통합 D5]

## 11. 실행·시도·원자적 반영 — 통합 추가 합의

아래 실행 유효성·원자성은 유지하며 N3/N5 전이는 D9의 최종 제품 결정을 적용한다. [통합 D9]

- 초기 분석과 N4 실행은 별개다. N3는 유효한 기초 분석과 규제 검사 및 현지 정상 결과 또는 승인된 실패 안내가 준비된 뒤 연다(4.6). [통합 D3] [통합 D9]
- proceed는 N3에서 받으며 해당 `job` 행 잠금 기준으로 단계·활성 실행 확인, 대표 행(`unit_type=job`)·최초 작업 생성, N4 전환을 한 트랜잭션에서 처리한다. 취소되지 않은 N4 실행의 중복 요청은 새 실행을 만들지 않는다. 구체 API 응답은 별도 명세다. [통합 D1] [통합 D2]
- 개별 작업은 대표 실행을 가리킨다. 실행 연결 컬럼·task_type을 이 문서에서 만들지 않는다. 작업이 현재 유효 시도이고 실행 중이며 대표 실행이 취소되지 않았을 때만 결과·완료를 함께 반영한다. 취소·결과 반영·후속 작업 생성·N5 전환은 같은 대표 행 기준으로 원자적으로 보호한다. [통합 D2]
- 중단은 대표 실행을 cancelled로 만들고 그 실행의 늦은 결과·재시도·후속 큐·N5 전환을 막는다. N4에서 포함 상태를 바꾸려면 중단해 N3로 복귀한 뒤 다시 proceed한다. 과거 유효 산출물 재사용과 늦은 결과 수락은 별개다. [통합 D2]
- 실패한 개별 행은 이력으로 남긴다. 재시도는 같은 대표 실행 아래 새 행으로 만들며 같은 대상·단계의 현재 유효 시도만 집계한다. 한도는 누적하고 같은 실패 작업의 중복 재시도를 막는다. [통합 D2]
- 인페인트 실패는 원본 배경 조판·N5 실패 표시(재시도 버튼 없음), 스타일 실패/측정 불가는 역할 기본값·N5 표시 없음, 미리보기 실패는 원본 표시·실패/재시도 안내와 상한 후 진행이다. 성공분과 실패 이력은 보존한다. [통합 D9]
- N5는 정상 결과 또는 승인된 대체 결과·실패 안내가 준비되면 연다. 번역 일부/복합 실패는 성공분 유지·실패 칸 비움·직접 입력, 번역 대상이 있는데 성공 0건이면 N4 자동 재시도→오류→재시도/중단이다. 대상 없음은 정상 생략이며 빈 문자열은 번역·텍스트 조판 대상이 아니다. [통합 D9]
- 큐 등록 실패 시 N4·대표 행과 대기 작업을 유지해 복구한다. 중복 전달의 중복 실행을 억제하고 결과·후속 생성·상태 전환 효과는 중복되지 않게 한다. 복구 주체·조건·주기, 재시도 횟수, 실패 코드, 유효성 검사와 잠금 상세는 구현 전 명세다. [통합 D2]

### 11.1 검수 확정·출력·중단과 삭제

- N5는 미해결 규제 경고·재검사 실패·제외하지 않은 실행 실패·빈 번역을 확인받고 확정할 수 있다. 빈 번역이나 대체 결과를 계산 성공으로 바꾸지 않는다. N6 저장·완료는 최종 렌더 성공이 필요하며 내보내기 일부 실패는 성공분과 실패 안내를 제공한다. [통합 D9]
- 오류 화면 중단은 N2→N1, N4→N3이며 입력·버킷을 유지한다. 전체 취소는 콘텐츠 삭제 동작이며 중단과 구분한다. [통합 D9]
- 작업이 존재하는 동안 원본·산출물·판정 근거를 보존하고 자동 만료하지 않는다. 전체 취소 시 이미지/문구가 담긴 DB·S3·audit 상세·인계 payload·GPU 자료를 삭제한다. 콘텐츠 없는 행위자·시각·대상 감사 기록만 남기고, 늦은 실행/업로드가 삭제 자료를 다시 남기지 않게 한다. 9장의 일반 보존보다 이 삭제 규칙이 우선한다. [통합 D9]
- 스타일은 측정값과 역할 기본값의 적용값을 분리한다. 기본 글자색·크기·폰트는 AI가 디자인 안을 받아 BE 공유·PM 확인 후 사용한다. 현재 임의 값을 추가하지 않는다. [통합 D9]
