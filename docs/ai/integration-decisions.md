# integration-decisions.md — BE 통합 결정 기록 (색인)

> 성격: **결정 색인.** `[통합 Dn]` 태그가 가리키는 결정의 한 줄 요약과 반영 위치만 둔다. 결정 원문(출처 · 세부 규칙 · 충돌 관리)과 5절 통합 계약 상세는 `archive/integration-decisions-v1-full.md`의 같은 번호에 있다 — 결정은 유효하며, 원문 속 "미구현 · 연결 전" 같은 상태 표현은 작성 당시 기준이다. 단, archive에 수록되지 않은 D12와 D12 보완의 원문은 이 파일 6절에 둔다.
> 출처: AI·BE 통합 채팅에 사용자가 전달한 BE 승인·회신문과 사용자 확정문. D1~D7을 외부 PM의 직접 승인 문서로 취급하지 않는다. D8은 사용자가 전달한 PM 회신과 관련 PRD 조항 확인을, D9는 PM 최종 회신을 근거로 한다. D10 · D11은 사용자 결정 · 승인이다. D12는 사용자 결정(2026-10-12)과 PR #63의 PM 검토 · 사용자 일정 설명(D12 보완, 2026-10-12~13)이다.
> 구현 상태는 `status.md`, 남은 결정은 `open-questions.md`가 소유한다.

## 1. 기록의 적용 범위

이 파일은 결정의 출처와 추적을 소유한다. 실제 흐름은 루트 `README.md`와 `pipeline.md`, 값·경계·계산은 `contract.md`, 필드 대응은 `db-map.md`, 개발 인계는 `dev.md`, 남은 결정은 `open-questions.md`에 둔다. 동일 규칙을 이 파일에서 독립적으로 개정하지 않는다.

기존 `[계약 n]`·`[개발계획 n]`은 기존 상위 문서의 출처다. 이번 추가 합의는 `[통합 D1]`처럼 구분한다. 기존 상위 원문을 확보·개정했다는 뜻이 아니며, 상위 문서 반영은 별도로 추적한다(`open-questions.md` 3절). DB 컬럼·enum·API·오류 코드를 이 기록만으로 추가하지 않는다. 실제 API 규격은 `docs/openapi.yaml`·`docs/README.md`, DB 스키마는 `migrations/versions/`가 소유하며 API 문서 변경은 `feature/api-tracking` 관리 흐름을 따른다.

|---|---|
| 검사 구성 | 규칙 검사 `text_check`(영어 재대조 · 강제 용어, 기존)와 번역문 LLM 규제 판정 `translation_review`(신규, 번역기와 독립된 호출 · 프롬프트)는 독립된 검사다. 결과 소유 단위(producer)는 `translation_validation` · `glossary_validation`(규칙)과 `translation_llm_review`(LLM)로 나눈다. 섹션 단위 시도 · 블록별 결과이며 자동 번역 직후와 N5 수정 뒤 같은 경로를 쓴다. 모델은 설정으로 고르며 번역 모델과 같을 필요가 없다 |
| 불변 | 번역문 · 사용자 수정문을 바꾸거나 자동 교정하지 않는다. LLM이 규칙 경고 · 강제 용어 미적용을 해제하지 않는다. 검사 실패 · 재시도는 번역 재생성으로 이어지지 않는다. 원문 분석의 `section_verdict` · `content_findings` · `original_verdict`를 바꾸지 않는다. #71 대체 표현 구분과 #77 강제 용어 대안 표기는 미결을 유지하며 LLM으로 추정하지 않는다 |
| 검사 항목 | 판정 대상은 적용 분류(`applied_classes`, common 포함)의 regulated · conditional **전체**(문자열 매칭과 무관). allowed는 「적용 분류 안에 같은 표현이 허용된다는 사전 기록」이라는 범위로만 주는 참고 항목이며 판정 대상이 아니고 다른 항목의 위험 · 규칙 경고를 해제하지 않으며 risk의 근거로 쓸 수 없다. 적용 분류 밖 항목은 ID만 기록한다. 세 목록과 공급 스냅샷을 입력 지문 · 근거 이력에 포함한다 |
| 입력 | 대상은 포함 섹션 · 처리 대상(라벨 false · 로고 false) · 비공백 원문 · 비공백 현재 번역문 블록 전체. 대상 밖 섹션 블록은 번역문 없이 라벨 · 로고 값과 함께 문맥으로 준다(이웃 섹션 제외). 라벨 · 로고 값은 BE 공급 계약 후보이며 누락을 false로 추정하지 않는다. 겹치는 사실은 우선순위 enum으로 정하지 않고 각각 준다 |
| 판단 | 주장 존재 `mention`(present · absent, 형식 무관)과 `judgment`(risk · no_risk · undetermined)를 분리한다. 부정 · 인용 · 가정은 문맥 단서일 뿐 결론 규칙이 아니다. undetermined 사유는 `condition_unverifiable` · `insufficient_context` · `insufficient_evidence`. 미확인 상품 조건이 필요한 판단은 undetermined로만 낸다. risk에는 그 항목 자신의 사전 기록 또는 근거 참조가 필수이고, 근거가 부족하면 insufficient_evidence다. present + no_risk는 비해당을 설명하는 공급 근거 참조가 필요하다. 사전 기록만으로 낸 risk는 허용하되 `basis_summary=dictionary_only`로 외부 근거와 구분해 보존하며 법규 위반 확정으로 표시하지 않는다 |
| 위치 · flag | 위치는 quote · anchor로 받아 정규화하지 않은 번역문의 코드 포인트 [start, end)로 대조한다. 특정하지 못하면 응답 실패(반복 위치를 항상 표현하지는 못하는 초기 구현 한계). risk · undetermined는 위치마다 flag 1건, 위치 없는 undetermined는 위치 네 필드 null 1건, no_risk는 flag 없음 |
| 실패 | 모든 (대상 × 검사 항목) 쌍에 유효한 응답이 있으면 completed(개별 undetermined 포함 가능). 분할 하나라도 호출 · 응답 검증에 실패하면 시도 전체 failed이며 부분 채택하지 않는다. 성공 분할은 진단 · 이력으로만 남긴다. 출력 한도로 잘린 응답은 같은 설정 자동 재시도 불가(일시적인 호출 장애와 구분). 최소 분할 단위가 입력 상한을 넘으면 잘라내지 않고 `unsupported_input`. 검사 항목 0개는 범위 0개의 정상 처리이며 안전 확인이 아니다 |
| 유효성 | 결과 유효성은 그 검사에 영향을 주는 전체 입력 지문(대상 · 섹션 문맥 · 고정 묶음 · 모델 · 프롬프트 · 규칙 버전 · 분할 상한)으로 판단한다. 같은 섹션 다른 문장의 변경도 LLM 결과를 stale로 만든다. 고정 묶음을 최신 DB 사전으로 바꾸어 비교하지 않는다 |
| 집계 | 검사 항목에 대해서만 rule(detected · not_detected · not_checked · unavailable) × llm(risk · no_risk · undetermined · unavailable) 두 축을 보존하고 category를 만들지 않는다. detected는 겹침 억제 이후 유효 검출이다. allowed 참고와 강제 용어 결과는 별도 구역에 둔다. 영어 패턴 부재 · #77 unverifiable은 검사 범위 불완전으로 유지한다. `checks_settled`는 처리 종료 여부일 뿐 문제없음 · 확정 허용이 아니다. AI 집계값을 API 경고 코드 · 확정 정책으로 자동 승격하지 않는다 |
| 확정 경합 | 검사 중에도 N5 수정 · 검수를 진행할 수 있고, 검수 확정은 두 검사의 처리 종료를 기다린다(채택한 추천 방향). `checks_settled=false`이면 확정을 거절하고, 검사 채택 · 확정을 같은 job 잠금으로 보호하며, 확정 뒤 늦은 결과를 거절한다. 구체 API 오류 코드 · 응답 필드는 BE가 정한다 |
| 미확정 | 제품 동작(사용자 결정 필요): LLM undetermined의 확인 의무, LLM 실패를 기존 재검사 실패 확인 절차에 연결하는 방식, risk의 표시 등급(`open-questions.md` #81). BE · FE 계약 조정: 신호 코드 · `basis_summary` 표시 · `warningKey` · 검사 상태 API(#82). D9의 재검사 실패 확인 원칙은 유지한다 |

**구현 상태**: AI 구현(`pipeline/stages/translation_review.py` · `pipeline/handoff/review.py` · `check_aggregate.py` · 프롬프트 · 검증기 · 지문 함수, `contract.md` 5.3 · `pipeline.md` 7.8)만 했다. 변경 파일의 바이트 컴파일만 확인했고 테스트 · 실제 모델 호출 · BE 연결 · 통합 시험은 하지 않았다. BE 연결 사항은 `be-handoff.md` 8절이다.

| 구현 · 통합 시점 | 현재는 9월 범위의 1차 통합 · 릴리즈 준비 중이다. PM의 「12월 구현」은 **12월 최종 통합 범위**를 뜻한다(사용자 설명). AI 구현(LLM 판정 포함)은 지금 진행하며 미루거나 삭제하지 않는다. **1차 통합은 규칙 검사(`text_check`)만 연결**하고, LLM 판정(`translation_review`)의 BE 연결은 12월 최종 통합에서 한다. D9-2의 「이번 통합 제외」는 1차 통합 기준으로 유지한다. PR #63의 develop 머지는 1차 릴리즈 이후로 보류한다 |
| 활성 검사 | 어느 검사를 이번 실행에서 돌릴지는 BE가 명시한다(1차 `("rule",)`, 12월 `("rule", "llm")`). 실행 상태 none에서 활성 여부를 추정하지 않으며, 「실행하지 않기로 한 검사」와 「실행해야 하는데 누락된 검사」를 구분한다. 비활성 검사의 과거 결과는 현재 경고로 쓰지 않는다 |

| 검수 확정 | N5 수정 후 검사가 도는 동안 확정 버튼을 비활성으로 두고 서버도 확정을 거절한다. 검사가 끝난 뒤 미해결 규제 경고 · 검사 실패가 남으면 확인을 받고 진행하며 이력을 저장한다(막지 않음, F-CFM-09). 비활성 안내 문구는 화면문구에서 정한다 |
| 결과 표시 | 규칙 · LLM 결과는 같은 등급의 「규제 검증 결과」 한 신호로 보인다. 화면에 규칙/AI 출처 구분이나 불일치 안내를 두지 않으며 내부 근거 · 결과 구분은 유지한다. 사전 기록만 근거인 risk를 법규 위반 확정처럼 표시하지 않는다 |

| 판단 불가 | `condition_unverifiable`은 확인할 조건을 포함한 조건부 경고와 같은 모양으로 보이고, 같은 블록 · 같은 사전 항목의 조건부 경고가 이미 있으면 하나만 보인다. `insufficient_evidence` · `insufficient_context`의 표시는 12월 계획에서 정한다(미결). AI는 이 상태들을 구분해 돌려준다 |
