## 2. 결정 목록

**현재 적용 주의**: D8이 현지 uncertain·겹침·규제 분류의 이전 PM 대기 상태를 갱신한다. D1~D7의 N3 차단/N4 실패 유지·호출 범위·유형 경계는 D8 C1~C4와 함께 읽고, 충돌 지점을 재합의 없이 구현하지 않는다. 이전 기록의 PM 보류 표시는 해당 당시 상태다.


### D1 — 실행 경계와 처리 대상

- N3는 섹션 확인, N5는 검수. 사용자가 보는 진행 경계는 기존 proceed 한 번이며, ④→⑤→⑥⑦⑧은 N4 안에서 수행한다. 포함 섹션이 없으면 진행을 거절하고 proceed 전에 인페인트를 생성하지 않는다.
- proceed에서는 대표 행과 최초 작업만 만든다. ④~⑧ 전체를 미리 만들지 않는다. ④⑤가 유효하게 완료되고 입력이 준비된 뒤 ⑥⑦⑧을 함께 생성하며 서로의 완료를 직렬로 기다리지 않는다.
- ④⑤의 정상 완료는 `(true, NULL)` 생략 제외, `(false, true)` 로고 제외, `(false, false)` 하류 대상 세 조합이다. 라벨 NULL은 로고 값과 무관하게 미완료다. 옛 DB 값만으로 이번 실행의 완료를 판단하지 않는다.
- `is_excluded`는 하나라도 true이면 true, 둘 다 false이면 false, 나머지는 NULL. 기존 0003과의 불일치는 후속 마이그레이션 대상이며 반영 전 하류 큐를 생성하지 않는다.
- N5는 현재 실행의 필수 ⑥⑦⑧ 작업이 모두 성공 또는 정상 생략 완료일 때만 연다. 실패 시 N4·진행 중 상태를 유지하고 실패는 개별 작업에 둔다. 처리 대상 없음은 호출 없이 성공으로 집계한다. 빈 문자열 블록은 번역·텍스트 조판에서 제외하며 블록 0개와 구분한다.
- 반영: `pipeline.md` 1.1, `contract.md` 2.4·11, 루트 `README.md` 작업 흐름. 관련: #63·#64.

### D2 — 실행·시도와 결과 유효성

- 한 proceed를 `unit_type=job`인 대표 작업 행으로 식별하고 개별 작업을 연결한다. 실행·시도 연결 컬럼과 task_type은 미정이다. 블록·작업 revision은 기존 번역문·배치 계약용이며 실행 ID로 쓰지 않는다.
- 최초에도 존재하는 해당 `job` 행을 잠그는 기준으로 단계·활성 실행 확인, 대표 행·최초 작업 생성, N4 전환을 한 트랜잭션에서 처리한다. 채팅의 "작업 행 잠금"은 아직 없는 대표 행만 잠근다는 뜻으로 적용하지 않는다. 동시·중복 proceed로 새 실행을 중복 생성하지 않는다.
- 각 결과 반영·후속 작업 생성·N5 전환 시 대표 실행과 현재 시도의 유효성을 해당 변경과 같은 트랜잭션에서 검사한다. 중단도 같은 대표 행 기준으로 원자적으로 처리한다. 전체 모델 실행을 하나의 장시간 트랜잭션으로 묶는 뜻은 아니다.
- 재시도는 같은 대표 행 아래 새 개별 행을 만들고 이전 실패 행은 이력으로 보존한다. 같은 대상·단계의 현재 유효 시도만 집계하며, 이전 시도의 늦은 결과와 중단된 실행의 재시도·후속 작업·N5 전환을 허용하지 않는다. 한도는 시도 간 누적하고 중복 재시도 생성을 막는다.
- 큐 등록 실패 시 N4·대표 행을 유지하고 대기 행을 복구한다. 중복 전달의 중복 실행을 억제하고 결과 반영·후속 생성·상태 전환 효과는 중복되지 않게 한다. 장애 복구에서 계산 자체가 재수행되지 않는다는 보장은 하지 않는다. 복구 주체·조건·횟수는 구현 전 명세 대상이다.
- 반영: `contract.md` 11, `db-map.md` 3.6, 루트 `README.md`. 관련: #16·#64·#65.

### D3 — 초기 분석 인계

- 경계는 `analyze()`와 `AnalyzeResult` 버전 1. ①②③만 수행한다. 개발용 Split 버전과 DB JSON 버전은 별개이며 호환 규칙 변경은 BE 합의 후 버전에 반영한다.
- BE 워커가 절대 로컬 경로로 호출하고 검증·업로드·저장·임시 키→DB ID 변환을 담당한다. 임시 키는 분석 실행 범위에 묶이며 모르는 키는 저장 실패다. 줄·영역 키의 섹션 내 유일 범위는 유지한다.
- N3는 현재 유효한 초기 분석과 그에 대응하는 ③-1·③-1′ 결과 준비 후 연다. 이 초기 분석 실행은 proceed의 N4 실행과 구분한다. 각 단계 결과·참조를 일관되게 저장하고 부분 저장을 준비 완료로 노출하지 않는다.
- `range`는 추가하지 않는다. 섹션은 원본 전체 폭의 `[top_offset, top_offset + height)`이며 BE가 원본 기준 section.bbox를 파생한다. 블록 좌표는 섹션 로컬 정수 픽셀. ④의 0~1000 좌표는 모델 입력용이다.
- 원시 영역 score는 인식 신뢰도(현재 `rec_scores[i]`, 0~1), 블록 신뢰도는 구성 영역 최솟값이다. 인페인트는 영역 score를 사용한다. 0.5 유지와 임계값 품질 검증은 별개다. 빈 문자열 블록·role은 보존하되 의미 분류와 번역·텍스트 조판에 사용하지 않는다.
- 반영: `contract.md` 1.1·2.5·3·11, `db-map.md`, `dev.md`. 관련: #13·#34·#35·#36.

### D4 — 불확실·겹침·실패와 근거 보존

- `uncertain`은 완료된 판단 결과다. 불확실성만으로 자동 재시도하거나 present·absent·needs_fix로 바꾸지 않는다. 규칙 겹침과 `conflict_group` 자체를 위반 확정 배지로 쓰지 않는다.
- 호출 실패·시간 초과·잘못된 응답은 미완료이며 N3를 열지 않는다. 유효한 선행 결과·입력이 있으면 실패 단계만 재시도하고, 입력·사전·설정이 바뀌면 영향받는 단계부터 처리한다. 무조건 자동 반복하는 뜻은 아니며 재시도 가능 조건·단위·횟수는 미정이다.
- AI 판단 이유·사전 사유·겹침 근거는 분리한다. 모든 판정과 대응 finding을 보존하며 실제 사용한 사전 항목만 연결한다. 블록·매칭 구간은 있을 때 연결하고 이미지 전용 근거에는 만들지 않는다. 근거 종류와 설명을 보존한다.
- 사용자 포함·되살리기는 최종 포함 상태를 바꾸며 AI 판정 원본을 바꾸지 않는다. 화면 대표 사유를 고르더라도 다른 판정을 삭제하지 않는다.
- 반영: `contract.md` 4.3·8, `pipeline.md` 7.3. 관련: #43~#46·#48. 포함·제외·사용자 확인 정책은 PM 대기.

### D5 — 사전 실행 묶음과 이력

2026-10-07 보완: 아래 당시 미정이던 판정 스냅샷 저장 위치는 D6에서 audit_log.detail로 확정했다. 실행 묶음 전체 보존 위치·기간과 JSON 키는 여전히 미정이다.

- BE가 분석 실행 시작 시 DB 적재본으로 고정 묶음을 하나 만든다. AI는 실행 중 최신 DB나 같은 원본으로 만든 다른 묶음을 읽어 교체·대조하지 않는다. 원본과 DB 적재의 정합성은 적재 시 검증한다.
- 원본 ID→DB PK와 당시 내용의 대응은 BE가 묶음 생성 시 고정한다. 사전 참조로 AI는 RG·LC 원본 ID를 반환한다. ID 없음·묶음 밖 ID·당시 내용 불일치는 다른 행에 붙이거나 근거 ID를 비워 성공 처리하지 않는다.
- 서비스 판정값과 `source_verdict_status`의 원값을 구분하고 원값 누락을 추정 복원하지 않는다. AI 미지원 값은 공급 전에 거부한다. DB 적재 허용과 AI 공급 가능은 별개다.
- 결과는 실행 묶음의 ID·근거로 저장한다. 최신 DB와 달라졌다는 이유로 거절하거나 새 묶음으로 자동 재실행하지 않는다. 실행 버전·해시·사유·근거는 분석 실행에 보존하며 현재 행 조회로 과거 문구를 바꾸지 않는다.
- 이미 복사한 스냅샷은 원본 행 삭제 후에도 보존한다. 스냅샷 없이 연결만 있거나 식별 관계가 깨진 경우는 저장 실패다. 삭제 후 필수 FK를 보존하는 구체 방식은 미정이며, 임의 연결·근거 ID 제거로 성공 처리하지 않는다.
- 현재 AI 개발용 필수값을 DB에서 얻지 못하면 임의로 채우지 않는다. 정책 규칙 공급처·버전·해시, 일관된 조회, 공급 대상 행, 필드별 공급·누락 규칙, 묶음 보존 위치·기간, 스냅샷 위치, 대체 표현 문자열→배열 변환은 구현 전 명세 대상이다. 변환 규칙 확정 후 BE가 묶음 생성 시 한 번 수행하고 AI 실행 중에는 나누지 않는다.
- 반영: `contract.md` 9.1, `db-map.md` 3.7, `dev.md` 3.1. 관련: #3·#49·#71. PM 보류 정책은 승인되지 않았다.

### D6 — 판정·근거 저장과 재분석

- 기록일 2026-10-07. 출처는 사용자가 전달한 BE #48 회신문과 승인한 추천안·후속 content_type 회신문이다. 판정·근거 저장 원칙은 확정, JSON 키·API 상세는 구현 전 명세다.
- finding 6필드는 `section.content_findings.findings[]`, 정책 판정은 `section_verdict`, 대응·검사 범위·실행 당시 사전 스냅샷과 복수 근거는 `audit_log.detail`에 둔다. 새 테이블 없이 기존 위치를 사용하고 개발용 JudgeResult·PolicyResult 전체를 계약으로 승격하지 않는다.
- 초기 분석 실행은 `job_async_task`의 `task_type=ocr`, `unit_type=job` 행으로 식별한다. N4 대표 행을 translate로 확정한 것이 아니며 대표·개별 단계·재시도 task_type은 미정이다.
- 사용한 사전의 external_id와 스냅샷 객체는 필수다. 원래 없는 조문·URL·대체 표현·source_verdict_status는 NULL로 보존한다. 복수 근거와 원본 상태는 실행 스냅샷 배열에 둔다. 판정 행을 만들지 않아도 검사 범위·사용한 사전·정책 식별자와 버전을 audit에 남기며 판정 ID 목록은 비어 있을 수 있다.
- 문자 구간은 당시 source_ko의 정규화 전 Unicode 코드 포인트 `[start, end)`이며 matched_text는 해당 부분 문자열이다. 당시 원문·구간·매칭 문구를 복사하고 나중의 블록 조회로 과거 구간을 해석하지 않는다. problemText는 판정 행의 대표 문구 하나이며 전체 목록이 아니다.
- 현재 채택 대상인 초기 분석 실행만 이전 내용의 audit 기록·새 finding/판정·현재 실행 연결·완료를 한 트랜잭션으로 반영한다. 취소·오래된 실행의 늦은 결과는 반영하지 않는다. 실패는 uncertain이 아니며 N3를 열지 않는다. 최초 분석에 기존 유효 결과가 없으면 content_findings=NULL, 실패한 재분석은 기존 결과를 보존하되 이번 실행 성공으로 보지 않는다.
- original_verdict는 현재 채택한 분석 실행의 사용자 조정 전 정책 결과다. 사용자 포함·되살리기는 bucket·exclusion_reason·excluded_stage만 변경한다. 새 분석이 성공해 채택되면 원본을 교체하고 이전 원본은 audit에 보존한다.
- 반영: `contract.md` 4.4, `db-map.md` 3.2·3.4·3.6·3.7. 관련 #48·#46·#49·#71. 사전 단수 FK와 복수 연결의 상세, JSON 키·API는 미결이다.

### D7 — content_type 의미와 지원 범위

- content_type은 검사 대상이며 finding.status는 present·absent·uncertain이다. 사전 external_id·정책 결론과 분리하고 present를 위반 확정으로 해석하지 않는다. 기존 external_id 자체를 다른 분류 문자열로 바꾸지 않는다.
- 완료 finding은 합의한 6필드를 가진다. finding_key는 그 분석 실행의 그 섹션 안에서만 유일하다. image는 빈 블록 목록, image_and_text는 실제 텍스트 근거만 연결하고 임시 키→이번 실행 DB ID 변환은 BE가 맡는다. 사전 연결은 0개 이상이다.
- 미지원·미검사를 other·absent·uncertain으로 바꾸지 않는다. 검사하지 않은 항목은 finding을 만들지 않고 실행 검사 범위를 별도로 남긴다. 특정 문구·사전 항목의 absent를 유형 전체의 부재로 확대하지 않는다.
- 같은 유형이라도 판단 범위·근거가 다르면 finding_key를 나눈다. 사전 대응만으로 합치거나 복제하지 않는다. 사전 없는 이미지 판단에도 유형의 판정 기준이 필요하다. 개발용 사전 ID content_type과 사전 항목당 finding 1개·근거 합집합은 통합 규칙이 아니다.
- 기준·방법이 준비된 유형만 지원한다. 실제 목록 확정 전 BE가 허용값을 만들지 않고, 확정 후 목록 밖 값은 content_findings 저장 전에 거절한다. before_after 예시와 LC/RG ID는 운영 유형 목록이 아니다. 별도 API 합의 전 프론트에 content_type을 노출하지 않는다.
- 반영: `contract.md` 4.5, `pipeline.md` 7.3, `dev.md` 3.1. #4의 실제 지원 목록·판정 기준·사전 대응표는 미결이다. 채팅의 22유형은 미승인 후보이며 운영 enum·계약값으로 반영하지 않는다.

| 재분석 실패 후 기존 결과가 남음 | 기존 판정 보존과 이번 실패 표시, 현재 채택 실행 식별, 어느 결과로 진행 가능한지 |
| 모든 섹션이 제외됨 | N3 표시와 proceed 거절을 구분 |
| 패턴 신호가 없지만 전 섹션 검사에서는 present | 두 호출 방식의 결과 차이와 미검사 표시, 수용 여부 |
| 같은 현지 항목이 독립된 두 문맥에 나타남 | 한 유형과 복수 finding의 관계, 서로 다른 상태/근거 보존 |
| 한 문구에 사전 두 항목·매칭 여러 개 | finding·판정 행·audit 대응과 억제 전후 근거 추적 |
| 인페인트 실패/렌더 실패/번역 실패 | 단계별 대체 허용 여부, N4/N5 경계, 필수 산출물과 경고를 별도 확인 |
| 취소·재시도·중복 전달 후 늦은 결과 | 현재 유효 실행/시도만 반영, 성공분 보존, 중복 결과·후속 작업 차단 |

### 5.3 남은 초안 작성과 PR 리뷰 순서

1. **C1부터 구체화**: PM이 직접 답한 현지 실패 정책을 실행 완료·진행 조건으로 연결한다. C2·C3을 함께 정리한 뒤 실제 content_type 목록을 확정하고, C4는 단계별 대체 처리 표로 검토한다.
2. **분석·판정·사전 묶음**: 유형·판정 기준·사전 대응, verdict_status/verdict_type·배지·사유 코드 매핑, audit JSON/API, 공급 필드·버전·해시·대체 표현 변환·보존을 작성한다.
3. **하류 산출·검수 묶음**: style 키·단위·NULL, auto_adjust 역할, 번역 입력과 상품별 검증 정보, 렌더 overflow·char_limit, 신호 코드·노출을 작성한다.
4. **실행·운영 묶음**: 대표/개별/재시도 task_type, 연결·현재 시도 집계, 생략 표현, 오류·한도·복구·취소·중복 전달을 작성한다. 구조 초안은 앞 묶음과 병행하되 단계 입출력 확정 후 완료 조건을 맞춘다.
5. **문서 PR 리뷰**: 전체 초안을 한 PR로 제출하고 위 세 묶음 순서로 리뷰한다. 기존 확정 / 새 제안 / BE 작성 필요 / PM·데이터 확인을 표시한다. BE는 동의·구체 대안·보류 사유를 남기고 소유 상세를 보완한다. API 문서 반영은 feature/api-tracking 관리 흐름에 연결한다.

AI는 모델 입출력·판정 능력·산출물 의미와 대표 사례를 작성하고, BE는 저장·API·트랜잭션·작업·복구 상세를 작성한다. 양쪽 경계와 실패 의미는 공동 리뷰한다. 사용자 정책·지원 범위 변경은 PM, 사전 의미·충돌 데이터는 데이터 담당 확인이 필요하다. 이 절은 역할 제안이며 상대 담당의 리뷰 완료를 뜻하지 않는다.

**완료 기준**: 각 항목에 담당, 입출력·저장/API 대응, 필수/NULL/생략/실패 조건과 대표 사례가 있고, 미결 항목의 영향 범위가 명시돼야 한다. 확정된 부분만 소유 계약에 옮기며 코드·마이그레이션 구현은 별도 작업으로 진행한다. 관련 없는 PRD 전체를 옮기지 않는다.
