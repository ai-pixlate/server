## 2. 결정 목록

**현재 적용 주의**: D8이 현지 uncertain·겹침·규제 분류의 이전 PM 대기 상태를 갱신한다. D1~D7의 N3 차단/N4 실패 유지·호출 범위·유형 경계는 D8 C1~C4와 함께 읽고, 충돌 지점을 재합의 없이 구현하지 않는다. 이전 기록의 PM 보류 표시는 해당 당시 상태다.


### D1 — 실행 경계와 처리 대상

- N3는 섹션 확인, N5는 검수. 사용자가 보는 진행 경계는 기존 proceed 한 번이며, ④→⑤→⑥⑦⑧은 N4 안에서 수행한다. 포함 섹션이 없으면 진행을 거절하고 proceed 전에 인페인트를 생성하지 않는다.
- proceed에서는 대표 행과 최초 작업만 만든다. ④~⑧ 전체를 미리 만들지 않는다. ④⑤가 유효하게 완료되고 입력이 준비된 뒤 ⑥⑦⑧을 함께 생성하며 서로의 완료를 직렬로 기다리지 않는다.
- ④⑤의 정상 완료는 `(true, NULL)` 생략 제외, `(false, true)` 로고 제외, `(false, false)` 하류 대상 세 조합이다. 라벨 NULL은 로고 값과 무관하게 미완료다. 옛 DB 값만으로 이번 실행의 완료를 판단하지 않는다.
- `is_excluded`는 하나라도 true이면 true, 둘 다 false이면 false, 나머지는 NULL. 기존 0003과의 불일치는 후속 마이그레이션 대상이며 반영 전 하류 큐를 생성하지 않는다.
- N5는 현재 실행의 필수 ⑥⑦⑧ 작업이 모두 성공 또는 정상 생략 완료일 때만 연다. 실패 시 N4·진행 중 상태를 유지하고 실패는 개별 작업에 둔다. 처리 대상 없음은 호출 없이 성공으로 집계한다. 빈 문자열 블록은 번역·텍스트 조판에서 제외하며 블록 0개와 구분한다.
- 반영: `pipeline.md` 1.1, `contract.md` 2.4·11, 루트 `README.md` 작업 흐름. 관련: #63·#64.

### D2 — 실행·시도와 결과 유효성

- 한 proceed를 `unit_type=job`인 대표 작업 행으로 식별하고 개별 작업을 연결한다. 실행·시도 연결 컬럼과 task_type은 미정이다. 블록·작업 revision은 기존 번역문·배치 계약용이며 실행 ID로 쓰지 않는다.
- 최초에도 존재하는 해당 `job` 행을 잠그는 기준으로 단계·활성 실행 확인, 대표 행·최초 작업 생성, N4 전환을 한 트랜잭션에서 처리한다. 채팅의 "작업 행 잠금"은 아직 없는 대표 행만 잠근다는 뜻으로 적용하지 않는다. 동시·중복 proceed로 새 실행을 중복 생성하지 않는다.
- 각 결과 반영·후속 작업 생성·N5 전환 시 대표 실행과 현재 시도의 유효성을 해당 변경과 같은 트랜잭션에서 검사한다. 중단도 같은 대표 행 기준으로 원자적으로 처리한다. 전체 모델 실행을 하나의 장시간 트랜잭션으로 묶는 뜻은 아니다.
- 재시도는 같은 대표 행 아래 새 개별 행을 만들고 이전 실패 행은 이력으로 보존한다. 같은 대상·단계의 현재 유효 시도만 집계하며, 이전 시도의 늦은 결과와 중단된 실행의 재시도·후속 작업·N5 전환을 허용하지 않는다. 한도는 시도 간 누적하고 중복 재시도 생성을 막는다.
- 큐 등록 실패 시 N4·대표 행을 유지하고 대기 행을 복구한다. 중복 전달의 중복 실행을 억제하고 결과 반영·후속 생성·상태 전환 효과는 중복되지 않게 한다. 장애 복구에서 계산 자체가 재수행되지 않는다는 보장은 하지 않는다. 복구 주체·조건·횟수는 구현 전 명세 대상이다.
- 반영: `contract.md` 11, `db-map.md` 3.6, 루트 `README.md`. 관련: #16·#64·#65.

### D3 — 초기 분석 인계

- 경계는 `analyze()`와 `AnalyzeResult` 버전 1. ①②③만 수행한다. 개발용 Split 버전과 DB JSON 버전은 별개이며 호환 규칙 변경은 BE 합의 후 버전에 반영한다.
- BE 워커가 절대 로컬 경로로 호출하고 검증·업로드·저장·임시 키→DB ID 변환을 담당한다. 임시 키는 분석 실행 범위에 묶이며 모르는 키는 저장 실패다. 줄·영역 키의 섹션 내 유일 범위는 유지한다.
- N3는 현재 유효한 초기 분석과 그에 대응하는 ③-1·③-1′ 결과 준비 후 연다. 이 초기 분석 실행은 proceed의 N4 실행과 구분한다. 각 단계 결과·참조를 일관되게 저장하고 부분 저장을 준비 완료로 노출하지 않는다.
- `range`는 추가하지 않는다. 섹션은 원본 전체 폭의 `[top_offset, top_offset + height)`이며 BE가 원본 기준 section.bbox를 파생한다. 블록 좌표는 섹션 로컬 정수 픽셀. ④의 0~1000 좌표는 모델 입력용이다.
- 원시 영역 score는 인식 신뢰도(현재 `rec_scores[i]`, 0~1), 블록 신뢰도는 구성 영역 최솟값이다. 인페인트는 영역 score를 사용한다. 0.5 유지와 임계값 품질 검증은 별개다. 빈 문자열 블록·role은 보존하되 의미 분류와 번역·텍스트 조판에 사용하지 않는다.
- 반영: `contract.md` 1.1·2.5·3·11, `db-map.md`, `dev.md`. 관련: #13·#34·#35·#36.

### D4 — 불확실·겹침·실패와 근거 보존

- `uncertain`은 완료된 판단 결과다. 불확실성만으로 자동 재시도하거나 present·absent·needs_fix로 바꾸지 않는다. 규칙 겹침과 `conflict_group` 자체를 위반 확정 배지로 쓰지 않는다.
- 호출 실패·시간 초과·잘못된 응답은 미완료이며 N3를 열지 않는다. 유효한 선행 결과·입력이 있으면 실패 단계만 재시도하고, 입력·사전·설정이 바뀌면 영향받는 단계부터 처리한다. 무조건 자동 반복하는 뜻은 아니며 재시도 가능 조건·단위·횟수는 미정이다.
- AI 판단 이유·사전 사유·겹침 근거는 분리한다. 모든 판정과 대응 finding을 보존하며 실제 사용한 사전 항목만 연결한다. 블록·매칭 구간은 있을 때 연결하고 이미지 전용 근거에는 만들지 않는다. 근거 종류와 설명을 보존한다.
- 사용자 포함·되살리기는 최종 포함 상태를 바꾸며 AI 판정 원본을 바꾸지 않는다. 화면 대표 사유를 고르더라도 다른 판정을 삭제하지 않는다.
- 반영: `contract.md` 4.3·8, `pipeline.md` 7.3. 관련: #43~#46·#48. 포함·제외·사용자 확인 정책은 PM 대기.

### D5 — 사전 실행 묶음과 이력

2026-10-07 보완: 아래 당시 미정이던 판정 스냅샷 저장 위치는 D6에서 audit_log.detail로 확정했다. 실행 묶음 전체 보존 위치·기간과 JSON 키는 여전히 미정이다.

- BE가 분석 실행 시작 시 DB 적재본으로 고정 묶음을 하나 만든다. AI는 실행 중 최신 DB나 같은 원본으로 만든 다른 묶음을 읽어 교체·대조하지 않는다. 원본과 DB 적재의 정합성은 적재 시 검증한다.
- 원본 ID→DB PK와 당시 내용의 대응은 BE가 묶음 생성 시 고정한다. 사전 참조로 AI는 RG·LC 원본 ID를 반환한다. ID 없음·묶음 밖 ID·당시 내용 불일치는 다른 행에 붙이거나 근거 ID를 비워 성공 처리하지 않는다.
- 서비스 판정값과 `source_verdict_status`의 원값을 구분하고 원값 누락을 추정 복원하지 않는다. AI 미지원 값은 공급 전에 거부한다. DB 적재 허용과 AI 공급 가능은 별개다.
- 결과는 실행 묶음의 ID·근거로 저장한다. 최신 DB와 달라졌다는 이유로 거절하거나 새 묶음으로 자동 재실행하지 않는다. 실행 버전·해시·사유·근거는 분석 실행에 보존하며 현재 행 조회로 과거 문구를 바꾸지 않는다.
- 이미 복사한 스냅샷은 원본 행 삭제 후에도 보존한다. 스냅샷 없이 연결만 있거나 식별 관계가 깨진 경우는 저장 실패다. 삭제 후 필수 FK를 보존하는 구체 방식은 미정이며, 임의 연결·근거 ID 제거로 성공 처리하지 않는다.
- 현재 AI 개발용 필수값을 DB에서 얻지 못하면 임의로 채우지 않는다. 정책 규칙 공급처·버전·해시, 일관된 조회, 공급 대상 행, 필드별 공급·누락 규칙, 묶음 보존 위치·기간, 스냅샷 위치, 대체 표현 문자열→배열 변환은 구현 전 명세 대상이다. 변환 규칙 확정 후 BE가 묶음 생성 시 한 번 수행하고 AI 실행 중에는 나누지 않는다.
- 반영: `contract.md` 9.1, `db-map.md` 3.7, `dev.md` 3.1. 관련: #3·#49·#71. PM 보류 정책은 승인되지 않았다.

### D6 — 판정·근거 저장과 재분석

- 기록일 2026-10-07. 출처는 사용자가 전달한 BE #48 회신문과 승인한 추천안·후속 content_type 회신문이다. 판정·근거 저장 원칙은 확정, JSON 키·API 상세는 구현 전 명세다.
- finding 6필드는 `section.content_findings.findings[]`, 정책 판정은 `section_verdict`, 대응·검사 범위·실행 당시 사전 스냅샷과 복수 근거는 `audit_log.detail`에 둔다. 새 테이블 없이 기존 위치를 사용하고 개발용 JudgeResult·PolicyResult 전체를 계약으로 승격하지 않는다.
- 초기 분석 실행은 `job_async_task`의 `task_type=ocr`, `unit_type=job` 행으로 식별한다. N4 대표 행을 translate로 확정한 것이 아니며 대표·개별 단계·재시도 task_type은 미정이다.
- 사용한 사전의 external_id와 스냅샷 객체는 필수다. 원래 없는 조문·URL·대체 표현·source_verdict_status는 NULL로 보존한다. 복수 근거와 원본 상태는 실행 스냅샷 배열에 둔다. 판정 행을 만들지 않아도 검사 범위·사용한 사전·정책 식별자와 버전을 audit에 남기며 판정 ID 목록은 비어 있을 수 있다.
- 문자 구간은 당시 source_ko의 정규화 전 Unicode 코드 포인트 `[start, end)`이며 matched_text는 해당 부분 문자열이다. 당시 원문·구간·매칭 문구를 복사하고 나중의 블록 조회로 과거 구간을 해석하지 않는다. problemText는 판정 행의 대표 문구 하나이며 전체 목록이 아니다.
- 현재 채택 대상인 초기 분석 실행만 이전 내용의 audit 기록·새 finding/판정·현재 실행 연결·완료를 한 트랜잭션으로 반영한다. 취소·오래된 실행의 늦은 결과는 반영하지 않는다. 실패는 uncertain이 아니며 N3를 열지 않는다. 최초 분석에 기존 유효 결과가 없으면 content_findings=NULL, 실패한 재분석은 기존 결과를 보존하되 이번 실행 성공으로 보지 않는다.
- original_verdict는 현재 채택한 분석 실행의 사용자 조정 전 정책 결과다. 사용자 포함·되살리기는 bucket·exclusion_reason·excluded_stage만 변경한다. 새 분석이 성공해 채택되면 원본을 교체하고 이전 원본은 audit에 보존한다.
- 반영: `contract.md` 4.4, `db-map.md` 3.2·3.4·3.6·3.7. 관련 #48·#46·#49·#71. 사전 단수 FK와 복수 연결의 상세, JSON 키·API는 미결이다.

### D7 — content_type 의미와 지원 범위

- content_type은 검사 대상이며 finding.status는 present·absent·uncertain이다. 사전 external_id·정책 결론과 분리하고 present를 위반 확정으로 해석하지 않는다. 기존 external_id 자체를 다른 분류 문자열로 바꾸지 않는다.
- 완료 finding은 합의한 6필드를 가진다. finding_key는 그 분석 실행의 그 섹션 안에서만 유일하다. image는 빈 블록 목록, image_and_text는 실제 텍스트 근거만 연결하고 임시 키→이번 실행 DB ID 변환은 BE가 맡는다. 사전 연결은 0개 이상이다.
- 미지원·미검사를 other·absent·uncertain으로 바꾸지 않는다. 검사하지 않은 항목은 finding을 만들지 않고 실행 검사 범위를 별도로 남긴다. 특정 문구·사전 항목의 absent를 유형 전체의 부재로 확대하지 않는다.
- 같은 유형이라도 판단 범위·근거가 다르면 finding_key를 나눈다. 사전 대응만으로 합치거나 복제하지 않는다. 사전 없는 이미지 판단에도 유형의 판정 기준이 필요하다. 개발용 사전 ID content_type과 사전 항목당 finding 1개·근거 합집합은 통합 규칙이 아니다.
- 기준·방법이 준비된 유형만 지원한다. 실제 목록 확정 전 BE가 허용값을 만들지 않고, 확정 후 목록 밖 값은 content_findings 저장 전에 거절한다. before_after 예시와 LC/RG ID는 운영 유형 목록이 아니다. 별도 API 합의 전 프론트에 content_type을 노출하지 않는다.
- 반영: `contract.md` 4.5, `pipeline.md` 7.3, `dev.md` 3.1. #4의 실제 지원 목록·판정 기준·사전 대응표는 미결이다. 채팅의 22유형은 미승인 후보이며 운영 enum·계약값으로 반영하지 않는다.

### 5.3 남은 초안 작성과 PR 리뷰 순서

1. **C1부터 구체화**: PM이 직접 답한 현지 실패 정책을 실행 완료·진행 조건으로 연결한다. C2·C3을 함께 정리한 뒤 실제 content_type 목록을 확정하고, C4는 단계별 대체 처리 표로 검토한다.
2. **분석·판정·사전 묶음**: 유형·판정 기준·사전 대응, verdict_status/verdict_type·배지·사유 코드 매핑, audit JSON/API, 공급 필드·버전·해시·대체 표현 변환·보존을 작성한다.
3. **하류 산출·검수 묶음**: style 키·단위·NULL, auto_adjust 역할, 번역 입력과 상품별 검증 정보, 렌더 overflow·char_limit, 신호 코드·노출을 작성한다.
4. **실행·운영 묶음**: 대표/개별/재시도 task_type, 연결·현재 시도 집계, 생략 표현, 오류·한도·복구·취소·중복 전달을 작성한다. 구조 초안은 앞 묶음과 병행하되 단계 입출력 확정 후 완료 조건을 맞춘다.
5. **문서 PR 리뷰**: 전체 초안을 한 PR로 제출하고 위 세 묶음 순서로 리뷰한다. 기존 확정 / 새 제안 / BE 작성 필요 / PM·데이터 확인을 표시한다. BE는 동의·구체 대안·보류 사유를 남기고 소유 상세를 보완한다. API 문서 반영은 feature/api-tracking 관리 흐름에 연결한다.

AI는 모델 입출력·판정 능력·산출물 의미와 대표 사례를 작성하고, BE는 저장·API·트랜잭션·작업·복구 상세를 작성한다. 양쪽 경계와 실패 의미는 공동 리뷰한다. 사용자 정책·지원 범위 변경은 PM, 사전 의미·충돌 데이터는 데이터 담당 확인이 필요하다. 이 절은 역할 제안이며 상대 담당의 리뷰 완료를 뜻하지 않는다.

**완료 기준**: 각 항목에 담당, 입출력·저장/API 대응, 필수/NULL/생략/실패 조건과 대표 사례가 있고, 미결 항목의 영향 범위가 명시돼야 한다. 확정된 부분만 소유 계약에 옮기며 코드·마이그레이션 구현은 별도 작업으로 진행한다. 관련 없는 PRD 전체를 옮기지 않는다.

#### 재분석·재시도와 proceed 경쟁 처리 제안

1. 재분석 시작 후 기존 판정은 보존하되 현재 입력과의 유효성을 별도로 판단한다. 실패했다는 이유만으로 기존 결과를 새 입력에 유효하다고 간주하지 않는다.
2. 입력·사전·설정이 달라졌거나 유효성을 확인할 수 없으면 이전 결과로 자동 진행하지 않는 안을 추천한다. 입력이 동일하고 이전 실행이 유효하면 실패한 새 시도를 정리한 뒤 기존 실행을 채택 대상으로 유지할 수 있는지 BE가 제안한다. 새 복귀 버튼이나 API를 여기서 요구하지 않는다.
3. 사용자 포함·되살리기와 진행 중 재시도 결과가 서로 덮어쓰지 않도록, N3 전환/proceed 직전에 현재 실행·시도·입력·bucket을 같은 트랜잭션 기준으로 확인하는 안을 추천한다. 재시도 시작과 proceed가 경합하면 하나의 결과만 채택되게 한다.
4. 실패 결과를 허용 예외로 처리해 N3에 넘긴 뒤 늦게 도착한 성공 결과가 bucket·판정을 바꾸지 않도록 해당 시도의 수락 가능 여부를 닫는다. 종료·취소·실패의 구체 저장값은 BE 명세다.

#### BE에 남기는 결정 목록

- **완료 집계:** ocr·job 실행 안에서 개별 실패를 보존하면서 N2 종료를 어떻게 표현할지. 이전 합의의 현재 유효 시도만 집계하는 원칙을 유지할지와 구체 연결.
- **결과 저장:** PRD의 현지 NULL과 현재 통합 content_findings(규제·현지 finding)의 관계. 현지 실패 때문에 정상 규제 finding까지 지우지 않도록 하되 새 JSON 키를 임의로 정하지 않음. 전체 6필드 구조·검사 범위/audit와 맞출 것.
- **실패의 범위:** 현지 사전 조회만 실패한 경우와 공통 묶음 생성·스냅샷 무결성 실패를 어떻게 구별할지. 실제 사용하지 못한 사전은 사용했다고 기록하지 않을 것.
- **재분석 표시:** 이전 유효 결과를 남긴 상태에서 이번 실행의 판정 실패/검사 미수행과 기본 제외 정책을 어느 실행·화면에 적용할지. 기존 결과 보존을 이번 성공으로 표현하지 않을 것.
- **재시도와 진행:** 재시도 종료 시점·횟수·진행 차단·취소와 늦은 결과 무효화, N3에서 재시도를 시작할 수 있는지. 자동 무한 반복 금지.
- **화면·API:** auto_local/auto_local_failed, 배지 없는 판정 실패, 검사 미수행 안내를 기존 상태·오류·API에 어떻게 대응시킬지. 실패 안내 때문에 가짜 section_verdict/finding을 만들지 않을 것.
- **테스트할 경합:** proceed와 재시도 동시 요청, 실패 확정 후 성공 지연 도착, 재분석 실패 후 옛 결과 보존, 전 섹션 제외에서 되살리기, 사전 조회만 실패와 스냅샷 손상의 구분.

### 5.5 C2 — 현지 검사 호출 범위（추천안·미확정）

### 5.6 C3 — 유형·사전·finding 대응（추천안·미확정）

| 사례 | 추천 결과·검토점 |
|---|---|

#### N5 집계·재시도 추천

- 작업 성공, 대상 없음의 정상 생략, 정책상 허용된 실패 대체를 구분해 집계한다. 세 범주는 설명용이며 새 DB status가 아니다. 실패를 성공으로 덮어쓰지 않고, BE가 실제 저장값·API 표현을 제안한다.
- 현재 유효 실행·시도만 대상으로 모든 필수 작업이 성공/생략 또는 **승인된 실패 대체**로 정리되고, 검수에 필요한 결과·실패 표시가 준비됐을 때 N5에 진입하는 안을 검토한다. 재시도 대기/실행 중에는 아직 정리된 결과로 보지 않는 안을 추천한다.
- 대체 허용은 단계별 명시 목록으로 정한다. 인페인트·렌더·번역의 PRD 근거가 있다고 스타일·상류 판정·저장 오류까지 일괄 허용하지 않는다. 정책 미합의인 상태에서 기존 N4 차단을 먼저 제거하지 않는다.
- 같은 실행의 유효한 성공분은 보존한다. 실패 단계 재시도로 출력이 바뀌면 그 출력을 소비한 조판·렌더 등도 무효화/재생성해야 한다. 예: 내부 인페인트 재시도로 배경이 바뀌면 이전 배경의 렌더는 최신 결과가 아니다. 관계없는 번역·스타일은 입력 유효성을 확인해 재사용한다.
- 번역 실패 후 직접 입력은 N5 수정 흐름과 revision·재검사·재렌더에 연결한다. 이전에 출력한 원본 대체 화면이나 실패 상태가 새 결과의 성공을 가리지 않도록 현재 결과를 기준으로 표시한다.
- N5 진입 허용은 최종 확정·내보내기 허용이 아니다. 실패/빈 번역문/대체 원본에 대한 N5 확인 및 최종 출력 조건은 관련 조항을 별도 검토한다. 이번에 새 확인 창이나 최종 출력 예외를 만들지 않는다.
- 중단·재진행은 이전 대표 실행을 무효화하고 새 실행을 사용한다. 산출물 재사용은 입력·판정·revision 유효성을 따로 확인하며, 취소된 워커의 늦은 결과 반영을 허용하지 않는다.

|---|---|

BE는 단계별 작업 상태·대체 결과 참조·실패 원인·N5 응답·자동 재시도 종료와 사용자 재시도 경계·후속 렌더 무효화·집계 트랜잭션을 제안한다. AI는 스타일 필수/NULL, 번역 실패 블록 처리, 배경 대체와 렌더 의존성을 정리한다. PM은 기존 하류 성공 필수 합의를 PRD 예외로 변경할지와 복합/전부 실패·최종 확정 범위를 확인한다. **C4는 아직 승인된 운영 예외가 아니다.**

다음 작업은 C1~C4의 리뷰 결정표를 묶은 뒤, 분석·판정 묶음의 verdict_status/verdict_type·배지·사유 코드 매핑 초안을 작성하는 것이다. 후보와 확정값·기존 API 차이를 분리하고 전체 문서 PR 리뷰로 연결한다.

#### 섹션 집계·표시·빈 값

- 제외형 판정이 하나라도 있으면 섹션 제외라는 PM 정책을 따른다. 단수 exclusion_reason에 규제·현지·실패가 동시에 해당할 때의 우선순위는 아직 없다. 사전 순서나 마지막 행으로 정하지 않고 BE·PM이 결정한다. 모든 판정은 보존한다.
- N3 제외 섹션은 포함형까지 전체 판정 행을 표시한다. 포함 섹션의 주의는 PRD의 N5 흐름과 맞추며, 배지 계산을 FE나 export가 각각 다시 하지 않도록 역할을 정한다. 사용자 되살리기는 restored_by_user와 원래 판정을 남기고 원본 상태를 고치지 않는다.
- 대체 표현 있음은 NULL 여부만으로 임의 확정하지 않는다. 빈 문자열·공백·배열/문자열 변환·자리표시자·부적합 데이터의 취급을 명세한다. 누락/잘못된 형식을 금지형으로 자동 바꾸거나 임의 대체 표현을 만들어 포함시키지 않는다. RG-021/022의 값 검증과 번역 준비는 별도 계약이다.
- 사전 원값→서비스 정책값→배지→섹션 권고→사용자 bucket의 각 층을 연결하되 원본 스냅샷은 불변이다. 기존 행의 원값을 새 이름에서 역추정하지 않는다. 이전 enum과 새 enum을 혼합해 내보낼지 여부는 API 호환 명세에서 정한다.
- 운영 겹침 규칙으로 억제된 매칭은 판정 대상에서 제외하는 방향이지만 원시 근거·억제 관계를 보존한다. 겹침 전용 배지를 만들지 않고 살아남은 판정의 개별 배지를 사용한다. 신호 코드 compliance_flags/SignalCode의 대응은 이 표의 verdict_type과 별도 안건이다.

#### 리뷰 결정·검증 사례

BE는 새 현지 서비스명/배지/제외 사유를 언제 어느 층에서 이관할지, DB CHECK·로더·API·기존 데이터 호환, 배지 파생 주체와 AI 입력/출력, 실패 표시 응답, 단수 제외 사유 우선순위를 제안한다. AI는 원값 보존과 정책 매핑·호환 버전·지원하지 않는 입력 거부를 정리한다. 사용자 정책이 달라지는 매핑은 PM 확인 대상으로 분리한다.

검증 사례: regulated 대체 있음/없음, conditional 대체 있음, rewritable 원값 보존, 현지 두 원값의 present/uncertain/absent, 현지 실패와 uncertain 구분, allowed 억제 후 판정 0행의 audit, 복수 제외 사유가 있는 섹션, 되살리기 후 AI 원본 보존, 빈 문자열/공백/템플릿의 대체 표현. 각 사례는 입력·정책 행·배지·bucket·사유·audit 기대 결과를 함께 검토한다. 실제 테스트나 코드 변경은 아직 하지 않았다.

다음 작업은 사전 공급·판정 저장의 필드별 매핑표(필수/NULL·출처·스냅샷·API 노출)와 audit JSON 구조 초안이다. 현재 판정값 매핑은 공동 리뷰 대기이며 enum을 먼저 구현하지 않는다.

각 snapshot_key·match_key·evidence_key는 이 audit 문서 안의 연결키 제안이다. 사전 external_id나 DB PK를 대체하는 전역 식별자가 아니다. 원본 ID와 실행 묶음의 대응을 유지하며 연결 대상 부재를 NULL/다른 행으로 고쳐 성공 처리하지 않는다. 사전 항목 삭제 후에도 스냅샷은 남아야 하므로 현재 FK 제약과 삭제 정책은 BE가 별도 검토한다.

저장 검증·트랜잭션 추천:

1. 고정 묶음에서 지원값·필수값·사용 ID·스냅샷·검사 범위를 검증한다. 최신 사전 내용과 비교해 결과를 거절하지 않는다.
2. 이번 실행의 블록 참조, finding 식별 범위, 문자 구간 및 `matched_text == source_ko[start:end]`, 모든 배열 참조의 존재를 검사한다. 화면의 UTF-16 인덱스와 혼용하지 않는다.
3. 현재 채택 대상 실행인지 확인하고 교체 전 내용, 새 finding/판정 및 연결 audit, 현재 실행 연결·완료 반영을 하나의 DB 트랜잭션으로 처리한다. ID 배정 이후 audit의 판정 ID도 같은 트랜잭션 안에서 확정한다.
4. 취소/오래된 실행은 현재 결과를 교체하지 않는다. audit 저장 실패도 전체 결과 저장 실패로 보고 일부 결과만 완료 처리하지 않는다. C1의 부분 실패 저장은 이 무결성 예외가 아니다.
5. 사전을 사용했지만 판정이 0행인 allowed/억제 사례도 검사 범위·사용 스냅샷·정책 버전과 대응을 남긴다. 감사 이력과 작업 실패 이력의 역할을 구분한다.

리뷰 사례: 한 finding의 복수 사전, 사전 없는 이미지 근거, 동일 사전의 여러 판단 범위, allowed로 판정 0행, 억제된 매칭 보존, 사전 재적재/삭제 후 결과 저장, 근거 확인일 누락, 대체 표현 안의 구분자, 재분석 실패/늦은 성공, 블록 수정/삭제 후 과거 매칭 해석, 보조 평면 문자·결합문자 구간, audit 쓰기 실패의 전체 롤백. 현재는 사례 정의이며 테스트 실행 결과가 아니다.

BE 결정 요청은 공급처가 없는 필드의 보완 방식, 단수 대표 컬럼 선택, audit 키·크기·보존 및 조회/API 범위, 삭제 후 식별 관계, 동시성/트랜잭션이다. AI는 통합 입력형의 필수/선택과 사용 근거·검사 범위 출력을 정리한다. 다음 초안은 하류의 text_block.style·auto_adjust·overflow 경계이며, 이 초안의 미결은 공동 PR 리뷰에 남긴다.

### 5.13 auto_adjust의 사용자 배치와 자동 결과 분리（추천안·미확정）

| 층 | 확인한 의미 | 차이 |
|---|---|---|
| AI 계약 6.1 | schema_version·layout_bbox·updated_by=user | 사용자 배치 입력. 원본 bbox 보존, 섹션 로컬, 미리보기/최종 렌더 공통 |
| OpenAPI AutoAdjust | 저장 font_scale·line_break_applied → 응답 fontScale·lineBreakApplied | 자동 조판 결과. 사용자 layout_bbox를 표현하지 않음 |

| 현재 CFM 조회/수정 | 조회는 auto_adjust를 그대로 autoAdjust에 넣음. BlockPatch는 trans1·revision | OpenAPI의 내부 키 변환과 실제 조회 차이 존재. 사용자 영역 변경 요청 형식도 현재 명세에 없음 |

**추천: 사용자 배치 입력과 자동 조판 결과를 서로 다른 의미로 인계한다.** 기존 AI 계약의 layout_bbox는 유지하는 방향으로 검토하고, font_scale·line_break_applied 같은 자동 결과는 해당 렌더 산출물에 연결한다. 최종 저장 위치는 기존 JSON 안의 명확한 하위 구조와 별도 저장 위치를 BE가 비교 결정한다. 이번 초안만으로 컬럼·엔드포인트·JSON 키를 추가하지 않는다.

- 배치가 없으면 원본 bbox, 있으면 layout_bbox를 사용한다는 기존 계약은 유지한다. 원본 bbox에 사용자 변경을 덮어쓰지 않는다.
- 사용자 배치도 섹션 로컬 정수 px로 받는 안을 추천하되, 원본 bbox의 정수 규칙이 사용자 편집 정밀도까지 자동 확정한 것으로 보지 않는다. 화면 배율 역변환·반올림 주체, x/y≥0·w/h>0·섹션 내부 조건, 잘못된 영역의 거절 방식은 BE/FE 명세에 남긴다. 조용히 잘라서 저장하지 않는 안을 추천한다.
- 배치 초기화의 의미는 원본 bbox로 돌아가기다. 요청에서 키 누락/NULL/초기화를 어떻게 구분할지, 담당하지 않는 JSON 키를 보존하는 갱신 방식은 BE가 정한다.
- 번역문·배치 변경은 기존 계약대로 revision을 증가시키고 재렌더한다. 자동 렌더 결과 저장 때문에 입력 revision이 반복 증가하는 구조는 피한다. 실행 취소/현재 시도 검사도 revision 검사와 함께 적용한다.
- fontScale의 기준 크기·허용 범위·실제 적용값, lineBreakApplied가 자연 줄바꿈인지 강제 개행 삽입인지 아직 정하지 않았다. 자동 폰트 축소의 허용 자체와 최소 크기도 API 필드 존재만으로 승인하지 않는다. 렌더 결과가 원문/번역문을 임의 축약하지 않도록 한다.
- BE가 최종 저장/응답을 정한 뒤 OpenAPI 소유 브랜치 feature/api-tracking에서 요청·응답·호환 계획을 반영한다. 현재 클라이언트에 새 의미를 기존 필드로 조용히 내리지 않는다.

### 5.14 overflow·최신 렌더 유효성（추천안·미확정）

기존 계약은 완료된 최신 렌더의 현재 배치 영역에서 폭 또는 높이가 초과하면 true이며, 초기 false는 완료 증거가 아니다. 반면 현재 run_render는 charLimit이 있을 때 글자 수 비교로 overflow를 갱신한다. 글자 수 제한 검증과 실제 조판 초과는 다른 검사이며 분리하는 안을 추천한다.

| 상황 | 표시·저장 추천 | 확인할 경계 |
|---|---|---|
| 이번 입력의 렌더 미완료/실패 | 초기 false·이전 overflow를 현재 측정으로 표시하지 않음 | API boolean 외 완료/유효성을 식별할 정보가 필요. 새 필드/NULL 변경은 BE 결정 |
| 최신 렌더 성공, 폭·높이 이내 | overflow=false | 실제 사용 폰트·크기·행간·배치로 측정했는지 확인 |
| 최신 렌더 성공, 폭 또는 높이 초과 | overflow=true, 문장 보존 | 실행 실패와 구분. C4 및 검수/최종 출력 조건에 연결 |
| 글자 수 초과이나 실제 영역 이내 | 글자 수 제한 검사 결과와 overflow를 분리 | char_limit으로 자동 축약하거나 overflow를 대체하지 않음 |
| 글자 수 이내이나 긴 단어/높이 초과 | 실제 렌더 기준 true | 문자 수만으로 놓치는 사례 |
| 편집/배치 변경 후 옛 렌더 도착 | 현재 revision과 다르면 반영하지 않음 | 이미지 참조와 overflow를 같은 유효 입력 결과로 반영 |
| 배경·스타일·폰트 매핑 변경 | 같은 텍스트 revision이어도 결과 입력 유효성 재검사 | revision만으로 모든 렌더 입력을 대표하지 않음 |
| 대상 없음·원본 대체 | 측정 생략/대체를 실제 렌더 성공과 구분 | C4의 예외와 표시 계약 필요 |

BE 측정 명세에는 실제 폰트 로드 완료 시점, 줄바꿈·행간·padding·border, 측정할 텍스트 영역, 소수 px 허용 오차·정확히 경계와 같은 경우, 원본 px와 CSS/캡처 배율 대응을 포함한다. 프리뷰 배율 때문에 초과 결과가 달라지지 않게 원본 기준으로 판정하는 안을 추천한다. DOM 속성 하나를 지금 계약으로 고정하지 않는다.

렌더 입력에는 현재 번역문/배치 revision, 스타일 결과, 배경, 역할 폰트 매핑과 렌더 설정의 유효한 버전/식별을 묶는 안을 추천한다. 캐시 키·저장 필드는 BE와 정한다. 이미지 업로드만 성공했다고 DB 완료 처리하지 않고, 현재 실행/시도·입력을 검증한 결과 참조와 overflow를 함께 채택한다. 실패 시 옛 미리보기를 보존할 수 있어도 최신 완료로 표시하지 않는다.

리뷰 검증 사례: 색만 NULL·정렬만 NULL·단일 줄 기본 left, 대상 없는 블록, bg_color가 있는 사진 배경, 소수 글자 크기와 프리뷰 배율, 배치 초기화·경계 밖 입력, 폰트 지연/대체, 긴 단어의 폭 초과·여러 줄 높이 초과·정확히 경계, 글자 수 제한과 실제 초과 불일치, 편집 중 옛 렌더 도착, 같은 revision에서 스타일/배경 변경, 원본 대체와 렌더 성공의 구분. 테스트 실행이 아닌 공동 리뷰용 사례다.

결정 순서는 (1) AI 측정값/사유와 BE 조판값 경계 (2) 사용자 배치 요청 및 자동 결과 저장/API (3) 렌더 입력 유효성과 초과 측정 (4) C4·N5 집계 연결이다. 다음 문서 작업은 compliance_flags·API 신호 코드와 RG-021/RG-022 상품별 검증 정보의 공급/저장/인계를 정리하는 것이다. 이 초안의 미결도 전체 PR 리뷰에 포함한다.

#### 근거 갱신·노출·확정 경계

- 기존 계약의 type·producer·revision 필수와 실제 근거 ID만 연결하는 원칙을 유지한다. 재검증은 자신이 생산한 항목만 교체하고 다른 생산자의 기록은 보존한다. 원자 갱신 방식과 producer별 관리 범위는 BE 명세로 정한다.
- 번역문 수정 후 옛 revision 신호를 최신 경고로 표시하지 않는다. 새 검사가 대기/실패한 경우는 ‘검사 완료·문제 없음’과 구분한다. API 표현과 최종 확정 허용 조건은 미결이며 신호 빈 배열만으로 완료를 판단하지 않는 안을 추천한다.
- 사전·정책·상품 검증 정보가 바뀌면 텍스트 revision이 같아도 재검증 유효성이 달라질 수 있다. 검사 입력 버전 연결을 5.11·5.14와 맞춘다. 분석 당시 사전 스냅샷을 최신 DB 값으로 바꾸는 안은 채택하지 않는다.
- 같은 코드의 근거가 여러 개면 원본을 모두 보존한다. 화면에서 코드별 묶음을 만들더라도 problemText 하나나 대표 사유로 전체 근거를 대체하지 않는다. 블록/섹션 범위·중복 표시·정렬은 BE/FE와 결정한다.
- ReviewSignal.evidenceUrl은 현재 API에 presigned로 설명돼 있지만 사전 근거 URL은 외부 출처 링크일 수 있다. 외부 링크와 저장된 증빙 파일의 접근 URL을 구분해 직렬화한다. 저장 스냅샷의 근거를 만료 URL만으로 보존하지 않는 안을 추천한다.
- ConfirmRequest의 acknowledgedWarnings는 현재 blockId+code로 식별한다. 같은 코드의 복수 근거, 섹션 단위 경고, 확인 중 revision/검사 결과 변경을 어떻게 검증할지 남아 있다. 요청/응답을 이번에 새로 정하지 않고 서버가 최신 유효 경고 집합과 대조할 기준을 BE가 제안한다.
- 경고 확인이 상품 수치 검증이나 미완료 검사의 성공을 뜻하지 않도록 한다. 어떤 경고를 확인으로 통과할 수 있는지와 출력 차단 조건은 PM 정책 및 C4 최종 출력 경계와 별도 합의한다.

리뷰 사례: conditional과 regulated의 신호 차이, allowed 억제 후 신호 없음과 검사 실패의 차이, 강제 용어 적용 후 이전 근거 제거, 다른 producer 보존, 재시도 성공 후 과거 translation_failed 제외, 높이만 초과, 관리자용/MVP 이후 코드 차단, 동일 코드 복수 근거, 경고 확인 중 편집·재검증 완료. 실제 테스트는 아직 수행하지 않았다.

### 5.16 RG-021·RG-022 상품별 검증 정보와 번역 인계（추천안·미확정）

근거는 contract.md 5.1, open-questions.md #56·#70 및 2.7절의 사용자 경유 BE 전달 기록(2026-09-30)이다. 이번에 새 사전 정정본이나 운영 DB를 확인한 것은 아니다. 두 항목은 conditional 템플릿이며 사전 적재 성공·섹션 포함 권고와 번역 사용 준비를 구분한다. 여기서는 법규나 상품 적합성을 새로 판단하지 않고 정보 공급/저장/인계의 공백을 명세한다.

**유지할 제한**: 검증되지 않은 수치를 추정하지 않고 자리표시자를 최종 출력하지 않는다. OCR·한국어 표시값·셀러 입력만으로 검증 완료를 추정하지 않는다. RG-022는 수치 외에 당시 reason의 적용 조건 확인도 필요하다. 적용 조건의 실제 내용은 고정 사전/검증 근거에서 공급하며 문서에 임의로 새 조건을 만들지 않는다.

| 인계 정보 | 추천 책임·내용 | 미결 |
|---|---|---|
| 적용 대상 | BE가 job/상품과 실제 적용 블록·사전 항목의 연결을 고정 | 상품 동일성 기준·여러 상품/변형이 있는 이미지의 처리 |
| 사전·정책 | 실행 묶음의 external_id·서비스/원본 판정·reason·원문 템플릿·버전/해시 | 5.10 변환 형식과 연결. 최신 사전 재조회로 교체하지 않음 |
| 상품별 수치 | 지정된 확인 주체가 확인한 값과 표기 단위/형식 | 확인 주체·수용 증빙·검증 기준은 PM/데이터 확인. 숫자 범위나 반올림을 임의 정의하지 않음 |
| 검증 근거 | 확인 대상·출처·증빙 참조·확인 주체/시점·검증 정보 버전 | 기존 저장 필드 적합성, 접근 권한·보존·철회 정책은 BE 설계 |
| 적용 조건 | 당시 reason의 조건과 확인 결과·근거를 연결 | 미확인과 조건 불충족 구분. RG-022를 수치 존재만으로 통과시키지 않음 |
| 번역 산출 | 실제 사용한 값·템플릿·검증 정보 버전을 결과에 연결 | 저장 위치와 인계 JSON 키는 BE/AI 공동 결정 |

BE가 실행 시작/입력 준비 시 유효한 검증 정보를 고정해 AI에 전달하는 안을 추천한다. 사전 dictionary_id만으로 상품별 검증을 대신하지 않는다. 검증 스냅샷에 어떤 상품·템플릿·조건을 확인했는지 있어야 하며, 같은 수치를 다른 상품이나 다른 적용 조건에 재사용하지 않는다. 이 의미가 정해지기 전 신규 테이블·검증 상태 enum·오류 코드를 먼저 만들지 않는다.

#### 미확인·변경·재검증 처리 후보

| 상황 | 추천 처리 | 결정 주체 |
|---|---|---|
| 수치·조건·근거가 모두 유효 | 승인된 변환 방식으로 템플릿을 완성하고 사용 근거를 고정 | AI·BE, 검증 기준은 PM/데이터 |

| 조건 불충족 | 미확인과 구분해 해당 템플릿을 적용하지 않는 안 | 대안·제외·수정 흐름은 PM/데이터 |
| 사용자 직접 입력/경고 확인 | 입력했다는 사실과 근거 검증을 분리 | 이를 검증으로 인정할 기준은 PM 결정 |

| 생성 결과에 미치환 자리표시자·다른 수치가 남음 | 출력 검증에서 식별해 정상 완성 결과로 채택하지 않는 안 | 탐지 형식·오류 구분·재시도는 AI·BE |

수치/조건 미확인은 단순 일시 호출 실패와 다르므로 자동 재시도를 반복해 해결된 것으로 보지 않는다. 기존 conditional을 자동 제외로 바꾸거나, C4 번역 실패 빈 셀 예외를 그대로 적용하지 않는다. 이 항목의 사용자 정책은 앞선 PM의 uncertain·겹침 승인으로 확정된 것이 아니다.

영어 검사도 별도다. `SPF [value]`의 현재 리터럴 표현을 임의로 정규식/와일드카드로 바꾸지 않는다. 데이터 담당이 의도와 정정본을 확인한 뒤 AI가 수치 표현 검출·치환 결과 검증 범위를 제안한다. 표현 검출, 입력값과 생성값의 일치 검사, 상품 근거의 적합성 확인은 서로 다른 검사다.

리뷰 사례: RG-021 값 없음/유효값 있음, RG-022 값만 있고 조건 미확인, 근거가 다른 상품에 속함, 조건 불충족, 사전만 적재된 상태, 미치환 템플릿, 번역이 값을 변경함, 근거 수정/철회와 늦은 완료, 셀러 입력만 존재, 같은 텍스트 revision에서 검증 정보 버전 변경. 현재는 검증 사례 정의이며 운영 적용·모델 실행은 하지 않았다.

다음은 대표/개별/재시도 작업의 식별, 생략 완료, 오류·재시도·큐 복구·취소·중복 전달 등 실행·운영 상세 초안이다. 이후 전체 목록에서 실제 지원 유형·사전 대응·매칭 상세·공급/보존·최종 출력 등 미결을 담당별 결정표로 정리해 하나의 PR 리뷰로 연결한다.


### 5.17 실행·시도 식별과 작업 집계（추천안·미확정）

기준: 2026-10-07 원격 develop `4c0f791`·통합 `e5f441f`, 로컬 `b2a4470`. D1·D2·D6, contract.md 6.3·8·11장, migrations 0001·0004, docs/openapi.yaml의 TaskType/TaskStatus/JobTaskStatus와 재시도·중단 API, app/tasks.py·app/routers/jobs.py·sections.py·app/celery_app.py를 대조했다. 아래는 실행 상세 추천안이며 새 컬럼·task_type·오류 코드·운영 수치를 확정하지 않는다.

| 구분 | 기존 합의/현재 상태 | 상세 추천·BE 결정 |
|---|---|---|
| 초기 분석 실행 | ocr·unit_type=job 확정 | N4 실행과 별도 식별. ①②③/판정/정책의 재시도 단위와 하위 단계 기록 위치는 BE가 결정 |
| N4 대표 실행 | proceed당 job 단위 대표 행 | task_type 미정 유지. translate로 확정하지 않음. 대표 행은 집계/취소 기준이며 개별 단계와 중복 진척 집계하지 않음 |
| 개별 단계 | 대표 행 참조, 대상·단계별 작업 | 현재 API TaskType은 ocr/section/inpaint/translate/verify/render뿐. ④⑤⑦ 및 대표 행의 구분을 기존 값에 억지로 넣지 않고 확장/별도 단계 식별 방안을 BE가 제안 |
| 현재 시도 | 실패 행은 보존하고 재시도는 새 행 | 실행·대상·단계의 논리 작업과 시도 이력을 연결. 현재 시도 선택, 선행 시도 참조, 중복 생성 제약의 컬럼/인덱스는 후속 스키마 결정 |
| 입력 유효성 | revision은 번역문·배치용 | 실행/시도 식별과 분리. 사전·판정·배경·스타일·상품 검증 정보 등 단계별 입력 버전도 확인 |
| 정상 생략 | 대상 없음은 호출 없이 완료로 집계 | 호출하지 않았다는 사실·대상 없음 사유·실행 연결을 기록. 현재 status enum에 skipped는 없음. done+별도 결과 메타 또는 상태 확장의 저장/API 방식을 BE 결정 |
| 부분 실패 대체 | C1·C4 미확정 | 정상 생략으로 위장하지 않음. 승인될 경우 실패 이력과 채택한 대체 결과를 함께 집계하도록 별도 명세 |

현재 DB 작업 행에는 대표/재시도 연결 컬럼이 없다. 현재 retry 구현은 같은 행을 pending으로 바꾸며 오류/시각을 초기화한다. 새 행을 만드는 D2와 다르므로 기존 구현을 그대로 운영 계약으로 승계하지 않는다. 현재 API 재시도 허용은 translate/render로 제한돼 있어 초기 분석·라벨·로고·스타일 등의 내부 재시도와 사용자 재시도 범위를 구분해야 한다.

집계는 **현재 실행의 논리 작업별 현재 시도**만 사용하고 과거 실패/취소 행과 대표 행을 분모에 중복 산입하지 않는 안을 추천한다. 현재 OpenAPI의 task_type별 전체 행 집계와 N4 고정 표시(inpaint→translate→verify→render)는 ④⑤⑦ 식별과 ⑥⑦⑧ 병렬성을 표현하기에 부족하다. 순서 표시는 실행 직렬화를 뜻하지 않도록 바꾸는 방향을 검토한다.

후속 작업을 동적으로 만들기 때문에 초기 대기 행이 모두 done이어도 전체 실행이 완료된 것은 아니다. 필수 단계·대상이 확정돼 후속 생성이 끝났는지 확인한 뒤 N5를 판정한다. 전체 블록 0개, 전부 제외, 일부 섹션만 준비된 경우도 누락과 정상 생략을 구분한다. 섹션별 ④⑤ 완료 시 하류를 시작할지 모든 포함 섹션의 완료를 기다릴지는 별도 명시한다. 진척 분모/가중치·대상 확정 전 표시·N5와 N6 렌더 구분은 BE/FE 결정이다.

### 5.18 큐 전달·취소·결과 반영의 경계（추천안·미확정）

**추천은 DB에 작업 의도를 먼저 확정하고 큐 전달을 복구 가능하게 만드는 것이다.** DB 트랜잭션과 브로커 전송을 하나의 원자적 처리로 간주하지 않는다. 기존 대기 작업 행을 전달 의도로 사용할지 별도 전달 기록을 둘지, 전달 확인/재전송 식별 필드와 복구 담당 프로세스는 BE가 정한다. 새 테이블 생성은 이번 초안의 확정 사항이 아니다.

| 경계 | 추천 처리 |
|---|---|
| proceed 시작 | job 잠금 아래 단계·포함 섹션·활성 실행 검사, 대표·최초 작업과 N4를 함께 저장. 동시 요청은 같은 활성 실행을 사용하고 응답 형식은 BE 결정 |
| DB 커밋 전 오류 | 대표/작업/N4를 함께 롤백. 커밋 전 큐가 실행을 시작하지 않게 함 |
| 커밋 후 전송 실패/확인 불명 | N4·대표·대기 작업 유지. 복구는 같은 작업 ID를 재전달하고 새 proceed/실행을 만들지 않음 |
| 워커 수신 | 실행·현재 시도·취소 여부 검사 후 원자적으로 실행 권한 획득. 이미 완료/권한 보유/무효인 전달은 중복 실행하지 않음 |
| AI/모델 실행 | 장시간 DB 잠금을 유지하지 않는 안. 고정 입력과 실행 권한을 사용하고 종료 후 다시 유효성 검증 |
| 결과 반영 | 같은 대표 실행을 기준으로 현재 시도·실행 권한·revision/입력 유효성 재검사. 결과·완료·필요 후속 대기 행·전환을 DB 트랜잭션으로 함께 반영 |
| 후속 큐 등록 | 저장된 후속 대기 행을 커밋 후 전송. ⑥⑦⑧은 대상 확정 뒤 함께 생성하고 서로 완료를 기다리지 않음 |
| 중단과 완료 경쟁 | 취소와 결과 채택이 같은 실행 기준의 잠금/조건을 사용. 취소가 먼저 확정되면 늦은 결과·재시도·후속 생성·N5 전환 거절 |
| 완료가 중단보다 먼저 확정 | 이미 완료된 결과를 취소 전에 없었던 것으로 취급하지 않음. 현재 단계에서 중단 가능한지 다시 검사하고 API 동작을 BE가 명세 |
| S3 업로드 후 DB 반영 거절 | 채택된 결과 참조를 갱신하지 않음. 미채택 파일은 식별 가능한 키로 분리하고 정리 주체/보존 기간은 운영 정책 |

현재 Celery 설정은 acks_late·worker_lost 재큐잉을 사용한다. 이것만으로 작업 행 생성·모델 실행·결과 반영의 중복이 방지되지는 않는다. 워커 유실 시 실행 권한 만료/회수, 생존 확인, 새 소유권 식별과 옛 워커 차단 방법이 필요하다. 모든 잠금 경로의 순서도 통일해 교착을 피하는 방향으로 BE가 설계한다.

**보장 범위 구분**: 정상 중복 전달의 중복 실행을 억제하고, 결과 채택·후속 생성·상태 전환 효과는 한 번만 반영한다는 D2를 유지한다. 다만 외부 모델이 처리한 뒤 응답/DB 기록 전에 워커가 죽으면, 제공자의 멱등 키나 결과 조회 지원 없이 외부 호출 자체의 ‘정확히 한 번’을 보장했다고 말할 수 없다. 이 구간의 결과 불명 처리·중복 비용·복구 기준을 명세한다. 재전송·실제 새 시도·SDK 내부 재요청을 서로 구분하며 재전송만으로 retry_count를 올리지 않는 안을 추천한다.

### 5.19 실패·재시도·복구 운영표（추천안·미확정）

| 실패 종류 | 재시도 추천 | 남겨야 할 결정 |
|---|---|---|
| 일시 통신·서비스 장애 | 현재 실행/입력 유효, 재시도 가능 분류, 누적 한도 내에서 새 시도 | 단계별 분류·간격·지연 증가·동시 실행 한도 |
| 인증·설정·미지원 입력 | 같은 입력의 자동 반복 중지, 원인 수정 후 재처리 | 오류 코드·운영자 처리·입력 변경 시 새 논리 작업 경계 |
| 응답 형식/누락/판정 불일치 | uncertain이나 정상 생략으로 저장하지 않음 | 재생성 허용 여부·횟수와 결정적 입력 오류 구분 |
| 무결성/스냅샷/ID 손상 | 부분 성공으로 진행하지 않음 | 데이터 복구 후 어느 단계부터 다시 처리할지 |
| 시간 초과·워커 유실 | 실패 확정 전 실행 소유권·결과 불명 검사 | 제한 시간·회수 조건·늦은 결과 차단·재호출 비용 |
| 큐 전송 실패 | 저장된 유효 대기 행 재전달 | 복구 주체·주기·횟수·오래된 대기 감지 |
| 모델 성공 후 업로드/DB 실패 | 유효 산출물이 남으면 저장 단계 복구를 우선 검토 | 검증/보존 방식, 모델 재호출과 저장 재시도의 횟수 분리 |
| 상품 검증 정보 미확인 | 자동 모델 반복으로 해결하지 않음 | 5.16 사용자/운영 처리·재개 조건 |
| 정상 uncertain·측정값 NULL | 그 사실만으로 재시도하지 않음 | 정책 적용 또는 승인된 조판 대체 처리 |

현재 max_retry 기본값 2나 단독 실행 제한 시간·스텁 오류를 통합 운영값으로 확정하지 않는다. retryable은 AI의 분류 하나이며 BE가 실행 취소 여부·현재 시도·허용 유형·누적 예산·입력 유효성을 함께 검사한다. HTTP 오류, 작업 error_code, 사용자 신호 코드는 별개 값 공간을 유지한다.

실패한 행은 그대로 남기고 같은 논리 작업의 재시도 요청을 잠금/유일성 제약 등으로 직렬화해 새 시도가 하나만 생기도록 한다. 새 행에도 최초 이후 누적 횟수가 이어져야 하며, 자동/수동 요청으로 한도를 초기화하지 않는다. SDK 내부 재요청까지 포함한 총 호출 예산과 실제 호출 이력을 어떻게 관측할지는 AI·BE가 공동 결정한다. 재시도 응답의 taskId가 새 시도를 가리킨다면 FE 폴링/실패 신호도 그 ID로 연결해야 한다.

성공분은 입력이 유효한 범위에서 보존하고 실패한 단계만 다시 처리한다. 재처리 출력이 바뀌면 그 출력을 소비한 번역 검증·조판·렌더의 유효성도 갱신한다. 전부 다시 실행하거나 관계없는 성공분을 지우는 방식으로 단순화하지 않는다. 취소된 실행은 재시도하지 않고 새 proceed의 실행으로 분리한다.

리뷰 시뮬레이션: proceed 동시 2회, DB 커밋 후 전송 실패, 전송 성공/응답 유실, 같은 작업 동시 전달, 모델 응답 직전 워커 유실, 권한 회수 뒤 옛 워커 완료, 취소/결과/재시도 동시 경쟁, 실패 행의 중복 재시도, 여러 성공 작업이 동시에 후속 생성, 일부 섹션 준비·빈 대상, 과거 실패 행이 남은 상태의 N5 집계, 업로드 후 DB 실패, 입력 변경 뒤 결과 재사용. 기대 결과는 현재 실행의 결과 한 번 채택·후속 중복 없음·이력 보존이며 실제 장애 테스트는 구현 후 수행한다.

BE는 작업 저장/제약·API·집계·잠금·큐 복구 방식을, AI는 단계별 입력 유효성·실패 분류·재사용 가능한 산출물을 제안한다. 운영 횟수·시간은 실행 환경과 측정 근거로 정한다. C1/C4 예외 채택은 별도 공동 리뷰이며 이번 운영 초안으로 승인하지 않는다. 다음 작업은 전체 초안의 미결·담당·완료 기준을 한 결정표로 모으고, 실제 지원 유형/판정 기준·매칭 상세·최종 출력 등 아직 내용이 부족한 항목을 표시하는 것이다.

#### finding 분리와 근거의 구체 규칙 후보

1. 현지는 **유형+독립된 안내/문맥**을 한 판단 단위로 한다. 같은 안내가 여러 블록에 걸치면 하나, 같은 유형이라도 공간·내용상 독립된 안내면 둘로 나눈다. 블록 수나 사전 행 수를 finding 수로 쓰지 않는다.
2. AI는 각 판단 단위에 실제 사용한 블록 목록과 판단 범위 설명을 제공한다. 블록 없는 이미지 근거는 섹션 로컬 근거 영역 `{x,y,w,h}`를 별도 근거 기록으로 제안한다. 범위 식별·이미지 영역은 finding 6필드 밖 audit 인계에 둔다. 영역을 제공할 수 없는 경우 섹션 전체가 판단 범위임을 명시하고 정밀 위치를 꾸미지 않는다.
3. 해당 문맥이 하나도 없으면 검사한 섹션 전체 범위에 absent 하나를 남긴다. 문맥별 결과가 있으면 중복되는 섹션 전체 absent를 추가하지 않는다. 미검사 영역까지 absent로 확대하지 않는다. 호출 범위는 C2와 별도이며 이 규칙으로 호출 대상을 축소하지 않는다.
4. present/uncertain에는 대상 문맥 근거가 필요하다. absent도 실제 검토한 근거를 남긴다. image_and_text에는 실제 쓴 텍스트 블록만 넣는다. 이미지가 입력에 있었다는 이유만으로 근거 출처를 바꾸지 않는다.
5. 현지 유형의 주 판정 기준은 대응 LC 한 항목이다. 다른 사전이 실제 보조/정책 근거로 사용되면 별도 관계로 모두 남기되 그 항목 때문에 유형이나 finding을 복제하지 않는다. 판정 공급 뷰와 정책 뷰의 분리는 유지한다.
6. 규제는 **같은 블록의 같은 원문 구간**을 하나의 finding으로 제안한다. 같은 구간의 서로 다른 사전 매칭은 복수 연결, 다른 구간은 별도 finding이다. 부분 겹침도 별도 구간으로 남긴다. 억제 전 검출 finding과 매칭은 보존하고, 정책 행 생성은 R04의 살아남은 매칭에만 적용한다.
7. finding_key는 실행·섹션 내부에서만 유일하다. 정책은 content_type으로 사전을 조회하지 않고 별도 finding→사용 사전/매칭 대응을 소비한다. 사전 원값·정책 결과·사용자 bucket은 finding.status와 분리한다.

합성 기대 사례: 동일 문의 안내 두 블록 → finding 1개/블록 2개; 독립 문의 안내 두 곳 → 2개; 한 곳 해당·다른 곳 비해당 → 범위별 present/absent; 상품명만 보이는 기획명 → 해당 범위 absent; 상품 구성 자체를 판독할 수 없는 안내 → uncertain; 규제 두 사전이 동일 구간 → 검출 finding 1개와 사용 사전 2개; 규제 미매칭 → finding 없음/검사 완료 범위 기록. 실제 판정 품질 평가가 아니라 계약 기대 결과다.

| 원문 보존 | 정규화 전 원문을 보존하고 코드 포인트 [start,end)·원문 슬라이스를 저장. N5 구간은 trans_1 기준임을 명시하고 N3 source_ko 구간과 혼용하지 않음 |
| 한국어 | 현재 방식과 비교 가능하도록 문자별 NFKC→lower→공백 제거를 후보로 유지. 공백은 str.isspace 기준이며 LF/CR/탭도 제거한다. 각 출력 문자→원문 문자 위치를 보존. 문자열 전체 NFKC와 같은 동작으로 설명하지 않음 |
| 한국어 왼쪽 경계 | 패턴 시작 직전 원문 문자가 없거나 공백/구두점이면 허용. 직전 문자가 글자/숫자면 원칙적으로 거절. 오른쪽 조사/어미는 허용하되 최종 의미 판단은 현지 judge에서 수행 |
| 가격 접미 표현 예외 | LC-06에서만 숫자+단위와 이어진 가격 접미 패턴을 허용. 선행 금액은 숫자 또는 세 자리 쉼표 묶음, 선택 소수부, 선택 한국어 배수 단위(십·백·천·만·억)의 조합으로 제안. 허용 단위/패턴 목록은 버전된 매칭 규칙에 명시. 임의의 한국어 단어 뒤 ‘원’은 허용하지 않음 |
| 영어 | 문자별 NFKC→lower. str.isspace 공백(LF/CR/탭 포함)과 하이픈(-·U+2010·U+2011)을 구분자 한 칸으로 정규화하고 연속 구분자를 합침. 다른 기호는 보존. 패턴 양끝이 글자/숫자면 대응 원문 양끝에서도 단어 경계 요구 |
| Unicode 경계 | 문자 범주는 Unicode Letter/Mark/Number로 정의하는 안. 문자 확장 결과의 일부만 매칭하지 않도록 원문 문자 단위 시작/끝을 확인. 분해된 한글 자모 결합은 이 후보에서 하지 않으며 별도 사례/향후 정규화 변경으로 추적 |
| 동일 항목 중복 | 동일 사전 ID·블록·원문 구간의 반복 검출은 1개 매칭으로 집계하되 일치한 패턴 참조는 모두 보존. 다른 항목의 동일 구간은 유지 |

#24에서 확정한 source_ko는 줄 사이의 실제 LF(`\n`)를 보존한다. 저장/인계에서 줄바꿈을 공백으로 덮어쓰지 않고 매칭용 사본만 위 규칙으로 정규화한다. 합성 기대값: 원문 `ab\ncd`와 패턴 `abcd`는 한국어 후보에서 [0,5)로 매칭하며 원문 구간에 LF가 포함된다. 영어 후보에서는 `ab cd` 패턴과 일치하고 `abcd`와는 불일치한다. 공백/LF만 있는 source_ko는 strip 기준 빈 원문이지만 줄바꿈이 있는 비공백 문장을 empty_block으로 만들지 않는다. 이 구분을 R04·R12·R20의 BE/FE 공유에 포함한다.

가격 문법은 금액 적합성/통화 변환 검사가 아니라 후보 탐색 예외다. ‘3만원’에서 ‘원’과 ‘만원’이 함께 걸리면 다음 포함 규칙으로 긴 구간을 남긴다. 잘못된 숫자 그룹핑을 임의 교정하지 않는다. 한국어 경계는 현재 substring과 다른 후보이며 데이터/AI 대표 표본 비교가 필요하다. 영어 하이픈과 공백의 동등성도 현재 구현 완료가 아니다.

#### 겹침 적용 순서 후보

적용 범위 후보는 규제 표현의 정책 매칭이다. 현지 LC 패턴은 의미 판정을 위한 후보이므로 규제 매칭에 감싸졌다는 이유로 LC 검사 자체를 없애지 않는다. LC의 원시 매칭과 최종 의미 판단 근거는 그대로 보존한다. 이 적용 범위는 PM/데이터의 운영 의도와 함께 승인받을 상세 제안이다. 아래 비허용은 regulated/conditional 등 allowed 외 규제 항목을 뜻하며 법적 위반 확정과 같은 말이 아니다.

1. 원시 매칭을 모두 보존한다. 비교는 **같은 실행·언어·블록·텍스트 revision** 안에서만 수행한다. 검출 범위/사전 ID/정규화 버전을 기록한다.
2. 동일 구간의 금지·허용 조합은 적재 거부 원칙을 유지한다. 서로 다른 원문 패턴이 실행 정규화로 같은 구간에 충돌하면 공급 검사/실행 검증에서 오류로 식별하고 임의 우선순위로 판정하지 않는 안을 제안한다. 이 오류의 화면 전이는 C1과 BE가 결정한다.
3. **허용 구간 억제를 먼저** 계산한다. 원시 allowed 매칭이 다른 매칭 구간을 완전히 감싸면 그 내부 매칭을 억제한다. 일부 겹침은 억제하지 않는다. 모든 억제 원인 ID를 기록한다. allowed는 정책 판정 행을 만들지 않는다.
4. 3번 후 남은 비허용 매칭끼리 엄격 포함을 계산한다. 더 큰 구간에 포함된 짧은 구간을 억제하고 최대 구간을 남긴다. 동일 구간은 엄격 포함이 아니므로 서로 다른 금지 항목을 모두 유지한다. 길이 정렬 후 순차 삭제 대신 포함 관계를 한 번에 계산해 입력 순서에 의존하지 않게 한다.
5. 부분 겹침/비겹침은 모두 남긴다. 같은 짧은 매칭을 감싸는 최대 구간이 여러 개면 억제 원인을 모두 기록한다. 경고/정책 집계는 살아남은 항목별 결과로 수행한다. conflict_group 자체로 배지를 만들지 않는다.

이 순서는 **새 기술 제안**이다. 특히 allowed가 짧은 금지 매칭을 억제한 뒤 자신보다 긴 금지 매칭이 남는 경우를 PM/데이터 의도와 대조해야 한다. 억제된 원시 근거는 audit에 남으며 섹션 전체의 위반 없음으로 확대하지 않는다.

| 합성 입력/구간 | 기대 결과 후보 |
|---|---|
| 금지 A[0,10), B[2,6) | A 유지, B는 A에 포함돼 억제 |
| 금지 A[0,6), B[4,10) | 둘 다 유지 |
| 금지 A[0,4), B[4,8) | 접점만 있어 비겹침, 둘 다 유지 |
| 금지 A/B 모두 [0,6) | 두 사전 항목 유지, R03 검출 finding은 구간 단위 1개 |
| 허용 K[0,10), 금지 A[2,6) | A 억제, K 정책 행 없음, 원시 근거 보존 |
| 허용 K[0,6), 금지 A[4,10) | A 유지, K 정책 행 없음 |
| 금지 A[0,12), 허용 K[2,10), 금지 B[4,8) | K가 B 억제, A 유지. 긴 A를 허용으로 바꾸지 않음 |
| 금지 A[0,12), B[2,10), C[4,8) | A만 유지, B/C의 최대 포함 원인 A 기록 |
| 금지 A[0,6), B[0,10), C[4,12) | A 억제, B/C 유지 |
| 정규화 후 동일 구간의 금지/허용 | 임의 해소하지 않고 충돌 오류 처리 후보 |
| 원문 ‘연구원’, 패턴 ‘원’ | 한국어 왼쪽 경계 불충족 → 미매칭 |
| 원문 ‘3만원’, 가격 패턴 ‘원’·‘만원’ | 가격 예외로 둘 다 검출, 긴 ‘만원’ 유지 |
| 원문 ‘ab cd’, 패턴 ‘abcd’ | 한국어 후보: [0,5), matched_text는 공백 포함 원문. 영어 후보: 미매칭 |
| 영어 원문 ‘ALPHA-BETA’, 패턴 ‘alpha beta’ | 구분자 정규화로 매칭, 원문 하이픈 보존 |
| 영어 원문 ‘alphabet’, 패턴 ‘alpha’ | 오른쪽 단어 경계 불충족 → 미매칭 |

N5의 영어 검사 기록은 source_ko 스냅샷으로 대신하지 않고 해당 번역문/검사 입력 버전을 저장하는 추가 계약 제안이다. 승인 시 audit 구간 대상 필드와 API 표시를 함께 맞춘다. 규제 조건부 숫자 템플릿을 와일드카드로 확장하는 규칙은 여기서 추가하지 않는다(#56). 승인 전 기존 매칭 코드를 교체하지 않는다.

### 5.24 R16-a 구체안 — ④~⑦ 운영 인계（제안 v1·미확정）

개별 개발 함수는 그대로 두고 BE 워커와의 어댑터 계약을 별도 정의하는 안을 추천한다. 함수/JSON 이름·새 키는 여기서 제안만 하며 AnalyzeResult 버전 1과 개발용 결과 버전을 임의로 바꾸지 않는다.

#### 공통 인계 봉투 후보

- BE→AI: `contract_version`, `execution_id`, `attempt_id`, `stage`, `input_snapshot_id`, `image_id`, `section_key`, `section`, `blocks`, `config`, 단계별 추가 입력. 모든 키는 제안이며 DB 컬럼명이 아니다. config는 버전/해시와 실제 사용값을 함께 고정한다.
- `section.image_path`는 해당 워커 환경에 준비된 원본 섹션의 절대 경로다. `blocks`는 source_ko·role·bbox·source_lines의 원시 영역/score를 포함한다. 키는 분석 때 고정한 키를 유지하고 BE만 이번 실행 DB ID에 매핑한다.
- AI→BE: 동일 실행/시도/입력 식별, `outcome`, `payload`, `artifacts`, `diagnostics`, `error`를 제안한다. outcome 후보는 completed/skipped/failed이며 내부 인계용으로만 제안한다. API TaskStatus로 직접 저장하지 않는다. ‘completed’는 단계 계산 완료이며 렌더/검수 진입 보장이 아니다.
- skipped는 사전 합의된 처리 대상 없음에만 사용하고 사유/대상 수를 제공한다. failed에는 결과를 성공으로 저장하지 않으며 단계·분류·retryable 후보·메시지를 제공한다. 오류 코드 문자열/SDK 예외 노출은 BE와 별도 확정한다.
- artifacts는 산출 종류·로컬 절대 경로·크기/형식·내용 해시를 제안한다. BE가 검증·업로드 후 S3 키만 DB에 저장한다. 개발용 상대 경로는 명시된 출력 디렉터리 기준으로 어댑터가 해석하며 작업 디렉터리를 추측하지 않는다. 다른 서버에는 파일을 준비한 뒤 새 로컬 경로를 제공한다.
- 실행/시도 식별만 맞아도 충분하지 않다. 실제 파일 해시, 블록/판정/설정/브랜드 메타 버전 등 해당 단계의 입력 내용을 대조한다. 기존 개발 지문을 완전한 캐시 키로 사용하지 않는다.

| 단계·현재 호출 | 추가 입력/선행 조건 | payload·파일 후보 | 정상 생략·실패·저장 |
|---|---|---|---|
| ④ label.run | 원본 섹션 이미지·블록·라벨 설정. 포함 섹션/proceed 완료는 BE 검증 | 블록별 is_product_label boolean, 입력 확인 정보. 결과 파일 필수 아님 | 블록 0개 skipped. 공백 블록은 기존 false 규칙. 응답 하나라도 누락/중복/비boolean이면 섹션 failed·판정 미저장. is_product_label에만 저장 |
| ⑤ logo.run | ③ MergeResult, 유효 ④ 결과, brand.name_ko·name_en과 버전·해시 | 블록별 is_brand_logo와 생략 근거, 현재 logo_record에 해당하는 입력 확인 기록 | 라벨 true는 NULL/product_label. ④ false 블록은 boolean 필수. 브랜드 메타 누락은 무로고로 판정하지 않음. 전부 라벨이면 모델 호출 없는 skipped 결과와 블록별 생략 판정 인계 |
| ⑥ validate_inputs/build_masks/apply | 원본 이미지, ③ 영역, ④⑤ 결과와 ⑤ 기록, 모델/설정, 워커의 모델 어댑터 | 배경 RGB 이미지, 삭제/보호 마스크·진단은 별도 artifacts. 블록/판정 변경 없음 | 최종 마스크 0이면 모델 호출 없이 원본 배경을 지정한 skipped 후보. 개발 unchanged를 실패로 보지 않음. masked는 운영 배경 완료로 불인정. 추론/파일 오류 failed |
| ⑦ style.run 또는 extract | 원본 이미지, ③ 영역, ④⑤ 결과와 ⑤ 기록, 스타일 설정. ⑥ 결과 불필요 | 블록별 font_color/bg_color/est_font_px/align, 측정 사유·정렬 근거; 상세 영역 진단은 별도 | 대상 없음 skipped. 대상은 있으나 색/정렬 NULL이면 completed 가능, 사유 필수. 입력 오류 failed. style만 저장하고 원본 bbox/role을 수정하지 않음 |

⑤는 #68 M2대로 정해진 정규화 후 한글/영문 브랜드명 완전 일치만 비교한다. 별칭·번역·음역·부분 일치는 공급/비교 대상이 아니다. 개발 자료의 `products[].images` 연결은 운영에서 해당 job의 `brand_id`와 원본 이미지 소속 관계를 기준으로 대체하는 어댑터안을 제안한다. BE가 같은 셀러의 job·brand·이미지임을 확인하고 name_ko/name_en 스냅샷을 제공하며, 현재 개발 함수가 이 운영 입력을 이미 받는 것으로 보지 않는다.

⑤에서 전부 라벨인 경우에도 ⑥⑦ 입력 검증이 소비할 판정/기록은 생성한다. skipped가 필수 인계 자료 누락을 허용한다는 뜻은 아니다. ⑥ 마스크 없음도 ⑨가 쓸 원본 배경 참조가 필요하다. 생략 저장값은 R14가 정하며, 정상 생략과 C4 실패 대체를 혼합하지 않는다.

BE는 ④⑤의 섹션 단위 완전한 판정을 한 번에 반영한다. ⑥⑦⑧은 같은 고정 입력으로 병렬 실행하고 서로 결과를 기다리지 않는다. ⑨는 채택된 배경·스타일·번역과 현재 배치/revision을 소비한다. 각 단계의 진단 자료가 운영 데이터에 필수인지, 산출물 보존 기간은 BE와 결정한다.

검증 사례: 입력 파일 변경·동일 키 다른 블록, 브랜드 name_ko/name_en 버전 변경, 전부 라벨/블록 0개, ⑤ 기록 누락, 마스크 0, mask_only 결과, 스타일 색만 NULL, GPU 성공 후 업로드 실패, 취소된 시도의 정상 결과. 입력 무결성 실패는 빈 성공 결과로 바꾸지 않는다.

### 5.25 R16-b 구체안 — ⑧ 번역과 재검증 인계（제안 v1·미확정）

현재 번역 단계는 미구현이다. 아래는 신규 계약 추천이며 기존 함수가 제공하는 기능으로 표시하지 않는다. 섹션 문맥을 유지하되 저장/재시도 단위는 블록으로 추적하는 구조를 제안한다.

#### 원문 잔존 영역 인계 — #12의 미결 경계

블록 단위 번역 대상만으로 렌더 안전성을 판단할 수 없다. ⑥은 낮은 인식 신뢰도/빈 텍스트 등 보호 영역의 원문을 남길 수 있으므로 같은 블록의 번역을 그 위에 조판하면 겹칠 수 있다. R16 인계에는 원시 영역별 삭제/보호 분류·사유와 최종 보호 마스크(또는 동등한 영역 정보)를 ⑨에 전달하는 안을 추가한다. ⑧은 ⑥ 완료를 기다리지 않고 원문 문맥을 번역하되, 그 번역이 그대로 조판 가능하다고 확정하지 않는다.

선택지는 블록 전체 조판 보류, 보호 영역을 피해 배치, 영역별 번역/조판 분리이며 아직 승인하지 않는다. 기본 블록 번역문을 근거 없이 영역별로 잘라 대응시키지 않는다. BE·AI가 혼합 블록(삭제 영역+원문 보호 영역), 공백만 있는 영역, 전체 보호 블록의 기대 화면/실패/생략을 정하고 사용자 동작 변화는 PM 확인으로 남긴다. #12가 닫히기 전 해당 혼합 사례를 정상 렌더 지원으로 선언하지 않는다.

#### 호출·검증·저장 절차 후보

1. BE가 현재 실행/시도·블록 revision·분류·고정 묶음·용어 공급 상태·상품 검증 준비를 확인한다. AI 입력 검증에서도 ID/누락/형식을 재검사한다. 모델에 문서 내부 명령을 실행 지시로 취급하지 않도록 입력과 지시를 구분한다.
2. AI는 섹션 문맥과 번역 대상 목록을 받아 대상 키마다 정확히 하나의 결과를 반환한다. 누락/중복/알 수 없는 키는 전체 호출 응답의 구조 실패로 처리하고 일부만 임의 성공으로 추출하지 않는 안을 추천한다. 부분 성공은 명시적 블록별 결과가 구조 검증을 통과한 경우에만 허용한다.
3. 번역 후 독립 검증이 현재 문구의 규제 표현·강제 용어·템플릿 치환값을 확인한다. 현지 판정을 영어 번역문에 임의 재적용하지 않는다. 규제 표현 검출은 R04의 N5 규칙이며 검출 사실을 위반 확정으로 바꾸지 않는다. 강제 용어의 대소문자/활용형 허용은 버전된 용어 규칙으로 정하고 모델 자기 보고만으로 적용 성공을 인정하지 않는다.
4. 구조 불량·빈 성공문·미치환 템플릿/입력과 다른 검증 수치는 failed 후보다. 규제 표현 잔존·강제 용어 미적용은 번역문을 보존하고 현재 revision의 검사 근거로 인계하는 안을 추천한다. 검증 호출 자체 실패는 검증 미완료이며 ‘근거 없음’으로 통과시키지 않는다. 재생성 횟수·최종 확정 차단은 R09/R12/R15와 합의한다.
5. BE는 결과 채택 트랜잭션에서 현재 실행/시도·입력 revision을 확인한다. trans_1 변경에 따른 새 revision과 그 문장을 대상으로 한 검증 근거를 함께 연결한다. 검증 당시 입력 revision을 새 저장 revision으로 조용히 혼동하지 않도록 채택된 문장 해시/결과 참조도 인계한다. 구체 증가/비교 방식은 기존 6.3 계약과 BE 구현에서 확정한다.
6. 사용자 수정은 자동 번역으로 덮어쓰지 않고 현재 문구에 대해 검증·재렌더만 수행한다. 자동 번역 재시도는 실패 대상과 유효 입력에 한정하며 성공한 다른 블록을 바꾸지 않는다. 실패/보류가 있어도 N5로 갈 수 있는지는 C4의 별도 결정이다.

#### 소비와 검증 예시

⑨는 번역문과 현재 배치·스타일·채택 배경을 사용하며 ⑧은 인페인트/스타일 결과를 입력으로 기다리지 않는다. 모델 이름·프롬프트·용어 검색 설정·사전/정책 버전·실제 사용 근거를 실행 기록에 고정한다. DB에는 trans_1과 유효 검사 근거만 정해진 자리로 저장하고 개발 응답 전체를 복제하지 않는다.

기대 사례: 대상 0개 → 호출 없이 skipped; 두 블록 중 명시적 1개 실패 → 성공분 보존/실패분 재시도 후보; 대상 키 누락 → 응답 구조 실패; 비공백 원문에 빈 성공문 → 실패; 강제 용어 미적용 → 문장+검사 근거; 상품 검증값 미제공 → 해당 템플릿 호출 준비 미완료; 편집 후 옛 결과 → 반영 거절; 재검증 실패 → 이전/빈 신호로 안전 판정하지 않음; 모든 번역 실패 → N5 진입은 C4 결정 전 허용하지 않음.

**세 구체안의 검토 요청 단위**: R03은 9유형 및 판단 단위, R04는 언어별 경계와 allowed 우선 적용 순서, R16은 공통 봉투/단계 산출물·번역 부분 결과/검증 경계를 각각 승인 또는 수정한다. 모두 ‘구체안 작성 완료·미검증·공동 리뷰 대기’이며 운영 계약 확정이 아니다. 다음은 R01~R20 결정표의 준비 수준을 이번 구체안과 맞추고 한 문서 PR의 리뷰 요청을 준비하는 것이다. 불확실 항목을 임의로 확정하거나 새 논의 목록을 계속 늘리는 대신 해당 행의 대안·근거·결정자를 통해 닫는다.
